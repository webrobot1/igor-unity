## Гигиена браузера

Инстанс браузера один на всех — держать открытым ровно на время САМОЙ браузерной работы: следующая сессия либо агент упрётся в блок «Browser is already in use».

- Открыл сам — сам и закрываю: `browser_close`, как только браузер не нужен БЛИЖАЙШИМИ шагами — уход в серию правок кода, смена задачи, конец проверки, финальный отчёт, ДОЛГИЙ не-браузерный этап между браузерными шагами (прогон проверок, замер анализатором, добор данных MCP-тулами, ожидание чужого исполнителя). Решает нужда ближайших шагов, не ощущение «закончил»: явного «закончил» при чередовании проверок с правками не наступает. Подготовительный шаг ТОЙ ЖЕ браузерной работы закрытия не требует — правка файла, результат которой прямо сейчас уходит в уже открытую страницу (собранный текст либо картинка под вставку); закрытие между такими шагами теряет несохранённое состояние страницы. Общее намерение продолжить подготовительным шагом НЕ является — как и не-браузерный этап, чей результат в открытую страницу не уходит: на его время браузер закрывается, хотя браузерная работа не закончена и продолжится после. Намерение вернуться и оценка «этап короткий» держать открытым не разрешают — длительность следующего этапа оценивается ДО него и систематически занижена, повторное открытие стоит одного вызова против блокировки чужой сессии на неопределённый срок. Чек в конце КАЖДОГО хода: браузер открыт, а ближайший шаг его не требует → `browser_close`.
- Знание об открытости браузера даёт ВЫЗОВ закрытия, не память о своих прошлых закрытиях: между прошлым закрытием и текущим шагом лежит повторное открытие, и «я же закрывал» относится к прежнему эпизоду. Напоминание хука об открытом браузере памятью не проверяется — реакция на него одна: `browser_close`. Вызов дёшев и повторим: браузер уже закрыт — ответ безвреден, инстанс занят чужой сессией — приходит отказ; оба исхода состояние называют, догадка его не даёт. Признак промаха, ловимый самим автором: напоминание сверено с памятью о своём закрытии и объявлено инерцией хука.
- Параметр имени файлового артефакта тула (скриншот, дамп сетевых запросов, снапшот страницы) либо не передавать вовсе, либо задавать абсолютным путём в каталог инструмента (`core` «Место файла, заведённого по ходу работы», `core` «Файлы»). Артефакт, который должен ПЕРЕЖИТЬ закрытие браузера (материал продукта — кадр сцены ролика, вложение статьи), под адресом из своего вызова не остаётся: адрес, названный параметром вызова, хук уборки снимает следом за `browser_close`. Такой файл переносится на своё рабочее место ТЕМ ЖЕ проходом, что съёмка — по новому адресу уборка его не находит. Описание тула обещает обратное (относительное имя остаётся в каталоге инструмента) — на дефолт не полагаться.
- Свои браузерные артефакты в каталоге инструмента снимает хук проекта следом за своим `browser_close`; своя обязанность тут — само закрытие. Прочего в каталоге хук не касается: чужие файлы и собственные рабочие материалы задачи остаются, своё снимает сам вызывающий (`core` «След своего прохода»). Вручную каталог не чистить: типовой промах ручной уборки — маска по текущей директории, сносящая файлы корня проекта (`core` «Файлы»). Отчётная строка об уборке приходит не на каждое закрытие — её отсутствие ручную уборку не разрешает.
- Открыл не я — не трогаю: вкладка браузера пользователя за собой не закрывается, инстанс под чужой сессией не закрывать и артефакты его не чистить (отказ «браузер занят» → уборки нет вовсе).

Триггер срыва: браузер оставлен открытым после использования — серия проверок вперемешку с код-правками, висит несколько ходов; ЛИБО после проверки ушёл в долгую серию правок кода под намерение скоро вернуться — пользователь: «ты пошел код писать в mcp play оставил открытым»; ЛИБО держал открытым весь долгий не-браузерный этап (прогон проверок), простой заметил пользователь раньше агента; следующий вызов заблокирован — «ты не закрыл браузер» (в т.ч. повторно); ЛИБО закрыл браузер между подготовкой файла и вставкой результата в открытую страницу — несохранённое состояние страницы потеряно; в корне репозитория копятся неотслеживаемые png — «почему скриншоты оказываются не в `.playwright-mcp`». ЛИБО два напоминания хука подряд сверил с памятью о своём прошлом закрытии и счёл инерцией — после того закрытия браузер открывался снова; закрывал пользователь: «почему ты снова не закрыл плеер, что мне пришлось за тебя закрывать — и хук, и правило только сегодня усиляли».

## Приёмы браузерной автоматизации

- Отладочный режим включён → панель профайлера Symfony (`.sf-toolbar`) лежит поверх страницы и попадает в кадр: скрывать её перед снимком, не вырезать обрезкой после.
- Клик берёт ПЕРВЫЙ элемент под селектор. Цель отбирать признаком, однозначным для неё (текст кнопки): класс либо тип цель не идентифицируют — повторяются на странице. Однозначного признака нет → перед кликом сверить число совпадений селектора и позицию цели среди них.
- Команда не завершилась, а действие не произошло → первым исключить блокиратор ВНЕ разметки страницы: нативный диалог ОС держит вкладку, а снимок страницы его не несёт — оттого и диагностика инструмента (указание на блокирующий JS-диалог, «страница правку не принимает»), и сам снимок уводят ВНУТРЬ страницы, где причины нет. Типовой источник — клик, попавший в чужую кнопку загрузки файла. Разметку и селекторы разбирать после того, как блокиратор исключён.
- Файловый диалог Playwright перехватывает штатно: клик по кнопке загрузки → `browser_file_upload` с абсолютным путём. Не перехватило → запасной приём патчем `HTMLInputElement.prototype.click`→upload. Оригинальный `click` восстановить сразу после загрузки — иначе у пользователя перестаёт открываться ручной файловый диалог. Kapture путь файлового диалога не проходит: шаг загрузки локального файла ведётся только Playwright. Playwright занят — шаг на запасной канал не переложить (`orchestration` «Самостоятельность»), дальше по `core` «Нужный ресурс недоступен».
- Диалог ОС (выбор цвета, шрифта) Playwright недоступен — ограничение инструмента, не сайта. Обход: буфер обмена плюс `Ctrl+V`, вызов API страницы либо шаг человека.
- Каталог файла НА загрузку ограничен рабочим каталогом проекта и каталогом инструмента: путь во временный каталог сессии отклоняется. Готовый файл копировать в разрешённый каталог перед загрузкой.
- Редактор либо компонент, ведущий собственную модель содержимого, сериализует из неё: прямая мутация DOM либо поля ввода теряется. Менять только его публичным API — командой редактора, установкой состояния, сбросом через жизненный цикл.

## Kapture: вкладка браузера пользователя

Kapture ведёт из WSL реальный Chrome на Windows — вкладку, уже залогиненную пользователем: своего входа агент не делает.

- Без фокуса окна работают `fill`, `keypress`, `dom`, `elements`, `navigate`, `reload`. Активного окна Chrome требуют `click`, `screenshot`, раскрытие свёрнутого блока
- `fill` заменяет содержимое поля целиком, переносы строк сохраняются
- Сохранение — `keypress Enter` по кнопке сохранения, не `click`. Коммит проходит только при окне Chrome в фокусе ОС: на время прогона пользователь держит фокус и компьютера не трогает
- Поток правки: navigate → fill → keypress по кнопке сохранения → проверка записи по состоянию кнопки в `dom`. Записанное не предполагать
- Прогресс длинного прогона вести в отдельном рабочем файле: он переживает рестарты и суммаризацию
- Кадр со вкладки браузера пользователя (скриншот страницы либо по селектору) принимать только после проверки поля видимости вкладки в ответе тула: вкладка невидима — кадр ложно-пуст (белый лист) при полностью отрисованном DOM. Команда вывода вкладки на передний план подтверждает лишь приём: окно браузера у пользователя не на переднем плане — поле видимости остаётся отрицательным и в последующих ответах. Скрытой вкладке браузер не выдаёт кадров анимации (`requestAnimationFrame`) — отрисовка замирает на произвольной стадии, частичный кадр читается дефектом «слой не рисуется», ожидание завершения не лечит. Пустой кадр либо висящие заглушки загрузки — повод перемерить видимость, не диагноз дефекта своей вёрстки или рендера. Видимость не наступила → снимать своим Playwright; он занят — ресурс удерживается сессией пользователя, дальше по `core` «Нужный ресурс недоступен». Триггер срыва: белый кадр со скрытой вкладки принял за факт и несколько заходов искал дефект в собственной вёрстке и рендере, пока не сопоставил пустоту кадра с полем видимости.
