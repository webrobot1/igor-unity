Правила написания и рефакторинга кода, не зависящие от языка. PHP-специфика — skill `php`, C#/Unity — skill `csharp`, скрипт страницы админки — skill `twig`.

## Типы

- Ссылка на тип — импорт короткого имени в шапке файла, не полное имя с пространством имён в точке использования. Тип, импорта не требующий (встроенный, глобального пространства языка), — вне правила. Встреченный inline-прецедент — не образец для копии (core «Копирование прецедента»)
- Форма возврата набора записей — по способу АДРЕСАЦИИ у потребителей: адресуют по идентичности (id/slug/хеш) → источник отдаёт словарём с этим ключом; только перебирают → позиционный список. Ключ-идентичность внутри значения не дублировать. Детектор — одинаковое пост-преобразование набора у ДВУХ и более потребителей (перекладка списка в словарь циклом, повторный поиск нужной записи по полю, ручная индексация): форму держит не тот слой, чинить в источнике, перекладку у потребителей снять (частный случай core «Root-fix у источника»). Проверять при написании метода и при появлении ВТОРОГО потребителя, не только на ревью и рефакторинге. Ось — ВЫБОР формы; последствия ПРАВКИ уже выбранной (снятый либо переименованный ключ у потребителей) — skill `php`. Вывод MCP-тула — своя ось: skill `mcp` «Словарь vs список в контуре тула». Триггер срыва: оба фронта переложили полученный список в словарь по одному и тому же полю; пользователь: «и не проще ли сразу по карте собирать в ключе… чтобы не пересобирать».

## Отказ и дефолт

- Невалидный ввод/импорт/коллизия инварианта → fail-fast: отказ исключением. Запрещено «спасать» подгонкой данных под инвариант (обнулить, обрезать до границы, отбросить, подменить поле), в том числе с предупреждением — предупреждение не разрешает записать изменённые данные. Подгонка прячет ошибку, которую чинят у ИСТОЧНИКА данных, и портит рабочие данные. Тот же запрет — на ОБХОД негодного экземпляра: данные не правятся вовсе, испорченный пропускается ради следующего равноправного кандидата (другой донор, другая копия, соседняя реплика). Самопроверка «не подгоняю ли значение» его пропускает — данные целы, а дефект источника остаётся невидимым. Исход тот же: исключение, называющее негодный экземпляр. Перебор кандидатов ради устойчивости к негодному экземпляру есть проектирование вокруг неверного состояния источника (core «Root-fix у источника»): там ось — ГДЕ чинить, тут — чинить или упасть. Best-effort с пропуском/подгонкой — только явное продуктовое требование, не дефолт. Атомарность отказа (откат, побочные эффекты на ФС и кеш) — skill `php`. Триггер срыва: «мягкая пред-проверка», ставящая поле в null с предупреждением вместо отказа; перебор кандидатов-доноров пропускал экземпляр с неполным против объявленного составом и брал следующего, хотя неполнота есть след прошлого сбоя у источника; пользователь: «при нормальнйо ситуации не может не совпадать количество слотов. не надоторентироваться на ненормальную. если чего не будет хватать можно ошибку выдавать»
- Перехваченное исключение, из которого потребителю показывают только текст сообщения (всплывающее уведомление, модалка, поле ошибки в ответе), записывать в журнал вместе со стеком. Автоматический журнал рантайма пишет лишь НЕперехваченные исключения — пойманное идёт мимо него, и причина остаётся видна только по тексту сообщения

### Дефолт против исключения

Требование не возвращать молча дефолт не запрещает дефолт как таковой: пустой ответ аксессора (null, false, 0, пустая коллекция) несёт один из двух смыслов, различать по тому, что значение значит для вызывающего.

| Смысл пустого ответа | Что это | Исход |
|---|---|---|
| Легитимное отсутствие | спроектированный ответ, у вызывающего есть корректная реакция: записи нет в справочнике, у действия нет своего варианта → общий fallback | дефолт оставить |
| Зависимость не готова | кеш не загружен, инициализация не отработала, метод вызван до своей предпосылки | бросить исключение |

Одно и то же значение означает И отсутствие, И неготовность → это и есть маскировка: развести — исключение на «не готова», дефолт только на «отсутствие».

Признаки маскировки:

- значение приходит из ветки по полю-кешу, заполняемому один раз при инициализации либо входе
- у вызывающего нет отдельной реакции на «не готов» — он трактует дефолт как отсутствие и едет дальше (сущность без визуала, флаг тихо false)
- предпосылка гарантирована порядком инициализации → дефолт-от-неготовности в норме недостижим, значит его появление есть баг, обязанный падать

Признаки легитимного дефолта:

- try-семантика поиска, где «не найдено» — обрабатываемое состояние
- состояние «не готов» невозможно (валидируется у источника на входе) ЛИБО у вызывающего есть fallback именно на этот дефолт, а не «поехали дальше»

По признакам непонятно → не угадывать дефолтом: прочитать вызывающие места (что они делают с дефолтом) и порядок инициализации. Ось — СМЫСЛ пустого значения для вызывающего; запрет снимать сам сигнал ошибки ради исчезновения симптома — core «Не глушить сигнал ошибки».

## Огораживание ввода

Перечислимое/справочное значение во ВВОДЕ (MCP `inputSchema`, JSON API, admin-select, WebSocket-команда) — огораживать: точный выбор из достоверного источника (`ref` на list-tool / `EntityType`/`ChoiceType` / справочник) + валидация против него ДО обработки, не произвольный текст. Идентификатор цели действия → path/обязательный ref; фильтр/опция → query. Исключение (нужна свобода: `code`/`data`/payload) — документировать явно. Доменная механика — skill `mcp` (`ref`) / `admin` (path vs query).

Запись ЧАСТИЧНА (partial — непереданное сохраняет прежнее значение) → проверка входа считает ИТОГОВОЕ состояние (присланное, наложенное на текущее), не присланный фрагмент. Нарушитель обходит проверку по фрагменту умолчанием: непереданное в базу расчёта не попадает, а в состоянии остаётся. Триггер срыва: проверка на неувеличение количества считала итоги по присланному словарю — клиент слал предмет в новый ключ, не упоминая старый, предмет оставался в обоих.

Место проверки внутри операции задаёт ЗАВИСИМОСТЬ условия от данных: проверяемое по одному лишь входу (диапазон, форма значения, сочетание параметров) стоит первым блоком операции — до первого обращения к носителю данных; требующее данных — сразу за их получением. Проверка входа, стоящая ЗА обращением к носителю, недостижима, когда обращение падает раньше: отказ приходит про чужой предмет, а на состоянии, где данных нет вовсе, негодный вход не проверяется ни разу. Механизм промаха: место проверки выбирается по точке, где значение ИСПОЛЬЗУЕТСЯ, а используется вход после подъёма данных. Признак промаха, ловимый самим автором: между сигнатурой и проверкой стоит обращение к носителю, а сама проверка о носителе ничего не утверждает. Исход — ПЕРЕНОС проверки вверх: недостижимость тут свойство места, снос мёртвой ветки (`core` «Root-fix у источника») — про ветку, состояния которой не создаёт ни один канал. Ось соседа: «Дедупликация» ниже держит ФОРМУ предусловия — инлайн против отдельного метода, — о месте его среди шагов операции молчит. Триггер срыва: гард диапазона параметра стоял за подъёмом справочника — по пустому справочнику приходил отказ про справочник, негодное значение параметра не проверялось вовсе.

## Запрещённое действие — не молчать

Действие без легитимного исхода (дубль; повтор операции, для чьих реальных целей есть иные инструменты — обновить, сбросить) → `throw` либо guard на входе не пускает, НЕ молчаливый возврат существующего / no-op: молчание маскирует, что действие недопустимо или бессмысленно. «Идемпотентное смягчение» разрешать недопустимое не оправдывает — внутренний потребитель, которому нужен уже существующий объект, ищет его ЯВНО (lookup / иной путь), не через ту же создающую операцию. Родственно `php` «Подавление ошибок» (коллизия инварианта → fail-fast) и «Огораживание ввода» выше (guard на входе). Триггер срыва: разрешил повтор запрещённого молчаливым возвратом существующего под предлогом «идемпотентность нужна внутреннему вызову»; пользователь — «для обновления/сброса есть инструменты, зачем давать сделать недопустимое».

## Боевой потребитель новой возможности

Заводя в продукт новую возможность (тул, параметр, поле, контрол, метод), НАЗВАТЬ её потребителя ВНЕ тестирования и его задачу: игрок, гейм-дизайнер в админке, механика игры, внешний ИИ в рабочем сценарии. Потребитель не называется → не заводить: облегчение собственной проверки и прогона спек потребителем не является. Нужду прогона закрывать существующими каналами либо разовым артефактом (`core` «Канал доступа к данным») — тот и так временный.
Граница — РАБОТОСПОСОБНОСТЬ канала, не удобство проверяющего. Без чего канал не отдаёт данные НИКОМУ (срез ответа, не влезающего в лимит вывода) — свойство самого канала: заводится независимо от того, кто первым в лимит упёрся, потребителя ему называть не требуется (обязательность и форма среза — skill `mcp` «Срез вывода read-тула»). Что лишь сужает выдачу под конкретный вопрос (фильтр по значению поля) — возможность: потребителя ей называть по правилу выше.
Демаркация: `core` «Root-fix у источника» меряет ЧИНИТЬ ЛИ найденный дефект, тут — СТРОИТЬ ЛИ новую возможность; `core` «Временное отступление от правила» — намеренное нарушение со снятием тем же проходом, тут — постоянный код в продукте.
Триггер срыва: предложил тулу фильтр, которым весь парк данных проверяется одним вызовом, — потребитель нашёлся только в прогоне спек; пользователь: «это не боевой функционал — искать по размерам нужно только для тестов и проверки спек».
Ветка ПРИЁМА либо ОБРАБОТКИ второй формы значения — второго вида входа, второго состояния данных — проходит тот же тест со стороны ПРОИЗВОДИТЕЛЯ: назвать свой КАНАЛ ЗАПИСИ, фактически создающий такую форму (форма админки, MCP-тул, выгрузка, импорт). Потребитель такой ветки воображается всегда, и тест по нему проходит формально: «кому-то пригодится» названо, а вопрос «чем это значение у нас создаётся» не задан ни разу. Ни один свой канал форму не создаёт → ветку не заводить: форма отбивается отказом, а принимать ли её вообще — правило продукта, решает пользователь (`core` «Правило продукта — решение пользователя»). Шаг, на котором промах неизбежен, — момент, когда под встреченную форму пишется ВЕТКА вместо ОТКАЗА. Признак промаха, ловимый самим автором: ветка обрабатывает форму, которой ни один свой канал записи не производит. Каналы записи перебирать ЦЕЛИКОМ — `core` «Полнота охвата и проверки» (каналы наполнения носителя): там обход предшествует СУЖДЕНИЮ о содержимом, тут — заведению поведения. Соседи по иным осям: «Множество потребителей внешнего канала» ниже запрещает СУЖАТЬ проверку доводом «свой клиент так не шлёт» — противоречия нет, оба ведут к отказу: там всякий дотянувшийся до канала обязан пройти гейт, тут чужая форма встречает отказ вместо собственного поведения; «Отказ и дефолт» выше — невалидный вход и запрет подгонки, тут форма объявлена валидной самим контрактом; `core` «Утверждение о коде — после чтения ЭТОГО кода» (достижимость ветки на приходящих данных) — истинность утверждения об уже существующей ветке, тут решение её не писать. Триггер срыва: обложка записи каталога принималась в двух видах — имя файла в репозитории записи либо адрес на стороннем сайте, — и второго не создавал ни один свой канал: обложка грузится картинкой через форму админки и MCP-тул, оседает файлом, выгрузка пишет в манифест только имя файла, импорт этого поля не читает вовсе; взяться адрес мог лишь ручной правкой чужого манифеста, а публичная витрина ставила его в тег картинки — браузер посетителя шёл к третьей стороне. Ветка была размазана по семи носителям, верным исходом был отказ при синхронизации.

## Охват новой механики по носителям и каналам

Механика реализована у ОДНОГО носителя → назвать КЛАСС носителей, которым она применима, и провести её по классу целиком; у каждого носителя — по ВСЕМ каналам, которые к нему ведут (форма админки, MCP-тул, обновление из внешнего репозитория, импорт, установка из каталога; список открытый). Класс задаёт СВОЙСТВО, ради которого механика заведена, не имя типа, каталог либо модуль: носитель того же класса лежит в другом модуле и под именем, к правимому не близким.
Промах молчит по конструкции: канал, механики не получивший, работает по-прежнему и отказа не даёт — он о ней не знает вовсе, а его собственный успешный исход утверждает о ЕГО действии и читается подтверждением полноты.
Шаг, на котором промах неизбежен, — сдача работы после первого канала: механика проверена там, ради чего писалась, и вопрос «чем ещё приходит то же состояние» не задаётся ни разу.
Признак промаха, ловимый самим автором: механика написана в точке, куда её привёл вход задачи, а перечень носителей класса и каналов к каждому не составлялся.
Носитель либо канал остаётся без механики по решению пользователя (`core` «Правило продукта — решение пользователя»), своим усмотрением из класса не изымается.
Соседи по иным осям: «Боевой потребитель новой возможности» выше решает, СТРОИТЬ ЛИ возможность, и об охвате построенной молчит; «Единый источник истины» ниже, абзац о заведении общего носителя, обходит проект в поисках СУЩЕСТВУЮЩИХ копий механизма под подключение к канону, тут у носителя либо канала поведения нет вовсе; `php` «Дедупликация» несёт инстанс этого правила для пары фронтов одной операции; `core` «Многофайловая правка» задаёт множество носителей у ПОЧИНКИ дефекта, тут чинить нечего — реализация своя и новая; `core` «Полнота охвата и проверки» держит охват АНАЛИЗА перед суждением, тут охват РЕАЛИЗАЦИИ; `core` «Фактический вопрос ≠ нормативный» читает конвенцию по соседям-аналогам ради ДОВОДА о желаемом устройстве — направление там обратное, от соседей к одному, обязанности обхода оно не несёт.
Триггер срыва: перечень потерянного при заливке собрал сервис записи и довёл до человека фронт формы, а второй канал того же носителя — обновление из внешнего репозитория — те же возвращённые сервисом потери отбрасывал и объявлял обновление успешным; ЛИБО правило видимости записей вынес в метод сервиса у одного типа сущностей, а у соседнего типа того же класса та же механика осталась написанной по месту дважды, во втором месте без учёта владельца — ровно с дефектом, ради снятия которого вынос и делался.

## Множество потребителей внешнего канала

Проектируя ВЫДАЧУ либо ПРИЁМ на канале, доступном извне (эндпоинт игрового клиента, публичный роут, внешний API), множество потребителей считать по тому, что канал ДОПУСКАЕТ, не по тому, как ходит свой клиент: его поведение — свойство сегодняшней его версии, а зовёт канал и недобросовестный потребитель, любым допустимым значением.
Границу выдачи задаёт проверка НА САМОМ канале, у каждой точки входа своя. Отбор, стоящий у перечисляющей операции, границей для выдачи по прямому идентификатору не служит — точка входа там другая, проверку она держит сама.
Признак промаха, ловимый самим автором: безвредность обоснована ПОВЕДЕНИЕМ потребителя («таких запросов не делает», «идентификаторы берёт из перечня»), а не проверкой, стоящей на канале.
Соседи по иным осям: «Огораживание ввода» выше — ФОРМА значения на входе, тут ОХВАТ множества, обязанного пройти проверку; «Боевой потребитель новой возможности» выше — СТРОИТЬ ЛИ возможность, тут она построена и считаются дотянувшиеся до неё; `core` «Root-fix у источника» — тест достижимого сценария вреда, где на внешнем канале достижимо всё, что канал допускает, и поведением своего клиента множество не сужается.
Триггер срыва: перечень записей отдавал лишь выданные в игру, а выдача по прямому идентификатору проверяла только принадлежность записи игре — любой обладатель валидного токена выкачивал невыданное, черновики и тестовое; безвредность обосновывалась тем, что клиент таких идентификаторов не спрашивает; пользователь: «не надо ограничиваться только действием потребителя, надо думать и что было бы, если потребитель был бы другим (например, злоумышленник)».

## Ограничение модели — по названному вреду

Вводя в проектируемую модель ОГРАНИЧЕНИЕ — запрет, уникальность, взаимоисключение «либо A, либо B» — назвать вред от его ОТСУТСТВИЯ: что сломается либо испортится, у кого и при каком действии. Вред не называется — ограничения не вводить, разрешённое остаётся разрешённым.
Отсутствие сценария ИСПОЛЬЗОВАНИЯ ограничение не оправдывает: «не вижу, зачем так делать» — довод не строить механику ПОД случай, а не запрещать его. Стройность модели («единица описывает один предмет»), симметрия и аккуратность вредом не являются.
Названный вред подтверждается фактом тем же проходом; подтверждения нет — ограничение снять с предложения, не смягчать формулировку.
Ограничение есть ГЕЙТ доступа к данным → вред подтверждается обходом ОСТАЛЬНЫХ каналов, отдающих те же данные, и тем, чем закрыт каждый. Соседний канал отдаёт без единого условия — вреда от отсутствия гейта нет вовсе: он закрывает копию того, что рядом лежит открытым, и оставляет пустые места у своего же потребителя, которому те же данные открыты. Соседний канал сужает выдачу собственным критерием — копия обязана держать ТОТ ЖЕ критерий, иначе она и есть его обход. Требование держит КОПИЯ содержимого; производное представление, по которому исходного содержимого не восстановить, копией не является — критерий соседнего канала на него не переносится. Признак промаха, ловимый самим автором: гейт обоснован адресом своего канала («канал служебный», «сюда ходит только свой»), а не тем, чем те же данные закрыты у соседа. Оси соседей: «Множество потребителей внешнего канала» выше считает потребителей ОДНОГО канала, тут перебираются НЕСКОЛЬКО каналов к одним данным; `core` «Полнота охвата и проверки» обходит каналы НАПОЛНЕНИЯ носителя перед суждением о содержимом, тут — каналы ВЫДАЧИ перед введением гейта. Триггер срыва: картинку раздела каталога служебный роут гейтил правом, а публичная витрина отдавала ту же картинку анониму своим роутом без единого условия — гейт закрывал копию открытого и давал битые плитки своему же читателю; у картинок записей каталога тот же публичный канал сужен публичностью записи, а служебный роут отдаёт превью — производное, не копию: проверка с него снята, критерий соседа остался на самом продукте.
Гейт точки входа (роут, эндпоинт, тул) строится на СВОИХ данных — принадлежности адресуемой записи, её собственном критерии видимости. Вызов проверки доступа к ПОСТОРОННЕЙ точке входа гейтом не является: он выражает доступ к ДАННЫМ через доступ к чужой странице, а одни и те же данные показывают разные страницы. Связь двух точек входа такой гейт держит молча — у второй меняют имя, право либо состав страницы, и первая начинает отдавать либо отбивать не то, по её собственному коду этого не видно. Своего критерия у записи нет вовсе → заимствованной проверкой его не подменять, а спросить, ЧТО отдаёт канал. Отдаётся производное представление, по которому исходного содержимого не восстановить, — закрывать нечего, гейта нет вовсе. Отдаётся само содержимое либо продукт — нужен свой критерий у записи либо собственное право роута. Признак промаха, ловимый самим автором: гейт называет ЧУЖОЙ адрес, а не свойство отдаваемой записи. Ось — ЧЕМ гейт построен, когда он нужен; НУЖЕН ЛИ он — абзац выше. Триггер срыва: превью записи в служебном разделе закрывалось проверкой доступа к списку своего типа — доступ к данным записи выражался доступом к чужой странице; пользователь: «надо запретить ограничивать доступ к определенному route путем внедрение в него проверки на доступ к другому».
Зеркало теста достижимого сценария вреда (`core` «Root-fix у источника»): тот стоит на решении ЧИНИТЬ ЛИ найденное, тут — ЗАПРЕТИТЬ ЛИ разрешённое, бремя то же. «Боевой потребитель новой возможности» выше меряет, СТРОИТЬ ЛИ возможность.
Триггер срыва: предложил правило «набор картинок занимает либо префаб, либо компонент, но не оба», обосновав тем, что набор описывает один предмет; вреда от совмещения не назвал и при проверке не нашёл; пользователь: «я не вижу проблем привязывать и prefab и компонент (то если трогать можем что то сломать). то есть поламать это не поломает полагаю ничего но вопрос зачем кому так делать правда».

## Механика игры — в её контенте

Механика конкретной игры реализуется её собственным контентом: элементы игры со своим кодом (компоненты, команды, префабы), код механик в песочнице. Платформа под неё не подстраивается: ради одной механики не заводят ни поле сущности платформы, ни справочник, ни новый канал доставки данных клиенту. Платформенный код бандлов и схемы MCP под неё не правят.
Проба перед предложением расширить платформу: назвать потребителя ВНЕ этой игры — класс механик, который возможность закрывает у ЛЮБОЙ игры на платформе. Не называется → решать в контенте игры. Обратная сторона: расширение законно, когда его обоснование формулируется без имени конкретной игры и её механики.
Зеркало той же оси: платформенное обоснование («любой клиент», «все игры») требует и НОСИТЕЛЯ, общего всем названным потребителям. Разделяемый носитель уровнем ниже — фреймворк либо библиотека механик — общим им не является: его множество ограничено взявшими этот же носитель, игры на прочих остаются без правки. Второй фильтр — доедет ли правка хотя бы до этого множества: экземпляр носителя у потребителя есть его собственная копия, наружу она отдаётся только каналом отправки наверх, а копия, ведомая вышестоящим источником и без права отправки, не отдаёт её вовсе. Провенанс и право отправки лежат в мета носителя (раскладка каналов — MCP instructions), читать их ДО правки. Проба: назвать потребителей, ради которых правка вносится, и путь, которым она дойдёт до каждого; путь не называется — платформенное решается кодом платформы.
Демаркация: «Боевой потребитель новой возможности» выше меряет, СТРОИТЬ ЛИ возможность вообще; skill `spec-rules` — куда класть спеку игрового контракта; тут — ЧЬЯ сторона механику реализует.
Триггер срыва: ради вкладок книги заклинаний одной игры предложил завести поле «вкладка книги» у сущности групп команд и возить клиенту новый справочник групп; пользователь: «зачем ты предлагаешь заводить поле вкладка кииге вообще - то есть ради одной механики конкретной игры я как понимаю ты хотел аж не то что фреймворк или код игра а игровые тулзы под одну механнику переделать ?», «у нас разве нет skill про это мы мы не меняем код бандлов под конкрертную механику»; решение осталось в контенте игры — структурой значения у компонента префаба.
Триггер срыва зеркала: правку, обоснованную тем, что недействительного значения не должен получать клиент ЛЮБОЙ игры, внёс в копию фреймворка одной игры — копию ведёт вышестоящий источник, отправки наверх у неё нет by-design, до других потребителей правка не дошла бы никогда.

## Место правки на маршруте данных

Причину закрывает не одна точка: у значения есть маршрут (вычислитель → сборка пакета → канал доставки потребителю), правка законна на каждом звене. Лестница `core` «Root-fix у источника» выбирает, ЧЕМ чинить; тут — ГДЕ.
Проба ДО правки: пройти маршрут до потребителя и назвать проходы, которые по этим же данным УЖЕ идут. Правка ложится в тот, где нужный признак УЖЕ вычислен, — там она сводится к условию внутри готового цикла.
Собственный обход тех же данных ради одной проверки — параллельный механизм поверх существующего; его цену умножает частота прохода, и на пути, идущем каждый кадр либо на каждую запись, она становится решающей. Признаки чужой точки: под правку заводится цикл; повторно добывается то, что соседний проход уже держит.
Соседи по иным осям: `core` «Root-fix у источника» запрещает лечить у ПОТРЕБИТЕЛЯ вместо источника — тут каждая точка причину закрывает; «Решение — там, где есть контекст» ниже про границу ЗНАНИЯ, тут про цену и готовый признак.
Триггер срыва: фильтр недействительного значения внёс в общий сборщик изменений сущности, идущий для каждой изменившейся сущности каждый кадр; пользователь: «довольно дорогая операция… может, на уровне websocket это дешевле сделать, например если уже какой-то цикл есть» — в канале доставки шёл проход по тем же данным с уже готовым признаком, правка свелась к одному сравнению.

## Решение — там, где есть контекст

Код ВЫБИРАЕТ представителя из нескольких равноправных входов (первый попавшийся, минимальный, «любой из»), потому что настоящее значение зависит от контекста, которого в этой точке НЕТ, — признак, что решение принимается НЕ НА СВОЁМ МЕСТЕ. Лечение: перенести решение туда, где контекст однозначен, либо не принимать его здесь вовсе.
Граница правила — тест «меняет ли выбор представителя ИСХОД»: варианты эквивалентны по последствиям → выбор безвреден; исход зависит от того, кого выбрали → решение не на месте.
Замена эвристики выбора (с «первого» на минимальный/максимальный/усреднённый) дефекта не снимает: произвол сохраняется, а на входах, где представители расходятся, добавляется систематически ложный исход.
Чаще всего недостающий контекст — ВОЛЯ человека, ради которого действие и совершается. В коде он не восполним ничем: ни эвристикой, ни случайным выбором, ни «разумным умолчанием» — искомое значение существует только у человека. Решение переносится туда, где выбор делает он сам, и приходит в код готовым — параметром действия; действие ведёт к выбранному само.
Выбирая за человека, механика отнимает и возможность НЕ действовать: исход наступает сам, отказаться от него нечем. Признак — действие, привязанное побочным к другому: не выбрано ни то, над чем оно совершается, ни оно само.
Демаркация с `core` «Root-fix у источника»: там ось — КУДА чинить дефект; тут — ГДЕ проходит граница знания, за которой решение принять нечем. Перенос выбора к человеку меняет само правило продукта → выносится ему по `core` «Правило продукта — решение пользователя»; тут — признак, по которому дефект опознан.
Триггер срыва: guard мерил условие по «первому потребителю» глобальной сущности, хотя у каждого потребителя своя единица измерения; «усиление» выбором минимального дало бы ложные отказы; пользователь: «а как он мерит блокируемую клетку, если у тайла может быть несколько тайлсетов, у каждого свой размер нарезки, а выбираем блокировать или нет мы глобально без выбора карт» — решение перенесли в расчёт, знающий конкретного потребителя, выбор представителя исчез. ЛИБО подбор вещи с земли стоял побочным действием ходьбы: дойдя до клетки, код клал в инвентарь последнюю из лежащих — игрок не мог ни выбрать вещь, ни пройти по вещам, не подняв их; замена «последней» на ближайшую либо случайную выбора ему не вернула бы, починкой стал перенос решения к игроку — цель приходит его командой, действие ведёт к ней само.

## Переопределение с вкладом родителя

Переопределяя метод-носитель вклада родителя/примеси (вклад в результат/побочный эффект/мета/инициализацию) — осознанно: либо вызвать родительский вклад (`parent::`/`base.`/`super.`), либо полностью заместить; молчаливый дроп вклада — баг, не выбор. Кросс-доменно: PHP trait/parent, C# `base.`, JS `super.`, mixins/middleware/декораторы, Unity-контроллер с `Awake`/`OnEnable`/`OnDisable` без `base.*`. Триггер срыва: наружу/в кэш/в сериализацию не попало то, что давал родитель. PHP-механика (алиас трейтового метода + merge, class-over-(parent|trait) без `insteadof`) — skill `php` «Наследование».

## Оповещение о смене состояния

Состояние ведёт один компонент, читают его несколько → синхронизирует читателей ОБЪЯВЛЕННЫЙ канал оповещения, срабатывающий на КАЖДОМ пути смены состояния. Путь через контрол человека поднимает событие сам; программный — вызов api компонента, применение фильтра, восстановление сохранённого, начальная установка — не поднимает, и второй читатель молча остаётся на прежнем значении: расхождение не ловят ни компилятор, ни тесты, видно оно только на экране.
Точка срабатывания — появление у состояния ВТОРОГО читателя: перечислить все пути смены и провести каждый через канал.
Путь мимо канала лечится в точке, ОБЩЕЙ всем путям, — оповещение поднимается там, где состояние меняется. Вторая подписка у читателя и вызов оповещения у каждого инициатора закрывают по одному пути, следующий остаётся сломанным.
Канал, объявленный СЛОВАМИ (коммент, докблок «управление приходит событиями»), механикой не обеспечен: пути сверять по коду, поднимающему событие, — объявление проверки не заменяет.
Соседи по иным осям: `core` «Root-fix у источника» — защита инварианта на всех точках ЗАПИСИ значения, тут значение верно, а о смене не узнал читатель; «Единый источник истины» ниже — ДВА носителя одного состояния, тут носитель один; «Свежесть производного артефакта» ниже — годность сохранённой копии по её отметке, тут оповещение живых читателей.
Триггер срыва: второй проигрыватель страницы узнавал о смене клипа только из события выпадающего списка, а первый менял клип ещё тремя путями — фильтром строки, кнопкой строки, вызовом своего api, — события при этом не поднималось, второй оставался на прежнем клипе; в его же комментарии канал был объявлен теми же событиями.

## Свежесть производного артефакта

Годность уже существующей копии производного (ответ по условному запросу, файловый кеш) решает ОТМЕТКА свежести — валидатор `ETag`/`Last-Modified`, время изменения файла против даты записи-источника. Отметка мерит ровно СВОЙ источник: вход содержимого, лежащий вне этого источника, её не двигает — копия годна по отметке и врёт содержимым. Мимо отметки, построенной на ДАННЫХ источника, идут ФОРМАТ сериализации и ВНЕШНЕЕ состояние, от которого зависит записываемое значение.
Перед записью значения в производный артефакт — назвать источник ЭТОЙ отметки и все входы значения. Вход вне источника → значение не класть вовсе, вычислять в момент выдачи; либо втянуть вход в саму отметку. Стабильность значения относительно СВОЕГО источника от протухания не спасает: пересчёт при синхронизации («Единый источник истины» ниже) запускает отметка, а такой вход её не двигает.
Изменяемый состав полей либо формат сериализации держать на отпечатке — метка версии схемы плюс данные. Голая дата (дата записи-источника, время изменения файла) метки не несёт: обесценить ею прежние копии нечем.
Правя формат — снять существующие копии ТЕМ ЖЕ проходом, не «потом»: свои файлы снести, пересоберутся из источника лениво. Отметка лежит ОТДЕЛЬНО от копии (реестр, манифест, поле записи) → снос копии снимает и её запись в отметке. Запись осталась — следующая сверка считает снесённое свежим, копия не пересоберётся никогда.
Копию у чужого потребителя снимает лишь СДВИГ отметки, которую он сверяет. Пересборка двигает её, только когда отметка = момент сборки файла; приколоченная к дате данных не двигается — версия формата тогда идёт в саму отметку либо в адрес.
Формат разбирает ЧУЖАЯ сторона своим кодом — метку версии формата держит ОНА, отдающему остаётся отметка по своим данным. Момент смены структур разбора знает только разбирающий; метка формата на отдающей стороне — второй параллельный механизм поверх чужого. В проекте разбирающая сторона — клиент игры: бамп метки вносить в его коде, правило её ведения — канон клиента (указатель — skill `unity`).
Дефект молчит: источник отвечает корректно, врёт копия у потребителя, ни линт, ни тест, ни лог его не ловят. У автора правки не воспроизводится — своей копии нет либо снёс её по ходу работы; бьёт по чужим копиям после выкладки.
Ось отдельна от бампа метки-триггера при мутации данных (skill `orm-access`): там вход в источник отметки ВХОДИТ, до отметки не доехала сама правка; тут вход источником отметки не покрыт.
Триггер срыва: часть ответа уехала на отдельный роут, данные не менялись — отпечаток прежний, клиент получил 304 на копию прежней формы; правка сериализации кеш-файла его время изменения не двинула — потребитель разобрал старую форму из кеша, годного по отметке; в кеш положили значение, зависящее от состояния вне источника его отметки, — состояние изменили, отметка не двинулась, потребитель молча разобрал устаревшую копию; метку версии формата, разбираемого чужим клиентом, завёл на отдающей стороне — клиент снёс битую копию, запись её отметки оставил и данных больше не запрашивал.

## Ожидание чужого времени в сборке ответа

Вызов, ждущий сторону, чьё время НАМ НЕ ПОДКОНТРОЛЬНО, — поход по сети к чужому серверу, запуск чужого процесса, обращение к стороннему сервису, — в сборку ответа, которого ждёт его получатель, не ставить, когда он КРАТЕН числу записей выдачи. Три признака нужны ВМЕСТЕ:

- ЧЬЁ ВРЕМЯ ждём. Ось — время, не граница, за которую уходит вызов: обращение к соседнему модулю и запрос фронта к своему же бэку читаются «внешними», правилом не покрыты — тот же процесс либо та же машина, время предсказуемо; ЧИСЛО запросов к своей базе, кратное числу записей выдачи, держит skill `orm-access`
- КРАТНОСТЬ числу записей выдачи — вызов на строку списка. Одиночный такой вызов на странице одной записи не запрещён
- МЕСТО — внутри формирования ответа. Ответ ушёл получателю → тот же вызов законен, и в нём ЛЕЧЕНИЕ: запрещена сборка ответа, не показ значения вообще

Ограничитель (не больше N вызовов на запрос, порог свежести у записи) решением не является: ответ несёт N ожиданий подряд, а выдача остаётся неактуальной — обновлены N записей из показанных. Записей больше, чем успевает опросить один запрос → просроченные находятся всегда, и оба дефекта держатся разом.

Свежесть ведёт канал МИМО сборки ответа: до-опрос из браузера после отрисовки по показанным записям плюс обход по расписанию. Сборка ответа читает только сохранённую отметку.

Соседи по иным осям: «Место правки на маршруте данных» выше — выбор ЗВЕНА среди проходов, уже идущих по тем же данным, тут работа выносится за пределы ответа вовсе; «Свежесть производного артефакта» выше — годность сохранённого значения по его отметке, тут — чем и когда отметка обновляется.
Триггер срыва: геттер признака «есть обновление» ходил по сети за состоянием чужого репозитория, ≈0,9 с на запись; ограничитель в 3 опроса на запрос при 134 записях и пороге свежести 10 минут держал страницу списка на ≈3 с при 9 запросах к базе на 11 мс, а свежими из двух десятков показанных строк становились 3; перенос опроса за отдачу ответа дал 176 мс.

## Анализ и рефакторинг

- Вердикт статического анализа — «условие всегда истинно/ложно», «проверка избыточна», «ветка недостижима», «типа/метода не существует» — гипотеза его модели, не факт: модель собирается по объявлениям и отслеживаемым присваиваниям, состояний рантайма она не знает. Рабочий код под вердикт не править: снимать проверку либо сужать объявление — только назвав, на чём вердикт держится, и исключив живой случай. Образцы живой ветки по причине промаха модели (список открытый): объявление не описывает состояние — проверка закрывает окно до инициализации, где прямое чтение падает; присваивание не отслеживается — проверка элемента, который тот же проход пишет по ВЫЧИСЛЯЕМОМУ индексу, держит уже назначенное от затирания; значение переключателя меняется вне прогона анализа — ветка за константой, выключенной по умолчанию и включаемой вручную (отладочная отрисовка, диагностический режим). Разобрался → исход один из двух: проверка лишняя → снять; проверка живая, неверна МОДЕЛЬ анализа → код оставить как есть, гасить сообщение. Подгонка кода под модель запрещена: сужение объявления под то, чего рантайм не делает, врёт каждому потребителю объявления. Канал гашения есть не у всякого анализатора: где база заглушённых ошибок ведётся в его конфиге — ложное заносится туда, где канала нет — сообщение остаётся, его игнорируют. Общая планка «вывод инструмента врёт наравне с трактовкой» — core «Локатор ≠ доказательство». Триггер срыва: снял «избыточную» проверку по вердикту анализа, не назвав его причины, — защита исчезла, дефект всплыл на живом канале
- Кандидат на мёртвый/избыточный код, возникший по ходу работы (метод, обработчик события, ветка, ставший ненужным после рефактора или переноса логики) — не помечать «безвреден, оставим»: обойти ВСЕ его потребители и пути вызова (core «Полнота охвата и проверки»), подтвердилось лишним → удалить САМ, автономно, без запроса разрешения. Автономность держит ВОССТАНОВИМОСТЬ удаляемого, и она отдельная проверка ПЕРЕД сносом, не следствие подтверждённой мёртвости: восстановимо то, что лежит в истории либо в индексе — файл отдаёт `git ls-files --error-unmatch <путь>`, удаляемый блок внутри файла — `git show HEAD:<путь>` либо `git show :<путь>`. Неотслеживаемый файл (`??` в `git status` — работа прошлой сессии без коммита), носитель под игнором git и код вне репозитория стираются НЕВОЗВРАТНО: их снос идёт гейтом-через-подтверждение наравне с прочим необратимым по данным (CLAUDE.md, граница послабления локального контура). Признак промаха, ловимый самим автором: мёртвость подтверждена обходом потребителей, а отслеживаемость удаляемого не спрошена ни разу. Ось соседа: core «Рабочее состояние репозитория — пользователя» запрещает git-операции, снимающие состояние рабочего дерева и индекса ЦЕЛИКОМ, тут удаляется названный носитель и решает восстановимость его содержимого. Тем же проходом править устаревшие комментарии-ссылки на удалённое, иначе висячая ссылка. Не накапливать мусор. Триггер срыва: подтвердил мёртвость двух файлов обходом потребителей и снёс их автономно по этому правилу — файлы были неотслеживаемыми, работой прошлых сессий без коммита: `git show HEAD:<путь>` отвечает «path does not exist», восстановить нечем
- Видимость члена выбирает его ФАКТИЧЕСКИЙ потребитель, и выбирается она при написании: зовут только изнутри класса → закрытый, только наследники → защищённый; открытость по умолчанию, без названного вызывающего снаружи, — промах. Видимость шире потребителя гасит автоматический контроль неиспользуемости: закрытый член анализ сторожит по умолчанию, открытому нужна отдельная настройка, без которой мёртвый метод живёт в коде, пока его не заметит человек. Открытый член без вызывающих вне класса → сузить видимость либо инлайнить при единственном вызове («Дедупликация»). Видимость задана контрактом надкласса либо интерфейса → решать в контракте: реализация с суженной видимостью его не удовлетворяет
- Tolerance/fallback под легаси-формат СОБСТВЕННЫХ данных, перечислимых и обновляемых → мигрировать данные к текущему формату и удалить ветку, не держать совместимость бессрочно. Перед удалением ветки — мигрировать легаси-данные ИЛИ убедиться, что их нет. Удаление без миграции = тихая потеря данных на следующем чтении. Зеркало преждевременной абстракции («Дедупликация»): fallback под формат, которого в реальных данных не было, не добавлять. Граница: формат, намеренно живущий ПАРАЛЛЕЛЬНО основному, — не легаси, tolerance оставить. СМЕНА собственного формата (расширение, имя артефакта) → ветку back-compat не заводить вовсе, канон один с первого коммита: легаси-источники снимает та же разовая миграция (core «Root-fix у источника»). Отсрочка «пока старые данные не обновятся» — не переходное решение, а отложенный долг. Предмет буллета шире ФОРМАТА: любое прежнее СОСТОЯНИЕ собственных данных, которое новый guard делает недостижимым, закрывается тем же порядком — формат при этом не менялся вовсе, и по слову «формат» правило к случаю не примеряется. Проверка, оставленная «для данных, легших до guard'а», — тот же tolerance: снимать её тем же проходом, что заводит guard. Триггер срыва: перенеся проверку инварианта в точку записи, оставил прежнюю на выгрузке бэкстопом под старые данные; пользователь: «мы не должны закладывать в код заплатки на заведомо не достижимых более проблем (которые стали недостижимы) и если проблема что какие-то старые данные могут их вызывать - решение перезаливать данные, а не плодить код-заплатки»
- Правка, обязанная сохранить поведение (сведение копий, вынос общего, перенос кода), чей вклад доходит до БАЙТОВ выпускаемого наружу документа (файл выгрузки, экспорт, отдаваемый потребителю ответ), принимается сверкой ОТПЕЧАТКА документа до и после правки. Чтение кода приёмкой тут не служит: перенос молча меняет порядок полей, отступы, экранирование, условие пропуска пустого — расхождения не ловят ни компилятор, ни тесты, падает потребитель документа позже и в другом месте. Эталон снимается ДО правки; снятый после требует поднять прежний код из истории (`core` «Рабочее состояние репозитория — пользователя»: прежнее содержимое берут во временную копию вне рабочего дерева). Входы под прогон подбирают так, чтобы каждый сведённый экземпляр исполнился хоть раз: сведённое, не исполнявшееся ни в одном прогоне, приёмкой не проверено. Оси соседей: `core` «Верификация артефактом» — общее правило приёмки своим артефактом, тут артефактом служит отпечаток документа у правки, чей ожидаемый исход «ничего не изменилось»; «Единый источник истины» ниже — ОХВАТ выноса, все ли копии подключены к канону, тут приёмка уже внесённого.

## Единый источник истины

Повторяющийся литерал/значение/конфиг/логика — не копировать: один источник (класс констант, enum, конфиг бандла-владельца, общий сервис/база/трейт). Ссылаться по имени (`Enum::Case->value`), не строкой. Копия устаревает молча — источник уехал, копия соврала. PHP-механика выноса кода (proxy/inline/extract, операция из двух фронтов) — skill `php` «Дедупликация»; перечни enum/числа/имена в skill и доке — skill `skill-rules` / `doc`.

Денормализованная проекция значения (кэш ради фильтра/листинга/скорости) — легитимна by-design, НЕ запрещённая копия абзаца выше, но верна лишь ПЕРЕ-ВЫЧИСЛЯЕМОЙ из источника при каждой синхронизации/импорте, не статичной копией в промежуточном носителе (манифест, экспорт-файл, соседняя запись). Носитель проекции выбирать по ИЗМЕНЧИВОСТИ источника — тест перед выбором: переживёт ли значение изменение источника? Стабильная мета (при пере-загрузке источника не меняется) вмораживание переживает; изменчивый производный признак (меняется при пере-загрузке/пересборке источника) во вмороженном носителе соврёт после изменения источника → пересчитывать при sync из актуального источника, не вмораживать. Механизм срыва — перенос формы прецедента без её обоснования: частный случай `core` «Копирование прецедента». Триггер срыва: денормализовал изменчивое значение статичной копией в манифест/файл по образцу стабильной меты, при изменении источника копия соврала; пользователь — «значение же пере-считается при синхронизации, зачем вмораживать». Ось ДОЛГОВЕЧНОСТИ носителя — тот же выбор, предмет её шире проекции: любое производное либо вспомогательное состояние объекта. Долговечность мерится сроком жизни объекта-хозяина, не соображением «надёжнее сохранить». Тест перед выбором: назвать событие, при котором носитель теряет состояние, и спросить, переживает ли это событие сам хозяин. Не переживает, и без хозяина состояние бессмысленно → потеря состояния при этом событии — норма, более долговечного носителя не заводить. Триггер срыва: собрался хранить очередь ожидающих в данных, переживающих перезагрузку, обосновав это тем, что рантайм-буфер перезагрузку не переживёт; пользователь: «при перезагрузке карты и монстры оживут, тела нет — сброс очереди тут норма, а не то, что надо тащить в базу; почему ты не додумываешь эту логику».

РАЗМЕЩЕНИЕ проекции — второй выбор рядом с пере-вычисляемостью: свойство едет потребителю каналом СВОЕГО носителя, не справочником обо ВСЕХ элементах его класса внутри ЧУЖОЙ сущности. Копий такого справочника становится столько, сколько чужих сущностей его везут, а свойство доходит лишь туда, где такая сущность оказалась рядом, — хотя нужно оно везде, где виден сам носитель. Тест перед выбором: чьё это свойство — у его носителя есть свой канал доставки → расширять этот канал. Довод «канал носителя такого значения не возит» — не потолок, а сама задача: расширение канала дешевле параллельной доставки. Соседняя ось у `core` «Root-fix у источника»: там запрет на вторую эмиссию поверх канала, уже возящего данные в тот же слой, тут выбор — ЧЕЙ канал везёт значение. Триггер срыва: базовую цену предмета, лежащую компонентом у самого предмета, повёз клиенту справочник всех цен внутри компонента торговца; пользователь: «мы же обсудили что цена у предмета будет а ты всеравно в торговца зашил» — цена нужна и в инвентаре, где торговца нет вовсе. Довод об ЭКОНОМИИ, на котором держится такой выбор (значение у каждого элемента против одной записи-умолчания), строится по ВСЕМ точкам, где значение фактически материализуется, и точки перечисляются ДО вердикта. Открытая первой точка — обычно не единственная, и прочие ей не подобны: запись справочника несёт значение однажды, а порождённый из неё экземпляр рантайма получает копию при создании и увозит её соседнему процессу. Перечень точек по носителю держит `core` «Полнота охвата и проверки» (каналы наполнения), замер по каждой сравниваемой стороне — `core` «Вердикт и обоснование критерия»: полнота этого перечня и есть предмет замера. Триггер срыва: предложение перенести справочное свойство из значения, заданного каждой записи справочника, в умолчание, которое в экземплярах не оседает, отверг доводом «экономии нет, значение повторится столько же раз» — сосчитал копии в самом справочнике, копии в каждой создаваемой сущности и их отправку соседним процессам не сосчитал вовсе; пользователь: «как нет экономии — если заложить default, он не будет слаться и идти на каждом существе, забивая память, как сейчас… проверь», проверка кода подтвердила его довод целиком.

ПОДГОТОВЛЕННЫЙ СРЕЗ данных — тот же предмет правила, что значение: копией тут идёт не значение, а ПРАВИЛО его подготовки. Срез отдаётся потребителям производным артефактом (файловый кеш, экспорт, снимок), который собирается МОДИФИКАТОРАМИ — контекст сборки снимает, добавляет либо гасит часть полей. Потребитель ТОГО ЖЕ среза (страница, провайдер, сервис) читает этот артефакт, не первоисточник: первоисточник отдаёт СЫРОЕ состояние, и, чтобы показать то же, что видят прочие потребители, читающий обязан повторить у себя каждый модификатор сборки — копия правила молча расходится со сборкой, два фронта на одних данных показывают разное. Запись и правка идут в ПЕРВОИСТОЧНИК, из артефакта только читают; сам сборщик и код, вычисляющий модификатор, работают с первоисточником by-design. Нужного поля в артефакте нет → ДОПОЛНИТЬ сборку этим полем, не брать его из первоисточника в обход: мимо сборки идут и модификаторы поля. Ось — ВЫБОР канала чтения: эмиссия данных В канал — `core` «Root-fix у источника», годность уже взятой копии по отметке свежести — «Свежесть производного артефакта» выше, движение отметки при мутации — skill `orm-access`. Триггер срыва: два фронта показа собирали данные обходом сущностей и показывали разметку, которую сборка артефакта снимает, — в игре она не исполняется; пользователь: «я прошу данные для неё брать из кеша, который мы подготавливаем для работы наружу, а ты в базу продолжаешь стучаться».

Существующая ручная копия/дубль (в коде-прецеденте, во фреймворке-источнике) — НЕ довод сохранить дублирование, когда появляется или возможен общий источник (новый параметр метода, выносящий повторяемую обёртку): «уже так сделано» — защита статус-кво (подмена ought→is, `core` «Заземление перед суждением»). Вынести в источник и переписать ВСЕ копии разом, включая прецедент-образец. Триггер срыва: на предложение выноса сослался на существующую ручную обёртку/обход как «так уже во фреймворке/у соседа» вместо включения её в рефактор; пользователь: «есть что улучшает код — аргумент «уже так сделано» невалиден».

ЗАВЕДЕНИЕ общего носителя — вынос базы, трейта, общего сервиса, общей функции — самостоятельная точка обхода: носители выносимого механизма ищутся по ВСЕМУ проекту в момент выноса, довода «уже так сделано» и дефекта для этого не требуется. Границу множества задаёт сам МЕХАНИЗМ — что выносимый код физически делает: собирает то же значение, разбирает ту же форму ответа, ведёт то же преобразование. Сходство имени, каталога и бандла её не задаёт: носитель того же механизма лежит в чужом бандле под именем, к имени заводимой базы не близким, и ни грепом по именам копий, ни обходом соседних файлов не находится. Искать по составным частям механизма — по значению-константе, литералу, вызову, из которых выносимый код собран.
Носитель, написанный ТЕМ ЖЕ заходом, что и база, обходом не покрыт: в перечень копий, с которых вынос начинали, он не входил. Новый код, повторяющий механизм заведённой базы, подключается к ней, а не пишется рядом.
Копия, к базе не подключённая, застывает на поведении ДО выноса: канон дорастает тем, ради чего вынос и делался (поднятая причина отказа, проверка, единица), копия этого не получает — снятый в каноне дефект живёт в ней дальше.
Признак промаха, ловимый самим автором: перечень переписанных копий совпадает с тем, с которого вынос начинали, а поиск по механизму не проводился ни разу.
Оси соседей: абзац выше — ДОВОД против выноса, тут вынос уже идёт; `core` «Многофайловая правка» задаёт то же множество по механизму при ПОЧИНКЕ дефекта, тут точка — заведение носителя, чинить нечего; «Дедупликация» ниже — момент появления ВТОРОЙ копии, тут копии уже собраны в источник.
Триггер срыва: общий транспорт до демона узла (сборка адреса его API плюс разбор протокольной обёртки ответа) вынесли в базу по двум клиентам, с которых начали; третий носитель сборки адреса лежал в другом бандле под именем службы проверки синтаксиса, четвёртый писался тем же заходом рядом с базой и её не наследовал — его разбор ответа терял присланную узлом причину отказа и отдавал администратору один лишь адрес, ровно тот дефект, ради снятия которого в базе и написан разбор обёртки.

Состояние рантайма — тот же предмет правила, что значение: заводя поле-флаг под состояние, сперва проверить, не выражено ли оно уже НАБЛЮДАЕМЫМ свойством самого объекта (активность/видимость элемента, режим, статус) либо ЗНАЧЕНИЕМ-источником (настройка, поле сущности, ответ сервера). Выражено → читать его, второй носитель не заводить. Два носителя одного состояния расходятся молча — компилятор и тесты копию не ловят. Вопрос «чем эти два отличаются и зачем оба» — признак дубля, не запрос уточнить имена. Второй флаг законен, лишь когда несёт ДРУГОЕ независимое состояние: тест — назвать вход, при котором носители ОБЯЗАНЫ разойтись; не называется → носитель один. Мелкость формы (локальное поле класса против отдельного механизма/структуры `core` «Root-fix у источника») распознаванию не мешает — параллельный носитель тот же. Триггер срыва: под настройку игрока завёл второй флаг рядом с существующим, хотя состояние уже несла активность самой UI-панели, а источник — значение настройки; пользователь: «чем они отличаются и зачем оба».

КОНТРОЛ интерфейса (галочка, кнопка, переключатель) — тот же предмет правила, что значение: понятие тут — ДЕЙСТВИЕ пользователя, одно действие несёт один контрол. Заводя контрол, сперва искать существующий контрол того же действия по ВСЕМУ рендеру страницы (соседняя панель, вкладка, колонка списка, базовый шаблон), не по правимому файлу; нашёл → расширять его, второй не ставить. Различие СЕМАНТИКИ эффектов (временный показ против постоянной записи, мгновенный против применяемого по кнопке, свой сеанс против общих данных) — довод за разное ПОВЕДЕНИЕ одного контрола, эффекты складываются на нём; второго контрола оно не оправдывает. Тест «назвать вход, при котором носители ОБЯЗАНЫ разойтись» (абзац выше) меряет ось СОСТОЯНИЙ и на разных состояниях законно даёт зелёный — числа контролов он не проверяет, санкцией на второй не является. Два контрола одного действия расходятся молча, и сочетание их состояний делает исход действия неопределённым. Триггер срыва: под временный показ слоёв на превью завёл вторую вкладку со своими галочками, хотя тем же действием управляла колонка-галочка уже существующей вкладки; пользователь: «зачем ты сделал новую вкладку слои, если слева была вкладка слои и там была колонка видимый».

ИМЯ ключа в структуре-возврате (ответ сервиса, форма массива, поле контракта на несколько фронтов) — предмет того же правила, что значение: понятие называет ИСТОЧНИК одним именем, тем, которое читают ВСЕ потребители. Переименование ключей у потребителя (провайдер, контроллер, шаблон, клиентский код) заводит второй словарь того же понятия — расходится с первым молча, ни компилятор, ни линт, ни тесты его не ловят, фронты начинают звать одно поле по-разному. Детектор — перекладка ключей источника один-в-один при сборке своего ответа. Лечить переименованием в ИСТОЧНИКЕ со снятием перекладки, не вторым набором имён. Тут ось ВЫБОРА имени. Последствия ПРАВКИ формы (снятый либо переименованный ключ — обход всех потребителей, пропажа ключа всплывает runtime-warning) — skill `php` «Типы», буллет о shape ассоциативного массива-возврата. ВЫБОР контейнера и ключа-идентичности (словарь против позиционного списка) — «Типы» выше. Триггер срыва: потребитель отдавал наружу собственные имена поверх ключей источника — одно понятие звалось у разных фронтов по-разному, а внутри одного вывода несло два имени; ничего не упало, расхождение всплыло лишь на сверке.

## Дедупликация

Порядок решения общий для раздела: сперва СЛОЙ — чем логика является и куда принадлежит, — и лишь внутри разрешённого слоя меряется ФОРМА (порог метода, порог класса, инлайн единственного вызова, обёртка). Обратный порядок формально исполняет правило формы и ломает слой. Приёмником инлайна либо схлопывания служит потребитель, чей слой такую логику принимает: слой, состав кода которого ограничен правилом проекта (`php` «Дедупликация», skill `entity`), приёмником не бывает — единица остаётся своим слоем. Признак промаха, ловимый самим автором: потребитель назван, а принимает ли его слой эту логику, не спрашивалось.

- Перед созданием класса, перечисления либо метода — проверить существующие на совместимость (аргументы, домен): совместимо → расширить существующий, в том числе его сигнатуру; несовместимо → своя единица
- Методы с почти одинаковым телом → один метод, различие — аргументом. Различие, сведённое к одному значению либо наличию/отсутствию одного элемента результата (ключ в возвращаемой структуре) и заданное типом либо перечислением, → ветка внутри метода, не выносить в переопределение, отдельный метод либо класс: одно значение отдельной единицы не требует. Различаются ТЕЛА веток, не одно значение → переопределение законно (делать осознанно — «Переопределение с вкладом родителя» выше). Малое различие, всплывшее в уже схлопнутом методе, → ДОБАВИТЬ ветку, не разъединять обратно — преждевременная абстракция
- Дедуп НЕ откладывается «на потом» под давлением доставки: 2-й почти-идентичный метод — точка НЕМЕДЛЕННОГО схлопывания, не «накопится N копий — тогда» и не «в ревью словят». Ярлык «тривиальная обёртка / glue / мелко / задедуплю позже» копию НЕ оправдывает: тривиальность задаёт ФОРМУ дедупа (инлайн у вызывающего — правило единственного вызова ниже), не право отложить; почти-идентичные тела → один метод (правило выше). Решение — прямо сейчас; N почти-идентичных методов-обёрток даже тривиальных — тот же дубль. Триггер срыва: оставил 2-ю копию почти-идентичного метода под «тривиально/потом», дубль указал пользователь либо ревьюер — промах при живом правиле есть сигнал слабого ТРИГГЕРА, не отсутствия правила
- Метод с единственным вызовом — инлайнить, даже если «красиво выделен». Отдельный метод оправдан только при >15 строк со своей ветвистой логикой ИЛИ если вызывается из ≥2 мест ИЛИ рекурсивный. Цепочки крупных одноразовых методов (A→B→C) — тоже инлайнить
- Гард/предусловие без возвращаемого значения (валидирует и бросает, вызывающему ничего не отдаёт) — инлайнить в защищаемую операцию ДАЖЕ при >15 ветвистых строк: допуск «>15 ветвистых строк → метод» только для значение-возвращающих под-билдеров (`build*`/`compute*` → данные, что вызывающий вставляет в результат; имя документирует фрагмент вывода). Гард — интринсивное предусловие одного вызывающего, не переиспользуемая единица: имя прячет гейт за индирекцией, держать видимым в начале операции; отдельным методом оправдан лишь при ≥2 вызывающих. Различитель — не «проверка ли это», а возвращает ли потребляемое значение: предикат `isX`, по которому вызывающий ветвится, — значение-метод (правило не про него); `assertX`, который бросает, — гард
- Порог отдельного КЛАССА в своём файле выше порога отдельного метода: допуск «>15 ветвистых строк → метод» относится к методу внутри уже существующего класса, заведения нового носителя он не оправдывает. Класс, чей публичный интерфейс зовут из ОДНОГО файла-потребителя, схлопывается в этого потребителя методом. Оставляют класс по НАЗВАННОМУ основанию: ≥2 потребителя; точка расширения по конвенции слоя, ЗАПИСАННОЙ правилом проекта; граница между процессами либо раздельно развёртываемыми модулями. Основания нет — метод у потребителя; вынос ради единообразия решает пользователь (`orchestration`). Признак промаха, ловимый самим автором: санкция взята по правилу о МЕТОДЕ, а заведён файл с классом. Триггер срыва: сборка спецификаций наложения для кадра ушла в отдельный сервис с единственным публичным методом — ветвистым и длиннее пятнадцати строк, — а звал его один соседний сервис; пользователь: «а почему ты в другом сервисе насоздавал сервисы что вызыаются тока в другом сервисе», «ты выбирал инлайнить или вынести и решил вынести но почему то аж в отдельный фаил хотя метод используется в 1 месте»
- Прокси/обёртку не плодить — звать целевой напрямую. Классифицировать по ТЕЛУ (факт «реализует интерфейс» в классификации не участвует): чистый форвард без своей логики → прокси, адресат форварда — другой метод ЛИБО источник значения (переменная окружения, константа, конфиг); своя нетривиальная логика (проверки, бросок, null-fallback, «своё значение либо родительское», запрос к хранилищу, содержательное преобразование данных — разбор строки в структуру, пересчёт величины, сборка из нескольких источников) → не прокси. Приведение типа своей логикой НЕ является: каст приводит форму значения к объявленному типу, самого значения не меняет — форвард с кастом остаётся прокси. Формы: **метод-прокси**, лишь зовущий другой метод (в том числе геттер-делегат `getXY()`, чьё тело возвращает `getY()` у объекта, отдаваемого `getX()`) → звать `getX().getY()` в точках вызова; **геттер над источником значения**, чьё тело — чтение переменной окружения, константы либо конфига → читать источник в точке использования; **класс-прокси** (фасад), единственный метод которого форвардит во внедрённую зависимость → внедрять целевую во все точки вызова; **тонкий подкласс**, единственный метод которого лишь публикует наружу то, что внутри могло быть закрытым либо инлайном (флип видимости) → собирать значение у вызывающего через родительский метод. Прокси оправдан только своей нетривиальной логикой; развязка через интерфейс-порт (потребитель зависит от интерфейса, не от реализации) прокси не является — её механика для бандлов в skill `php`. Триггер срыва: тело геттера — каст прочитанной настройки, признак «преобразование данных» вывел его из прокси; обёртку нашёл пользователь
- Прокси/обёртку не оправдывают: ни «≥2 точек вызова», ни «симметрия с соседним сервисом» (соседний оправдан СВОЕЙ логикой, пустая обёртка симметрию не наследует), ни модификатор доступа. Модификатор — граница против ВНЕШНЕГО потребителя (опубликованный API, чужой непра́вимый код); нужен доступ изнутри своего модуля — звать целевой напрямую либо расширить видимость самого целевого, обёртку не заводить. Граница между процессами либо раздельно развёртываемыми модулями — настоящая, под это не подпадает. Ось тут — существование обёртки; ВЫБОР видимости члена держит «Анализ и рефакторинг»
- «Не прокси» (своя логика по телу) и «единственный вызов / единственный потребитель» — ОРТОГОНАЛЬНЫЕ оси, прогонять ОБА теста. Юнит с оркестрацией, проверками и броском проходит proxy-тест и всё равно подлежит инлайну, если вызывается из одного места. Остановка анализа на «не прокси» — типовой срыв
- Тест на прокси и инлайн применять к форме ПОСЛЕ безопасного behavior-preserving изменения, не к текущей. Юнит, становящийся прокси или одноразовым инлайн-кандидатом после правки, не ломающей и не раскрывающей лишнего ВНЕШНЕМУ потребителю, — УЖЕ таков. Типовые трансформы: расширить видимость — безопасность по оси поведения и инкапсуляции, вторая ось — компилируемость переопределяющих наследников, пройти по ним как при правке контракта; перенести тривиальную композицию к вызывающему; вынести тело в единый источник — метод стал чистым форвардом → инлайнить в точки вызова ТЕМ ЖЕ проходом, делегат не оставлять. Срыв: формулу вынес в общий сервис, старый метод оставил форвардом, точки вызова не переключил
- Перенос кода — схлопывание класса в потребителя, вынос в общий носитель, переезд между слоями и бандлами, разделение файла — есть НАПИСАНИЕ каждой перенесённой единицы заново, не транспортировка готового. На новом месте у КАЖДОЙ единицы (метод, класс, параметр, ветка) заново называется основание существовать: число вызывающих ТАМ, порог объёма и ветвистости, слой. Основания нет — единица схлопывается тем же проходом, а не переезжает как есть: форма унаследована от прежнего места, где порог мерился по прежнему окружению, и на новом им не оправдана. Поведение правило не трогает — пересматривается ФОРМА, контракт остаётся прежним. Механизм промаха: у переноса есть СВОЯ цель — новый адрес, схлопывание, — и её достижение проверяется само собой (поведение сошлось, страница жива), а форма переезжающих единиц не оценивается ни разу, потому что заново её никто не пишет. Признак промаха, ловимый самим автором: на новом месте лежит единица, которую я бы там не завёл, пиши я это место с нуля. Оси соседей: буллеты выше держат САМ порог — метода, класса, прокси-обёртки, — тут ТОЧКА, где пороги применяются заново; буллет о тесте после behavior-preserving трансформа — преобразование там ГИПОТЕТИЧЕСКОЕ, тут фактически совершаемое; `core` «Копирование прецедента» — чекпоинт в момент репликации ЧУЖОГО образца, тут единица своя и уже существующая; `core` «Многофайловая правка», абзац о коде по новому адресу — там по новому адресу рвётся покрытие сводов и спек глобами `paths`, тут предмет — форма самого кода; `core` «Профильный skill перед действием в домене» — обязанность сверять структурное решение с правилами, тут её применение к порогам. Триггер срыва: класс с единственным файлом-потребителем схлопнули в потребителя, семь приватных методов сборки данных страницы перенесли дословно — четыре из них (8–13 строк, по одному вызывающему, ветками одной развилки не являются) остались отдельными единицами и были инлайнены лишь после замечания пользователя: «а почему этот метод отдельно если используется тока в другом методе тут же», «и один раз», «и не является развилочным»
- Абстрактный/родительский класс с ЕДИНСТВЕННЫМ подклассом — красный флаг преждевременной абстракции. Закрытое тело, извлечённое в родителя и зовущееся из одного подкласса, схлопывать в этот подкласс (инлайн тела и удаление базы), пока второй подкласс не появился реально. Комментарий-обещание второго потребителя («общее тело для X/Y» при отсутствующем Y) второй подкласс не заменяет — частный случай запрещённого «возможного будущего потребителя», применённый к иерархии. Граница: правило не применяется там, где цепочка наследования — ЗАЯВЛЕННАЯ конвенция слоя, ЗАПИСАННАЯ правилом проекта (звено цепочки есть точка расширения, единственный подкласс у звена нормален by-design). Конвенция — записанное правило носителя, не наблюдаемая практика: «у соседей так же», «наследник пока один» и удобство её не образуют; конвенции нет → правило в силе

### Ветки одной развилки — одной формой

Ветки развилки РАВНОПРАВНЫ, когда каждая доводит операцию до её штатного исхода: ни одна не есть отказ, ранний возврат либо частный случай. Равноправные ветки оформляются ОДНОЙ формой — каждая своей именованной единицей либо все инлайн ветками одного условного оператора. Метод с развилкой собственного тела ветки после неё не несёт: ему остаются преамбула и выбор ветки.
Порог отдельной единицы (буллеты выше) мерится по КАЖДОЙ ветке, не по той, которую правишь: прошли обе — выносятся обе; не прошла ни одна — инлайн обе. Прошла одна → вынос соседней держится на единообразии, жёсткими критериями извлечения не оправдан, решает его пользователь (`orchestration`).
Механизм промаха: вторую ветку заводят к УЖЕ написанному телу — её пишут отдельной единицей, а первая остаётся телом метода, и порог к ней не примеряется ни разу.
Форма кода читается иерархией: вынесенное под именем — вспомогательное либо частный случай, оставшееся телом — основной ход; у равноправных веток сигнал ложен.
Признак промаха, ловимый самим автором: у одной ветки развилки есть своё имя, у соседней имени нет вовсе; либо метод с развилкой продолжается после неё телом одной из веток.
Оси соседей: буллеты выше — ПОРОГ отдельной единицы, заводить ли её вообще, тут исход порога общий у веток одной развилки; `orchestration` — развилка «метод либо инлайн» при невыполненных критериях извлечения.
Триггер срыва: приём нового формата ассета уехал в отдельный метод со своей транзакцией и своими ветками, прежний формат остался телом метода-развилки с телом того же объёма — порог отдельной единицы проходили оба, применён был к одному; комментарий над развилкой называл вынесенный формат действующим, а оставшийся в теле — легаси, и форма кода сообщала обратную приоритетность.

### Дополнение под одного потребителя

Единица нужна многим и остаётся; предмет правила — её ДОПОЛНЕНИЕ (параметр, ветка, поле, режим), заведённое ради ОДНОГО потребителя. Знать о дополнении обязаны ВСЕ: передавать значение, держать умолчание, разбирать ветку.
Перед добавлением назвать исход ОТКАЗА от дополнения — чем потребитель обходится БЕЗ него. Обходится общим значением либо своими средствами → не заводить: отказ меняет ЧАСТНОСТЬ (формулировку надписи, оттенок поведения), а не механику, нужное одному потребителю решать у него самого. Остаётся лишь СВОЯ копия единицы (разметки, тела, значения) → дополнение законно.
Цену меряет число мест, обязанных о дополнении знать, не размер самого дополнения. Копия единицы дороже этой цены.
Существующее — под тем же правилом: единственный потребитель дополнения ушёл → снять дополнение тем же проходом.
Соседи по иным осям: буллеты выше выражают аргументом различие ДВУХ уже существующих тел — тут второго тела нет, вопрос в том, заводить ли различие вовсе; `core` «Root-fix у источника» — параметр-флаг, разводящий потребителей склеенного критерия, лечится расщеплением критерия в источнике; «Боевой потребитель новой возможности» выше — возможность, у которой боевого потребителя нет ни одного; `core` «Команда об одном потребителе, носитель общий» — тут вердикт агента о форме единицы, там охват изменения, решаемый пользователем окном.
Триггер срыва: в общем методе завёл параметр под единственный вызов — десятки прочих мест вызова обязаны о нём знать, а без параметра потребитель обошёлся бы общей надписью.

### Ось понятия и вывод из неё

Несколько признаков, всегда выводимых друг из друга и заполняемых в одном месте, — одно понятие, разложенное на флаги. Свести к ОДНОЙ оси с закрытым перечнем значений; заполняет её точка, где известны исходные факты. Детектор разложения — тест на обязанность носителей разойтись («Единый источник истины» выше), прогнанный по набору ПОПАРНО: входа для пары не называется → признаки пары лежат на одной оси.

Вывод из оси принадлежит ОБЩЕМУ носителю — тому, что рисует, — не вызывающим. Стиль, доступные действия, подписи, тексты подтверждений, попадание под фильтры и счётчики (список открытый) он выводит сам, приняв одно значение оси. Вызывающему остаётся то, что осью не выражается.

Соседи по иным осям: «Единый источник истины» выше — ДВА носителя ОДНОГО состояния, тут N признаков, порознь осмысленных, вместе составляющих одно понятие; `core` «Root-fix у источника» — обратная операция, склейка двух независимых свойств в один критерий, лечится расщеплением в источнике; «Дополнение под одного потребителя» выше — дополнение общего носителя ради ОДНОГО потребителя, тут вычисление, повторяемое ВСЕМИ; `twig` «Страница-деталь сущности» — ось СЛОЯ (шаблон против контроллера), тут ось НОСИТЕЛЯ (общий против каждого вызывающего).
Триггер срыва: одно понятие несли набор булевых полей в данных и вычисление в шаблоне; вызывающие общего носителя вывода передавали в него признаки, выводимые из этого понятия.
