Правила написания и рефакторинга кода, не зависящие от языка. PHP-специфика — skill `php`, C#/Unity — skill `csharp`, скрипт страницы админки — skill `twig`.

## Типы

- Ссылка на тип — импорт короткого имени в шапке файла, не полное имя с пространством имён в точке использования. Тип, импорта не требующий (встроенный, глобального пространства языка), — вне правила. Встреченный inline-прецедент — не образец для копии (core «Копирование прецедента»)
- Форма возврата набора записей — по способу адресации у потребителей: адресуют по идентичности (id/slug/хеш) → словарь с этим ключом, ключ внутри значения не дублировать; только перебирают → позиционный список. Одинаковое пост-преобразование набора у двух и более потребителей (перекладка в словарь, повторный поиск по полю) → чинить форму в источнике, перекладку снять. Проверять при написании метода и при появлении второго потребителя. Правка уже выбранной формы — skill `php`; вывод MCP-тула — skill `mcp` «Словарь vs список в контуре тула».

## Отказ и дефолт

- Невалидный ввод, импорт, коллизия инварианта → fail-fast исключением. Запрещено «спасать» подгонкой данных под инвариант (обнулить, обрезать, отбросить, подменить), в том числе с предупреждением, и обходить негодный экземпляр ради следующего кандидата (другой донор, другая копия) — исключение называет негодный экземпляр. Best-effort с пропуском — только явное продуктовое требование. Атомарность отказа — skill `php`
- Перехваченное исключение, из которого потребителю показывают только текст сообщения (всплывающее уведомление, модалка, поле ошибки в ответе), записывать в журнал вместе со стеком. Автоматический журнал рантайма пишет лишь НЕперехваченные исключения — пойманное идёт мимо него, и причина остаётся видна только по тексту сообщения

### Дефолт против исключения

Требование не возвращать молча дефолт не запрещает дефолт как таковой: пустой ответ аксессора (null, false, 0, пустая коллекция) несёт один из двух смыслов, различать по тому, что значение значит для вызывающего.

| Смысл пустого ответа | Что это | Исход |
|---|---|---|
| Легитимное отсутствие | спроектированный ответ, у вызывающего есть корректная реакция: записи нет в справочнике, у действия нет своего варианта → общий fallback | дефолт оставить |
| Зависимость не готова | кеш не загружен, инициализация не отработала, метод вызван до своей предпосылки | бросить исключение |

Одно и то же значение означает И отсутствие, И неготовность → это и есть маскировка: развести — исключение на «не готова», дефолт только на «отсутствие».

Признаки маскировки:

- значение приходит из ветки по полю-кешу, заполняемому один раз при инициализации либо входе
- у вызывающего нет отдельной реакции на «не готов» — он трактует дефолт как отсутствие и едет дальше (сущность без визуала, флаг тихо false)
- предпосылка гарантирована порядком инициализации → дефолт-от-неготовности в норме недостижим, значит его появление есть баг, обязанный падать

Признаки легитимного дефолта:

- try-семантика поиска, где «не найдено» — обрабатываемое состояние
- состояние «не готов» невозможно (валидируется у источника на входе) ЛИБО у вызывающего есть fallback именно на этот дефолт, а не «поехали дальше»

По признакам непонятно → не угадывать дефолтом: прочитать вызывающие места и порядок инициализации.

## Огораживание ввода

Перечислимое/справочное значение во ВВОДЕ (MCP `inputSchema`, JSON API, admin-select, WebSocket-команда) — огораживать: точный выбор из достоверного источника (`ref` на list-tool / `EntityType`/`ChoiceType` / справочник) + валидация против него ДО обработки, не произвольный текст. Идентификатор цели действия → path/обязательный ref; фильтр/опция → query. Исключение (нужна свобода: `code`/`data`/payload) — документировать явно. Доменная механика — skill `mcp` (`ref`) / `admin` (path vs query).

Запись частична (непереданное сохраняет прежнее значение) → проверка входа считает итоговое состояние (присланное поверх текущего), не присланный фрагмент.

Проверяемое по одному лишь входу (диапазон, форма значения, сочетание параметров) стоит первым блоком операции, до первого обращения к носителю данных; требующее данных — сразу за их получением.

## Запрещённое действие — не молчать

Действие без легитимного исхода (дубль; повтор операции, для чьих целей есть иные инструменты — обновить, сбросить) → `throw` либо guard на входе, не молчаливый возврат существующего и не no-op. Внутренний потребитель, которому нужен существующий объект, ищет его явно, не через создающую операцию.

## Боевой потребитель новой возможности

Заводя в продукт новую возможность (тул, параметр, поле, контрол, метод), назвать её потребителя вне тестирования и его задачу: игрок, гейм-дизайнер в админке, механика игры, внешний ИИ. Не называется → не заводить: облегчение собственной проверки и прогона спек потребителем не является, нужду прогона закрывать существующими каналами либо разовым артефактом. Без чего канал не отдаёт данные никому (срез ответа под лимит вывода) — свойство канала, заводится без потребителя (skill `mcp` «Срез вывода read-тула»); фильтр под конкретный вопрос — возможность.
Ветка приёма второй формы значения (второй вид входа, второе состояние данных) проходит тот же тест со стороны производителя: назвать свой канал записи, фактически создающий такую форму (форма админки, MCP-тул, выгрузка, импорт), перебрав каналы целиком. Ни один не создаёт → ветку не заводить, форма отбивается отказом; принимать ли её — правило продукта (`core` «Правило продукта — решение пользователя»).

## Охват новой механики по носителям и каналам

Механика реализована у одного носителя → назвать класс носителей по свойству, ради которого она заведена (не по имени типа либо каталогу), и провести её по классу целиком; у каждого носителя — по всем каналам к нему (форма админки, MCP-тул, обновление из внешнего репозитория, импорт, установка из каталога). Канал, механики не получивший, отказа не даёт. Носитель либо канал остаётся без механики только по решению пользователя (`core` «Правило продукта — решение пользователя»).

## Множество потребителей внешнего канала

Проектируя выдачу либо приём на канале, доступном извне (эндпоинт клиента, публичный роут, внешний API), множество потребителей считать по тому, что канал допускает, не по тому, как ходит свой клиент. Границу выдачи задаёт проверка на самом канале, у каждой точки входа своя: отбор у перечисляющей операции границей для выдачи по прямому идентификатору не служит.

## Ограничение модели — по названному вреду

Вводя в модель ограничение (запрет, уникальность, взаимоисключение), назвать вред от его отсутствия — что сломается, у кого, при каком действии — и подтвердить фактом тем же проходом; не подтверждается → ограничение снять. Отсутствие сценария использования, стройность модели и симметрия вредом не являются.
Ограничение есть гейт доступа к данным → обойти остальные каналы, отдающие те же данные: сосед отдаёт копию без условий → гейта нет; сосед сужает выдачу критерием → копия держит тот же критерий; производное представление, по которому исходного не восстановить, копией не является.
Гейт точки входа (роут, эндпоинт, тул) строится на своих данных — принадлежности записи, её критерии видимости, собственном праве роута; вызов проверки доступа к посторонней точке входа гейтом не является. Отдаётся производное представление → гейта нет вовсе.

## Механика игры — в её контенте

Механика конкретной игры реализуется её собственным контентом: элементы игры со своим кодом (компоненты, команды, префабы), код механик в песочнице. Платформа под неё не подстраивается: ради одной механики не заводят ни поле сущности платформы, ни справочник, ни новый канал доставки данных клиенту. Платформенный код бандлов и схемы MCP под неё не правят.
Расширение платформы законно, когда его обоснование называет класс механик у любой игры без имени конкретной игры; иначе решать в контенте игры. Платформенное обоснование («все игры») требует и носителя, общего всем потребителям: фреймворк либо библиотека механик общим не является, а копия у одной игры, ведомая вышестоящим источником без права отправки наверх, правку никому не отдаст — провенанс и право отправки читать в мета носителя (MCP instructions) до правки.

## Место правки на маршруте данных

У значения есть маршрут (вычислитель → сборка пакета → канал доставки), правка законна на каждом звене. До правки пройти маршрут и назвать проходы, которые по этим данным уже идут: правка ложится туда, где нужный признак уже вычислен. Признаки чужой точки: под правку заводится свой цикл; повторно добывается то, что соседний проход уже держит; цена растёт с частотой прохода (каждый кадр, каждая запись).

## Место проверки условия

Условие проверяется в самой ранней точке, где его входы уже есть; позже стоит лишь условие, чьи входы появляются только там (результат создания, ответ вызова, значение живого объекта). Условия одного решения разводить по своим точкам, не писать одним блоком у позднейшего. Признак, известный при сборке набора, входит в её фильтр, не в отсев после.

## Необратимый шаг во внешней системе

Шаг операции необратим (заливка файла, публикация, отправка в чужой репозиторий, заведение сущности у стороннего сервиса), за ним идут ещё шаги → его исход сохранить в своей записи немедленно, до следующих шагов. Иначе отказ следующего шага оставляет запись без исхода: повтор делает необратимое заново — во внешней системе копятся дубли. Фиксируется ровно состоявшееся, не итоговое состояние операции: по нему повтор доводит оставшиеся шаги, необратимую часть не трогая. Условия отказа проверяются до необратимого шага («Место проверки условия»). Откат эффекта возможен → атомарный отказ вместо фиксации (skill `php` «Подавление ошибок»).

## Решение — там, где есть контекст

Код выбирает представителя из равноправных входов (первый, минимальный, «любой из»), и выбор меняет исход → решение принимается не на своём месте: перенести туда, где контекст однозначен. Замена эвристики выбора дефекта не снимает. Недостающий контекст — воля человека → выбор делает он, значение приходит параметром действия; действие, привязанное побочным к другому, отнимает и возможность не действовать. Перенос выбора к человеку меняет правило продукта → `core` «Правило продукта — решение пользователя».

## Переопределение с вкладом родителя

Переопределяя метод-носитель вклада родителя/примеси (вклад в результат/побочный эффект/мета/инициализацию) — осознанно: либо вызвать родительский вклад (`parent::`/`base.`/`super.`), либо полностью заместить; молчаливый дроп вклада — баг, не выбор. Кросс-доменно: PHP trait/parent, C# `base.`, JS `super.`, mixins/middleware/декораторы, Unity-контроллер с `Awake`/`OnEnable`/`OnDisable` без `base.*`. PHP-механика (алиас трейтового метода + merge, class-over-(parent|trait) без `insteadof`) — skill `php` «Наследование».

## Оповещение о смене состояния

Состояние ведёт один компонент, читают несколько → при появлении второго читателя перечислить все пути смены (контрол человека, вызов api, фильтр, восстановление сохранённого, начальная установка) и провести каждый через объявленный канал оповещения, поднимаемый в точке, общей всем путям. Канал, объявленный словами в комменте, механикой не обеспечен — сверять по коду, поднимающему событие.

## Свежесть производного артефакта

Годность копии производного (ответ по условному запросу, файловый кеш) решает отметка свежести (`ETag`/`Last-Modified`, время файла против даты записи-источника), и мерит она только свой источник: перед записью значения в производный артефакт назвать источник отметки и все входы значения; вход вне источника (формат сериализации, внешнее состояние) → значение вычислять при выдаче либо втянуть вход в отметку. Изменяемый состав полей либо формат держать на отпечатке — метка версии схемы плюс данные; голая дата метки не несёт. Правя формат, снять существующие копии тем же проходом, включая их запись в отдельно лежащей отметке (реестр, манифест). Формат разбирает чужая сторона → метку версии формата держит она (клиент игры — канон клиента, указатель skill `unity`). Бамп метки при мутации данных — skill `orm-access`.

## Ожидание чужого времени в сборке ответа

Вызов, ждущий сторону, чьё время НАМ НЕ ПОДКОНТРОЛЬНО, — поход по сети к чужому серверу, запуск чужого процесса, обращение к стороннему сервису, — в сборку ответа, которого ждёт его получатель, не ставить, когда он КРАТЕН числу записей выдачи. Три признака нужны ВМЕСТЕ:

- ЧЬЁ ВРЕМЯ ждём. Ось — время, не граница, за которую уходит вызов: обращение к соседнему модулю и запрос фронта к своему же бэку читаются «внешними», правилом не покрыты — тот же процесс либо та же машина, время предсказуемо; ЧИСЛО запросов к своей базе, кратное числу записей выдачи, держит skill `orm-access`
- КРАТНОСТЬ числу записей выдачи — вызов на строку списка. Одиночный такой вызов на странице одной записи не запрещён
- МЕСТО — внутри формирования ответа. Ответ ушёл получателю → тот же вызов законен, и в нём ЛЕЧЕНИЕ: запрещена сборка ответа, не показ значения вообще

Ограничитель (не больше N вызовов на запрос, порог свежести у записи) решением не является: ответ несёт N ожиданий подряд, а выдача остаётся неактуальной — обновлены N записей из показанных. Записей больше, чем успевает опросить один запрос → просроченные находятся всегда, и оба дефекта держатся разом.

Свежесть ведёт канал мимо сборки ответа: до-опрос из браузера после отрисовки по показанным записям плюс обход по расписанию; сборка ответа читает только сохранённую отметку.

## Канал проверки состояния среды

Состояние среды, читаемое рантаймом языка либо ядром напрямую (жив ли процесс, есть ли файл, занят ли порт), читается ими, не запуском внешней утилиты с разбором её вывода. Утилиты в образе может не быть вовсе, и её отсутствие приходит пустым выводом — тем же, каким приходит отрицательный ответ: решение строится на ложном «нет». Сигнала об отказе не возникает нигде — код возврата теряется в разборе, пустой вывод разбирается штатно, — и следствия расходятся веером, каждое со штатным видом.
Внешняя программа, делающая работу, невыразимую своими средствами, под правило не подпадает; своих средств для состояния нет → присутствие программы проверять отдельно, её отказ разводить с отрицательным ответом и отдавать отказом операции.

## Анализ и рефакторинг

- Вердикт статического анализа («условие всегда истинно», «проверка избыточна», «ветка недостижима», «метода не существует») — гипотеза его модели, не факт: снимать проверку либо сужать объявление — только назвав, на чём вердикт держится, и исключив живой случай (окно до инициализации, запись по вычисляемому индексу, переключатель, меняемый вне прогона анализа). Проверка живая, неверна модель → код оставить, сообщение гасить в конфиге анализатора либо игнорировать; подгонка кода под модель запрещена
- Кандидат на мёртвый код (метод, обработчик, ветка после рефактора) → обойти все потребители и пути вызова; подтвердилось лишним → удалить самому без запроса разрешения, если содержимое восстановимо из истории либо индекса (`git ls-files --error-unmatch <путь>`, `git show HEAD:<путь>`, `git show :<путь>`). Неотслеживаемый файл, носитель под игнором git и код вне репозитория стираются невозвратно — их снос под гейтом-через-подтверждение (CLAUDE.md). Тем же проходом править комментарии-ссылки на удалённое
- Видимость члена выбирает его фактический потребитель при написании: только изнутри класса → закрытый, только наследники → защищённый; открытый без вызывающих снаружи → сузить либо инлайнить («Дедупликация»); видимость задана контрактом надкласса либо интерфейса → решать в контракте
- Tolerance/fallback под легаси-формат либо прежнее состояние собственных перечислимых данных → мигрировать данные и удалить ветку тем же проходом, что заводит новый guard; перед удалением мигрировать легаси либо убедиться, что его нет. Смена собственного формата → back-compat не заводить, канон один с первого коммита. Формат, намеренно живущий параллельно, — не легаси
- Правка, обязанная сохранить поведение (сведение копий, вынос, перенос), чей вклад доходит до байтов выпускаемого документа (выгрузка, экспорт, ответ), принимается сверкой отпечатка документа до и после: эталон снимать до правки, входы подбирать так, чтобы каждый сведённый экземпляр исполнился.

## Единый источник истины

Повторяющийся литерал/значение/конфиг/логика — не копировать: один источник (класс констант, enum, конфиг бандла-владельца, общий сервис/база/трейт). Ссылаться по имени (`Enum::Case->value`), не строкой. Копия устаревает молча — источник уехал, копия соврала. PHP-механика выноса кода (proxy/inline/extract, операция из двух фронтов) — skill `php` «Дедупликация»; перечни enum/числа/имена в skill и доке — skill `skill-rules` / `doc`.

Один наблюдаемый исход строят несколько независимых исполнителей (разные контуры, языки, процессы) — едино правило исхода, не код: копия реализации тут неизбежна, потому расхождение исходов есть дефект, а не свойство контура. Правя одного исполнителя, назвать остальных и привести тем же проходом; направление выравнивания задаёт тот, чей исход верен по правилу продукта, своего правила ни один исполнитель не заводит. Приёмку выравнивания закрывает сверка каналов наблюдения между собой — `artifact-check` «Верификация артефактом».

Денормализованная проекция (кэш ради фильтра, листинга, скорости) легитимна, но верна лишь пере-вычисляемой из источника при каждой синхронизации; носитель выбирать по изменчивости источника: стабильная мета вмораживание переживает, изменчивый признак — пересчитывать при sync. Долговечность носителя состояния мерится сроком жизни объекта-хозяина: назвать событие, при котором носитель теряет состояние; хозяин его не переживает → потеря состояния норма, более долговечного носителя не заводить.

Свойство едет потребителю каналом своего носителя, не справочником обо всех элементах класса внутри чужой сущности; довод «канал носителя такого не возит» — задача расширить канал. Довод об экономии строится по всем точкам, где значение материализуется (запись справочника, копия в каждом экземпляре рантайма, отправка соседнему процессу), перечисленным до вердикта.

Подготовленный срез данных (файловый кеш, экспорт, снимок), собранный модификаторами, читают из артефакта, не из первоисточника: чтение сырого состояния повторяет у себя каждый модификатор и расходится со сборкой; запись идёт в первоисточник; нужного поля в артефакте нет → дополнить сборку.

Существующая ручная копия (в прецеденте, во фреймворке) — не довод сохранить дублирование при возможном общем источнике: вынести и переписать все копии разом, включая образец.

Заведение общего носителя (база, трейт, общий сервис, функция) — точка обхода всего проекта: носители выносимого механизма искать по тому, что код физически делает (значение-константа, литерал, вызов), не по имени, каталогу либо бандлу; носитель, написанный тем же заходом, подключается к базе, а не пишется рядом. Копия, к базе не подключённая, застывает на поведении до выноса.

Состояние рантайма — тот же предмет: заводя поле-флаг, сперва проверить, не выражено ли состояние наблюдаемым свойством объекта (активность, видимость, режим) либо значением-источником (настройка, поле сущности, ответ сервера); второй флаг законен, лишь когда назван вход, при котором носители обязаны разойтись.

Контрол интерфейса — тот же предмет: одно действие пользователя несёт один контрол; заводя контрол, искать существующий того же действия по всему рендеру страницы (панель, вкладка, колонка, базовый шаблон) и расширять его; различие семантики эффектов складывается на одном контроле.

Имя ключа в структуре-возврате называет источник одним именем для всех потребителей; переименование ключей у потребителя (перекладка один-в-один при сборке ответа) заводит второй словарь — лечить переименованием в источнике. Правка формы — skill `php` «Типы»; выбор контейнера — «Типы» выше.

## Дедупликация

Порядок решения: сперва СЛОЙ — чем логика является и куда принадлежит, — затем внутри разрешённого слоя ФОРМА (порог метода, порог класса, инлайн, обёртка). Приёмником инлайна служит потребитель, чей слой такую логику принимает; слой с ограниченным правилом проекта составом (`php` «Дедупликация», skill `entity`) приёмником не бывает.

- Перед созданием класса, перечисления либо метода — проверить существующие на совместимость (аргументы, домен): совместимо → расширить существующий, в том числе его сигнатуру; несовместимо → своя единица
- Методы с почти одинаковым телом → один метод, различие — аргументом. Различие, сведённое к одному значению либо наличию/отсутствию одного элемента результата (ключ в возвращаемой структуре) и заданное типом либо перечислением, → ветка внутри метода, не выносить в переопределение, отдельный метод либо класс: одно значение отдельной единицы не требует. Различаются ТЕЛА веток, не одно значение → переопределение законно (делать осознанно — «Переопределение с вкладом родителя» выше). Малое различие, всплывшее в уже схлопнутом методе, → ДОБАВИТЬ ветку, не разъединять обратно — преждевременная абстракция
- Дедуп не откладывается: второй почти-идентичный метод — точка немедленного схлопывания; ярлык «тривиальная обёртка / потом» копию не оправдывает — тривиальность задаёт форму дедупа (инлайн), не право отложить
- Метод с единственным вызовом — инлайнить, даже если «красиво выделен». Отдельный метод оправдан только при >15 строк со своей ветвистой логикой ИЛИ если вызывается из ≥2 мест ИЛИ рекурсивный. Цепочки крупных одноразовых методов (A→B→C) — тоже инлайнить
- Гард/предусловие без возвращаемого значения (валидирует и бросает, вызывающему ничего не отдаёт) — инлайнить в защищаемую операцию ДАЖЕ при >15 ветвистых строк: допуск «>15 ветвистых строк → метод» только для значение-возвращающих под-билдеров (`build*`/`compute*` → данные, что вызывающий вставляет в результат; имя документирует фрагмент вывода). Гард — интринсивное предусловие одного вызывающего, не переиспользуемая единица: имя прячет гейт за индирекцией, держать видимым в начале операции; отдельным методом оправдан лишь при ≥2 вызывающих. Различитель — не «проверка ли это», а возвращает ли потребляемое значение: предикат `isX`, по которому вызывающий ветвится, — значение-метод (правило не про него); `assertX`, который бросает, — гард
- Порог отдельного КЛАССА в своём файле выше порога метода: класс, чей публичный интерфейс зовут из одного файла-потребителя, схлопывается в него методом. Класс оставляют по названному основанию: ≥2 потребителя; точка расширения по конвенции слоя, записанной правилом проекта; граница между процессами либо раздельно развёртываемыми модулями. Вынос ради единообразия решает пользователь (`orchestration`)
- Прокси/обёртку не плодить — звать целевой напрямую. Классифицировать по телу: чистый форвард (в другой метод либо в источник значения — переменную окружения, константу, конфиг), в том числе с приведением типа, → прокси; своя нетривиальная логика (проверки, бросок, null-fallback, запрос к хранилищу, содержательное преобразование) → не прокси. Формы: метод-прокси и геттер-делегат `getXY()` → звать `getX().getY()`; геттер над источником значения → читать источник по месту; класс-фасад с единственным форвардом → внедрять целевую зависимость; тонкий подкласс с флипом видимости → брать значение через родительский метод. Развязка через интерфейс-порт прокси не является (skill `php`)
- Прокси/обёртку не оправдывают: ни «≥2 точек вызова», ни «симметрия с соседним сервисом» (соседний оправдан СВОЕЙ логикой, пустая обёртка симметрию не наследует), ни модификатор доступа. Модификатор — граница против ВНЕШНЕГО потребителя (опубликованный API, чужой непра́вимый код); нужен доступ изнутри своего модуля — звать целевой напрямую либо расширить видимость самого целевого, обёртку не заводить. Граница между процессами либо раздельно развёртываемыми модулями — настоящая, под это не подпадает. Ось тут — существование обёртки; ВЫБОР видимости члена держит «Анализ и рефакторинг»
- «Не прокси» (своя логика по телу) и «единственный вызов / единственный потребитель» — ОРТОГОНАЛЬНЫЕ оси, прогонять ОБА теста. Юнит с оркестрацией, проверками и броском проходит proxy-тест и всё равно подлежит инлайну, если вызывается из одного места. Остановка анализа на «не прокси» — типовой срыв
- Тест на прокси и инлайн применять к форме ПОСЛЕ безопасного behavior-preserving изменения, не к текущей. Юнит, становящийся прокси или одноразовым инлайн-кандидатом после правки, не ломающей и не раскрывающей лишнего ВНЕШНЕМУ потребителю, — УЖЕ таков. Типовые трансформы: расширить видимость — безопасность по оси поведения и инкапсуляции, вторая ось — компилируемость переопределяющих наследников, пройти по ним как при правке контракта; перенести тривиальную композицию к вызывающему; вынести тело в единый источник — метод стал чистым форвардом → инлайнить в точки вызова ТЕМ ЖЕ проходом, делегат не оставлять. Срыв: формулу вынес в общий сервис, старый метод оставил форвардом, точки вызова не переключил
- Перенос кода (схлопывание класса в потребителя, вынос в общий носитель, переезд между слоями и бандлами, разделение файла) — написание каждой единицы заново: на новом месте у каждого метода, класса, параметра и ветки заново называется основание существовать (число вызывающих там, порог объёма и ветвистости, слой); основания нет — единица схлопывается тем же проходом
- Абстрактный/родительский класс с ЕДИНСТВЕННЫМ подклассом — красный флаг преждевременной абстракции. Закрытое тело, извлечённое в родителя и зовущееся из одного подкласса, схлопывать в этот подкласс (инлайн тела и удаление базы), пока второй подкласс не появился реально. Комментарий-обещание второго потребителя («общее тело для X/Y» при отсутствующем Y) второй подкласс не заменяет — частный случай запрещённого «возможного будущего потребителя», применённый к иерархии. Граница: правило не применяется там, где цепочка наследования — ЗАЯВЛЕННАЯ конвенция слоя, ЗАПИСАННАЯ правилом проекта (звено цепочки есть точка расширения, единственный подкласс у звена нормален by-design). Конвенция — записанное правило носителя, не наблюдаемая практика: «у соседей так же», «наследник пока один» и удобство её не образуют; конвенции нет → правило в силе
- Класс списывается с существующего целиком — те же точки входа (роуты, команды, обработчики), тот же разбор входа и форма ответа — с заменой тела одного-двух шагов (источник данных, правило записи) → база: точки входа целиком у неё, заменяемый шаг — абстрактной точкой расширения; подкласс объявляет только точки расширения, точку входа не переопределяет. Различие в одном значении точки расширения не даёт — ветка (буллет о почти одинаковых телах выше). Признак по коду: два класса объявляют каждый своим телом точку входа с одинаковым именем либо одинаковым хвостом адреса маршрута. Второй подкласс тут существует в коде — граница с преждевременной абстракцией буллета выше; класс против трейта под базу — skill `php` «Наследование»

### Ветки одной развилки — одной формой

Ветки развилки РАВНОПРАВНЫ, когда каждая доводит операцию до её штатного исхода: ни одна не есть отказ, ранний возврат либо частный случай. Равноправные ветки оформляются ОДНОЙ формой — каждая своей именованной единицей либо все инлайн ветками одного условного оператора. Метод с развилкой собственного тела ветки после неё не несёт: ему остаются преамбула и выбор ветки.
Порог отдельной единицы мерится по каждой ветке: прошли обе — выносятся обе; не прошла ни одна — инлайн обе; прошла одна → вынос соседней ради единообразия решает пользователь (`orchestration`). Вторую ветку, заводимую к уже написанному телу, не писать отдельной единицей при первой в теле метода.

### Дополнение под одного потребителя

Единица нужна многим и остаётся; предмет правила — её ДОПОЛНЕНИЕ (параметр, ветка, поле, режим), заведённое ради ОДНОГО потребителя. Знать о дополнении обязаны ВСЕ: передавать значение, держать умолчание, разбирать ветку.
Перед добавлением назвать исход ОТКАЗА от дополнения — чем потребитель обходится БЕЗ него. Обходится общим значением либо своими средствами → не заводить: отказ меняет ЧАСТНОСТЬ (формулировку надписи, оттенок поведения), а не механику, нужное одному потребителю решать у него самого. Остаётся лишь СВОЯ копия единицы (разметки, тела, значения) → дополнение законно.
Цену меряет число мест, обязанных о дополнении знать, не его размер; копия единицы дороже этой цены. Единственный потребитель дополнения ушёл → снять дополнение тем же проходом.

### Ось понятия и вывод из неё

Несколько признаков, всегда выводимых друг из друга и заполняемых в одном месте, — одно понятие, разложенное на флаги. Свести к ОДНОЙ оси с закрытым перечнем значений; заполняет её точка, где известны исходные факты. Детектор разложения — тест на обязанность носителей разойтись («Единый источник истины» выше), прогнанный по набору ПОПАРНО: входа для пары не называется → признаки пары лежат на одной оси.

Вывод из оси принадлежит ОБЩЕМУ носителю — тому, что рисует, — не вызывающим. Стиль, доступные действия, подписи, тексты подтверждений, попадание под фильтры и счётчики (список открытый) он выводит сам, приняв одно значение оси. Вызывающему остаётся то, что осью не выражается.

Значения, друг из друга НЕ выводимые, но всегда заполняемые ВМЕСТЕ из одного источника и передаваемые порознь — отдельными параметрами либо полями, — поля одного объекта: передавать их объектом, не россыпью. Попарный тест выше такой набор пропускает: по ЗНАЧЕНИЮ признаки расходятся всегда, вход для пары называется, и набор читается независимым. Признак тут другой — назвать вызывающего, который заполняет одно значение БЕЗ другого; не называется → значения принадлежат одному объекту. Цена россыпи: распаковка повторяется у КАЖДОГО вызывающего заново, а сигнатура принимающей единицы растёт на параметр с каждым таким набором.

Точка срабатывания обоих классов — добавление параметра либо поля к существующей единице: попарный тест прогонять по новой паре, добавляемое против каждого соседа из того же источника.

## Root-fix у источника

Дефект родился в источнике (сосед/слой/процесс отдал не тот тип/формат/пакет, упал метод) — лечить в точке возникновения, не маскировать у потребителя; у потребителя — только диагностический лог. Формы обхода-маскировки:

- защита ради одного типа (`if`/`instanceof`/`match`/`method_exists`/`try-catch`/fallback/null-check/конвертер) → перенести защиту в тип (сделать безопасным / реализовать интерфейс везде / явно запретить тип `throw`) либо починить источник
- СКАН/пере-вычисление вместо инварианта, который источник обязан держать
- ПАРАМЕТР-ФЛАГ, разводящий потребителей общего критерия («пропускать ли X»): сперва проверить сам критерий — склеивает два независимых свойства → расщепить в источнике на два предиката с точными именами; режимный параметр законен, когда потребители решают разные задачи над одним свойством
- худшее — проектировать вокруг текущего неверного состояния источника: чинить источник, не строить поверх

Ограничение текущей реализации, всплывшее как «стопор», — кандидат на root-fix, не потолок: варианты выстраивать лестницей дёшево→дорого самому, брать простейший, решающий задачу. Формы простейшего: разовая операция над данными (мигрировать, перегенерировать, push) либо готовый инструмент вместо accommodation-кода под рассинхрон; расширение существующего механизма вместо параллельной структуры — просьба отразить состояние (подсветка, флаг, статус) → первым шагом найти существующий носитель состояния и расширить; данные для другого слоя → сперва существующий канал доставки в этот слой целиком, не эмиссия в чужом бандле. Перед обходом локализовать, чьё ограничение: само-наложенное вышестоящим кодом (root-fix там), само-наложенное формой хранения (заплатка внутри контейнера — маркер-значение, сигнал о дефекте вместо предотвращения — сигнал сменить форму: искать соседа с тем же классом данных и другой формой) либо framework/внешнее. Scope держать на фактической цели.
Предмет находки лежит на канале приёма чужого артефакта (файл от художника, пакет стороннего редактора, импорт) → достижимость меряется тем, что допускают формат и код приёма; «таких данных у нас нет» недостижимостью не является.
Прогон проверки вскрыл расхождение двух носителей одного контракта (элемент есть у одного, у второго не объявлен) → направление выравнивания решает потребитель элемента — читатель значения; читателей нет → снос элемента с обеих сторон. Исполняемость производителя живости не доказывает.
Вводя инвариант (зарезервированное значение, флаг-состояние, sentinel, по которому различается поведение), защитить его guard'ом на всех точках записи поля, включая чужие слои (sandbox, клиент); довод «сейчас так никто не пишет» пропуск не оправдывает. Место guard'а — где инвариант может быть нарушен, не где обнаружен: метод, отдающий данные наружу (сериализация, выгрузка), точкой записи не является. Инвариант на паре значений — точки перечислять по обоим. Заводя новую точку записи поля с действующим инвариантом, правило приведения формы держать в точке, общей всем каналам записи (skill `entity` «Один инвариант — один guard»).
Повод, под который код уже написан, исчез → судьбу написанного не решать молча ни откатом, ни оставлением: переоценить по существу; разрешимое чтением кода решает агент сам и называет строкой итога; продуктовую ценность решает пользователь окном `AskUserQuestion` с явной рекомендацией; исполнитель → стоп-сигнал координатору.

## Не глушить сигнал ошибки

Удаление либо подавление сигнала ошибки (throw, log, показ пользователю) ради исчезновения симптома — сокрытие дефекта: сперва заземлить механизм (почему ошибка возникает), затем чинить причину. Заземление вскрыло, что сам сигнал выбран неверно (throw на ожидаемом состоянии, где рантайм трактует его фаталом) → смена на корректный контроль-флоу законна.

## Полнота охвата и проверки

Перед суждением либо правкой кода обойти все ветви (error paths, `catch`, fallback, каскады, условные — дефект чаще в обработчике) и всех потребителей источника, у каждого свой контракт; граница потребителей — явный контракт, не предположение об идентичности. Расширение отдаваемого множества (снятие фильтра) обход не отменяет: потребитель-искатель (guard, резолвер) расширение переживает, потребитель-фильтр получает мусор либо ложный контрол — для каждого спросить отдельно.

## Утверждение о коде — после чтения ЭТОГО кода

Утверждение о поведении конкретного кода (какой класс/механизм, как вычисляется значение, что отдаётся наружу) — только после чтения этого кода; файл — один `Read`, тем более открытый в IDE или названный в треде. Спущенное сверху утверждение, на котором СОБИРАЕШЬСЯ действовать, требует чтения кода в точке действия.
Границы «ЭТОГО кода»:

- авторский текст о поведении кода (коммент, докблок, `description`) — не этот код: заземляет прослеженная самим цепочка (чтение вычислителя, замер в живой системе, пробный вызов). Наблюдаемое разошлось с описанным → первым действием разложить цепочку, лишь затем трогать значения. Одно правило описывают два текста у двух носителей → факт заземляет текст у той стороны, о которой утверждение; расхождение текстов — сама находка. Когда текст протухает — «Содержание комментария»
- vendor-звено на маршруте данных (submit формы, сериализатор, event-цепочка) — тот же «этот код»: читать в vendor до точки прохождения либо отбития значения
- при наследовании — член фактического класса исполнения, не предполагаемого родителя: подкласс затеняет свойство и метод
- у производного значения (кеш-поле, снимок, мемо, проекция) — вычислитель до конца цепочки, включая гейты, гасящие часть полей
- наблюдение живой системы заземляет наблюдённое значение, не правило его порождения (кто шлёт, по какому условию): правило читать в коде-вычислителе до трансляции наблюдения и до опоры на него
- давность собственного чтения: прочитанное ходами раньше заземляет прошлое состояние — перечитать в точке действия и перед утверждением о носителе; параллельная работа над носителем подтверждена → перечитать заново либо назвать время снимка
- обе стороны канала обмена: что уходит от отправителя, читается в коде отправителя, между сторонами лежат сборка пакета, отбор, чистка, кеш; обмен наблюдаем (пакет в журнале, дамп) → диагностировать снимком обмена, не реконструкцией из кода; вторая подряд гипотеза об одном дефекте — снимать обмен
- обе стороны сравнения («у соседа иначе», «как у X»): образец читается наравне с предметом, роль образца заземлением не является; носитель, открытый в сессии под другой вопрос, заземления не даёт
- достижимость ветки на приходящих данных заземляет код, порождающий передаваемое состояние, — гейты каждого канала, способного состояние создать, — не механизм рассылки

Пересказ термина либо пункта документа, объяснение поведения UI-контрола, резюме слов и требований пользователя — то же утверждение: читать носитель (FormType, шаблон, контроллер) до ответа, интерфейсная метафора основанием не является; деталь сверять и с формулировкой пользователя, и с кодом. Термин, в коде не существующий, — заземлять либо помечать предположением. Пример внутри объяснения и каждое утверждение составной фразы заземляются отдельно.

## Вердикт и обоснование критерия

Архитектурный/рефактор-вердикт («X лучше/хуже», «не переносить», «нарушает слои») — после grep/чтения реальных call sites и принятых в проекте паттернов; общий принцип без них не основание, принцип, опровергаемый кодом проекта, отбрасывать.
Форма ответа планку НЕ снижает: развёрнутый ответ с трейд-оффом, планом реализации либо оценкой профита/целесообразности/объёма — тот же вердикт под той же планкой (профильный skill + чтение носителей ЦЕЛИКОМ: констрейнты классов, ОБЕ стороны контракта, включая КЛИЕНТСКУЮ). Оценка ЧУЖОЙ идеи на профит — вердикт, не болтовня.
Числовая величина, названная фактом (в ТЗ, ответе, обосновании), заземляется замером, а переход от измеренного к искомому (разность, доля, отношение) доводится вычислением до конца. Константа в коде — гипотеза о величине, до наблюдаемого эффекта стоит ещё звено; «примерно сошлось» — сигнал считать точнее. Настраиваемое поле читать у носителя настройки (сцена, префаб, конфиг, запись базы, переменная окружения), не по объявлению в коде. Величина, зависящая от состояния системы, замеряется в рабочем состоянии. Величина с сырого носителя мерится тем же разбором формата, каким читает потребитель. Величина на входе, который выставит потребитель вывода (настройка игрока, выбор из диапазона), берётся краем объявленного диапазона с самым тяжёлым исходом, не умолчанием, и выбор края называется рядом с числом. Замер с экземпляра переносится только на экземпляры с тем же кодом механизма, ограничивающего величину, — проверить, действовало ли ограничение на замеренном.
Место, порождающее замеренную величину (запросы, время, память), заземляется замером с атрибуцией по вызывающему, не чтением кода; нет атрибуции у прибора → доработать прибор. Класс работы (база против приложения) — skill `diagnostics` «Где время массовой операции».

## Фактический вопрос ≠ нормативный

Фактический («что делает код / как устроено сейчас») заземлять в коде; нормативный («как ЛУЧШЕ/правильно организовать», «как надо») отвечать про идеал — текущая реализация тут ВХОД для фактов, не ПОТОЛОК для дизайна.

- Срыв 1: на нормативный вопрос («как лучше», «нужно ли», «стоит ли», «как считаешь») отвечаешь текущей реализацией — подмена ought на is. Ответ несёт позицию «надо / не надо» с обоснованием по выгоде сторон. Маскированные формы той же подмены, доводом не служат: текущее назначение носителя («у поля другая семантика»); записанный текст об устройстве (справка, `description`, докблок, README) — норму несут только правила проекта; цена изменения («сломаются вызовы», «дорого мигрировать», временная неработоспособность по ходу переделки) — законна лишь входом в приоритет после названной позиции; нейтральное описание механизма без позиции. Проба по своей фразе: описывает отсутствие предлагаемого либо цену внедрения → это формулировка задачи, не довод
- Срыв 2: отвергаешь предложение, разбив его слабую версию — оценивать сильную: форму, снимающую твоё возражение, искать самому (стенка-контракт формы → вычислимая форма кода; стенка-факт соседней системы → факт переводим). Два обойдённых пользователем возражения-стенки за тред — повторный промах (orchestration «Непрерывное обучение»)
- Срыв 3: прочитанный код принимаешь за границу пространства решений → ограничение снимать лестницей «Root-fix у источника»
- Срыв 4: на фактический вопрос об устройстве («как это работает», «по кнопке, в фоне либо запросом») отвечаешь предложением починки либо окном вариантов — ответ несёт само устройство по механизму (чем запускается, где исполняется, каким каналом); найденный дефект идёт после ответа отдельной строкой
- Срыв 5: защищаешь существующий механизм, назвав его свойство требованием задачи, — ради чего он заведён и кто его потребители, устанавливается перебором вызывающих до возражения; механизм, живущий ради обхода другой задачи, эталоном не бывает, своё прежнее решение планку поднимает

Инвариант, переживший стилман (дешевизна на горячем пути, безопасность), → guardrail у опасной точки, не повод отвергнуть лучшую организацию.
Каждое цитируемое отличие («у типа X нет фичи Y») классифицировать тестом «сохранилось бы это в дизайне с нуля?»: да → by-design, законный довод против; нет → пробел, довод за унификацию. Наличие у одного носителя паттерна не доказывает — конвенцию читать по всем соседям-аналогам; отсутствие у него того, что несут все соседи, — пробел. Установленная конвенция — тот же is: прецедент прогнать критерием, которым меряешь предложение, не проходит — называть долгом, не образцом, и правилом не записывать.
Перед категоричным «не делать / уже оптимально» — опровергающая линия (`core` «Независимая опровергающая линия»).

## Копирование прецедента

Нормативный момент возникает не только по вопросу «как лучше», но и ПРОАКТИВНО — когда сам проектируешь, КОПИРУЯ структуру прецедента (роут, форма, поток, раскладка, состав отдаваемого наружу): копирование — нормативный чекпоинт, не механическое тиражирование. Проверять ПЕРЕД репликацией:

- оптимален ли прецедент — не оптимален → выровнять к лучшему варианту ОБА (прецедент и новое), не тиражировать худший
- переносится ли обоснование формы: назвать ограничение, породившее форму у прецедента (внешний потребитель, свойство носителя), и проверить, действует ли оно на новом месте; не действует → сузить форму (private, инлайн, отдельные поля). Собственный код, чьё единственное назначение — заставить скопированную форму работать на новом месте (разборщик, адаптер, обёртка), — сигнал менять форму, не достраивать вокруг неё
- не сам ли прецедент обход у потребителя (accommodation-код над пробелом в трейте, базе, родителе) → root-fix в источник, сняв прецедент, новую копию и прочие ручные копии разом
- копируется и состав отдаваемого наружу (поля вывода, ключи ответа, схема) — каждый элемент проходит тот же чекпоинт

Точка срабатывания — момент, когда форма списывается с образца, куда бы копия ни ехала: в код, в схему хранения, в ТЗ, в вариант вопроса пользователю. Предмет шире кода: состав полей носителя, набор колонок, устройство данных.

## Образец и восстановление из git

Готовые образцы — в родительском бандле (composer.json) и в соседних бандлах того же класса.
Переписывая код либо UI с удалением старых файлов — снесённую функциональность восстанавливать самому из git-истории (`git show HEAD:<путь>`) целиком за один проход и до переписывания целевого файла.
Образец не назван, а дефект — неверное взаимодействие механик, которое в другой точке тех же данных работает → рабочий контрпример искать самому первым действием и сравнить носители битой и рабочей точки до предложений вариантов; обход (запретить действие, передать человеку) до сравнения — не вариант.

## Ссылка на админку при работе с кодом

Ссылка `/admin/...` в контексте правки кода:

1. `admin-routes`: URL по маске `path` → бандл/контроллер/имя роута детерминированно, без угадывания.
2. Read найденного контроллера/шаблона.
3. Grep — запасной путь: роут динамический или не нашёлся в каталоге.

Контроллер по ссылке не угадывать: открытый в IDE или новый в git файл с похожим именем ≠ нужный роут.

## Многофайловая правка

Код ложится по новому адресу (новый подкаталог, бандл, каталог с нуля) → покрытие сводов и спек глобами `paths` рвётся молча: до первой правки перечислить своды и спеки, чьи правила нужны этому коду, начиная с тех, чьи `paths` матчили прежнее место, и довести их `paths` до нового адреса.
При исправлении ошибок проверять все аналогичные файлы бандла; разнобой аналогичных конструкций между бандлами выравнивать по лучшему варианту. Сломан механизм → множество обхода задают его носители (типы, сущности, страницы), не сходство файлов; по каждому — свой вердикт достижимости, исход назвать перечнем носителей.

## Содержание комментария

Фиксируя правило в skill, не рассыпать его пересказ комментами по коду: максимум один короткий указатель в точке принятия решения.

Однотипный код в N местах, требующий пояснения, → сперва проверить, не снимается ли сам дубль дедупом («Дедупликация»); дедуп невозможен либо by-design (кросс-бандл, кросс-язык, симметрия ORM-сущностей) → знание в одном каноне: общий узел кода (трейт, база, интерфейс, enum, докблок), а без узла — ведущий носитель. Зеркалу коммент не нужен, когда код сам ведёт к канону; короткий указатель — только у неочевидного зеркала-ловушки (guard, риск рекурсии, неявный инвариант), указатели разные. Финальным проходом искать оставшиеся идентичные строки-комменты.

Содержание комментария (любой язык) — только ограничение либо инвариант, которого код не показывает: причина неочевидного решения, чужая система координат, скрытый контракт потребителя. Не писать: пересказ следующей строки; историю правки и переход было→стало («X убран», «теперь Y вместо Z», «раньше было») — тот же запрет у любого авторского текста-описания (`core` «Пишу текст описания или контракта»); обоснование правки ревьюеру — ему место в описании коммита. Причина-инвариант под запрет не подпадает. Плотность комментирования соседнего кода индульгенцией не является (вёрстка — skill `twig` «Комментарии в шаблонах»). Судья очевидности — будущий читатель без контекста: механику он выведет из кода; понимание, размазанное на много прыжков, — сигнал рефактора, не повод для коммента. Протухает то, что дублирует извлекаемое из кода; внекодовое стабильное (внешний контракт, чужая система координат) не протухает.
