## Объекты сцены и ссылки

- Singleton ищет ЛЮБОЙ объект на сцене, не создаёт
- Статические UI-панели — на сцене через Inspector. Динамическое создание — только повторяющиеся элементы (слоты, списки, боевой текст). `World` и `Map` — контейнеры: дочерние объекты удаляются в `Awake()` и создаются из JSON сервера
- UI-префабы (боевой текст, слоты, элементы списков) — создавать через Inspector либо MCP как `.prefab` в `Resources/Prefabs/`, не программно в коде. Ссылки — `[SerializeField]`
- Ссылки на UI и префабы — `[SerializeField]` плюс Inspector, не `Find`/`GetComponent` (кроме singleton)
- Назначенную в Inspector ссылку редактор держит по ИМЕНАМ: `[SerializeField]`-поле, класс компонента, файл этого класса. Переименование любого из трёх рвёт назначенное молча — ни компилятор, ни диагностики этого не видят. Переименовал → переназначить ссылки в сценах и префабах тем же проходом
- Потребители метода и поля живут не только в `.cs`: YAML сцен и префабов (`UnityEvent`, `[SerializeField]`), вызовы по имени строкой. Обход потребителей перед сносом мёртвого кода (правило — `code`) вести поиском ИМЕНИ по всему проекту клиента

## Контроллеры

- Контроллеры — линейная цепочка наследования; новый UI = новый контроллер, встраиваемый в цепочку; актуальный порядок — по наследованию классов, и цепочка ДВУХСОСТАВНА: верхние звенья в `Assets/Scripts/Controller/`, базовые — в `Assets/Plugins/Mmogick/Client/Controller/`; читать оба каталога, в одном цепочка обрывается. Каждый контроллер владеет своими `[SerializeField]` UI-объектами. Цепочка — ЗАЯВЛЕННАЯ конвенция слоя: единственный подкласс у звена нормален by-design, правило `code` «Дедупликация» о преждевременной абстракции при единственном подклассе сюда не применяется
- UI-объекты (тултип, менеджер боевого текста) — `[SerializeField]` на контроллере, проверка в `Awake()`, доступ через `MainController.Instance`. Не искать их singleton-поиском по сцене. Не назначен → `ConnectController.Error()`
- **Model — данные, Controller — UI**: модели сущностей не обращаются к UI-объектам и контроллерам. Все взаимодействия с UI (боевой текст, тултипы, фреймы) — в контроллерах
- MCP-тулы правки и чтения компонента видят только поля, объявленные в самом классе компонента, — `[SerializeField]`-поля предков невидимы и непатчабельны. UI-поля контроллеров объявлены в промежуточных классах цепочки → назначать поля предков через `script-execute` плюс `SerializedObject` (видит сериализованные поля всей иерархии, `ApplyModifiedProperties()` сам помечает сцену dirty); после — сохранить сцену

## Сигнал ошибки

- Нарушенный инвариант сигналить `throw` либо статическим `Error(text, ex)` цепочки контроллеров: он копит сообщение, закрывает соединение и следующим кадром цикла связи уводит игрока на экран входа с этим текстом, процесс не роняя
- `Error()` не бросает — исполнение продолжается со следующей строки, потому после вызова обязателен `return`: без него метод доезжает до конца на состоянии, которое сам признал нарушенным. Якорь: `ConnectController.Error`
- Игровой канал ошибки поднимается только из игрового РАНТАЙМА: вне игры получателя у него нет — он ищет объект сцены входа, которого там не существует. Гейт контекста — на самом канале, не у каждого вызывающего: `Awake` компонента префаба отрабатывает и при СБОРКЕ префаба редакторным скриптом, где `[SerializeField]`-поля ещё не назначены, и жалоба оттуда выбрасывает играющего на экран входа. Вынос проверки назначенности из `Awake` к точкам создания экземпляра чинит одного вызывающего, прочие компоненты с проверкой в `Awake` остаются

## Данные с сервера

- Данные с сервера — `*Recive` (`Struct/Recive/`), отправка — `*Response` (`Struct/Response/`). Именно `Recive`, не `Receive`
- Имена полей и типы C# — **как приходят с сервера**. Slug компонентов, событий, ключи JSON совпадают с серверными. Несовпадения → сверять с серверным `storage/game/`
- Модели и префабы существуют по серверным kind. Реакции на `event.name`, `eventGroup.name`, `component.name` и `entity.action` (анимации) прописаны в контроллерах и моделях; кастомные пакеты вне world (настройки игры, книга заклинаний) — по `event.code`/`component.code`. У другой игры состав иной → менять клиент
- Анимации управляются сервером через `action`, клиент переключает слой Animator. Клиентские триггеры не добавлять
- Разбор серверного payload — обязательно с `NullValueHandling.Ignore`. Сервер шлёт скаляры всегда, включая `null` (канон серверной сериализации: null ≡ дефолт поля). Без `Ignore` пишется `null` в не-nullable C#-поле и разбор падает. Проверять при каждом новом клиентском десериализаторе серверного payload
- В редакторе и dev-билде разбор серверного payload строгий (`MissingMemberHandling.Error`, ставится в `BaseController`): пришедшее с сервера поле, которого нет в C#-структуре, роняет разбор ВСЕГО пакета. Падение — сигнал отставания структуры от сервера, не дефект клиента: чинится объявлением недостающего поля. В релизной сборке проверки нет by-design
- Тип, читающий пакет ЧАСТИЧНО by-design (конверт сетевого потока со служебными полями), гасит эту проверку своими настройками разбора (`MissingMemberHandling.Ignore`) — иначе он падает на любом поле мира, которого ему знать не полагается. Гасить точечно у такого типа, проверку целиком не отключать
- Все расхождения структур с сервером за один вход в игру: временно добавить в настройки сериализатора обработчик ошибок, помечающий ошибку обработанной и копящий сообщения; после сбора списка — снять. Разбор падает на первом расхождении — без обработчика каждый прогон даёт ровно одно
- Отказ разбора «нельзя разложить JSON-массив в словарь» — серверный дефект (словарь ушёл массивом), чинить на сервере. Конвертер-обход на клиенте не добавлять. Зеркало на сервере — `serialization` «Словари с числовыми ключами»: дубль осознанный, правится парно
- Валидация команд двухслойная: клиент — UX-фильтр, заведомо невалидную команду не отправляет; сервер — истина, всё дошедшее невалидное режет, покрывая обход клиента. Клиентский фильтр ЗЕРКАЛИТ серверную валидацию: каждому серверному условию действия (серверу нужно X для действия Y) отвечает клиентский guard, не отправляющий Y при ложном X; условие без такого guard → клиент шлёт заведомо-невалидное. Симметрия сервер-валидация↔клиент-guard закладывается на ДИЗАЙНЕ фичи, тестом не ловится. Серверный рез различает исход: ожидаемая ГОНКА (рассинхрон клиент↔сервер — лаг позиции, сменившееся состояние цели) — graceful, тихий отказ без дисконнекта; жёстко, с дисконнектом — только генуинные (умышленные, контрактные) нарушения. Ни снимать клиентский фильтр («сервер разберётся»), ни смягчать серверное наказание генуинных нарушений ради клиентских багов. Якорь: `EquipmentController.SendEquip`

## Интерфейс

- Текст в мировых координатах (боевой текст, имена) — через World Space Canvas плюс UI Text, не TextMesh. Sorting через `Canvas.sortingOrder`. TextMesh (MeshRenderer) не совместим с 2D sorting pipeline
- Оформление текста интерфейса держат два носителя, руками его не задавать: роли строк (название, пояснение, значение, приглушённое, отступ заголовка блока) — `TextStyle`, контур надписи — компонент `TextOutline`: его только вешают, настроек у него нет. Толщину контура компонент держит фиксированным одним экранным пикселем и переводит в единицы объекта через `transform.lossyScale.x` — не долей кегля: холсты сжаты по-разному, а кегль надписей расходится от 15 до 110, единое число в единицах объекта под них не подобрать. Свой `Outline` или теги разметки в коде заводят два вида одного и того же — расходятся они молча, ни компилятор, ни тесты этого не ловят
- Полоска-индикатор на `Image` со степенью заполнения (`type = Filled`) требует назначенного спрайта. Без спрайта заполнение игнорируется — полоска всегда рисуется полной. Симптом «доля считается верно, полоска не двигается» — про спрайт, искать причину в расчёте бесполезно
- Окно интерфейса задаётся фиксированным размером с якорем-точкой (`anchorMin` == `anchorMax`), не растяжкой по родителю (`anchorMin` (0,0), `anchorMax` (1,1)) с отрицательным `sizeDelta`. Холст `UI` масштабируется `ScaleWithScreenSize` плюс `ScreenMatchMode.Shrink`: логическая сторона холста не превышает эталонную (`Reference Resolution`) и зависит от соотношения сторон экрана — ширина падает ниже эталона на экранах уже 16:9 (16:10, 4:3), высота — на более широких. Растянутое окно меняет размер вслед за холстом, а его содержимое (кнопки, заголовки, области списков) фиксировано — при сжатии холста оно вылезает за края либо обрезается. Признак дефекта при разборе вёрстки окна — растянутые `anchorMin`/`anchorMax` при отрицательном `sizeDelta` в сотни единиц: размер окна считается от размера экрана
- Элемент, всплывающий поверх интерфейса на время (тултип), вправе перекрывать то, что под ним: места в раскладке он не занимает, с экрана исчезает. Требования к размещению постоянных элементов на него не распространяются. Перекрытие, найденное при разборе вёрстки, — дефект только у элементов, которые на экране остаются
- `Image` сам участвует в раскладке и отдаёт предпочитаемый размер по нативному размеру своего спрайта: элемент с фоновой плашкой внутри `LayoutGroup` получает ширину ПЛАШКИ, а не своего содержимого — надписи разной длины выходят одинаково широкими, и признака в вёрстке не видно. Ширина по содержимому — только явным `LayoutElement.preferredWidth` (его приоритет в раскладке выше). Якорь: `SpellTab.Setup`
- Элемент интерфейса не берёт состояние с КАРТИНКИ другого элемента (цвет, прозрачность, спрайт как признак): источник бывает скрыт, а у выключенного объекта `Update`/`FixedUpdate` не идут — значение замирает на последнем перед скрытием. Ни компилятор, ни тесты такую связь не ловят: отражающий элемент продолжает рисовать устаревшее. Общее состояние — метод на общем предке, зовут его оба. Якорь: `MoveableObject.IsUnavailable`

## Ревью дельты клиента

Ревью уже написанного C# ведёт главная сессия инкрементально по дельте репозитория клиента (`/mnt/c/Unity/release`): протокол маркера — skill `fileagent`, маркер `.claude/workflows/client-review.last` серверного проекта с SHA репозитория КЛИЕНТА. Зона — `*.cs` СВОЕГО кода: `Assets/Scripts/**`, `Assets/Plugins/Mmogick/**`, собственные плагины автора в `Assets/Plugins/`. Вендоренная копия чужого пакета — вне ревью ЦЕЛИКОМ, единица исключения — каталог пакета с поддеревом; имя папки принадлежности не показывает, решает содержимое: свой код ссылается на типы проекта и несёт авторские README, вендорный самодостаточен как upstream-пакет. Отдельный файл на признак не проверять — авторская правка внутри вендорного каталога принадлежности каталога не меняет, обновление пакета сменой версии её затирает, и перенос правок поверх новой версии — задача клиентской разработки, не ревью. Сцены, префабы и ассеты — не предмет ревью. Порядок: канон устройства клиента (skill `unity`) → файлы дельты целиком → правила этого свода и `code` измерение за измерением → вердикт по каждой находке (`finding-verify`) до правки. Правится сразу: мёртвый код с доказанным отсутствием потребителей (обход имени по `.cs` и YAML сцен и префабов), полное имя типа при импорте в шапке, перехваченное исключение без стека в журнале при живом канале, коммент о снесённом либо прежнем поведении. Под решение пользователя: меняющее поведение либо порядок исполнения, имя `[SerializeField]`-поля, класса-компонента и его файла, находка с root-fix на сервере. После правки — диагностики компиляции (skill `unity`); правку, работоспособность которой они не показывают, проверять в Play Mode.

## Сборки и статика

- Сборку задаёт `.asmdef` своего каталога, видимость — список `references` этого файла, не расположение каталога. Сборки разделены по РОЛИ, и роль решает, куда класть новый код:
  - `Assets/Plugins/Mmogick` — платформенный клиент: базовые классы, от которых наследуется код конкретной игры. Игру не видит
  - `Assets/Scripts` — код самой игры. Ссылается на платформенную, оттого видит её
  - редакторный инструментарий — своя сборка в своём каталоге. В платформенную не класть: её наследуют все игры платформы
- Состояние и константы, нужные платформе и игре, — в платформенную сборку. Якорь: `DebugLayers`
- Тип, вешаемый на объект сцены (`MonoBehaviour` и наследники), — только в РАНТАЙМ-сборке: компонент ищется по скрипту рантайм-сборки, добавление класса из Editor-сборки возвращает пустоту. Такой тип нужен редакторному инструменту → подкаталог СВОЕЙ сборки инструмента с отдельным рантайм-`.asmdef`, файл целиком под `#if UNITY_EDITOR`; в игровой код его не выносить
- Статика переживает остановку Play Mode — перезагрузка домена при входе в игру в проекте выключена. Объекты Unity, созданные кодом в рантайме (`Sprite`, `Texture2D`, `Material` — не ассеты), при остановке уничтожаются. Следующий запуск достаёт из статического кеша уничтоженный объект: C#-ссылка на него не `null`, сам объект мёртв. Выдача из такого кеша проверяет живость Unity-оператором `!= null` и при промахе рисует заново — наличие ключа живости не означает. Промах не роняет игру, а тихо портит картинку: `Image` с уничтоженным спрайтом рисует белый прямоугольник. По симптому дефект читается как ошибка вёрстки либо цвета — искать причину там бесполезно
