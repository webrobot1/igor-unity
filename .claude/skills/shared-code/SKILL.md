> **Ведомая копия.** Источник — `/var/www/html/game/.claude/skills/shared-code/SKILL.md` в серверном репозитории; копию перезаписывает его хук при каждой правке источника. Правка копии теряется молча — вносить её в источник. Серверного репозитория нет под рукой → назвать нужную правку пользователю.

## Типы

- Ссылка на тип — импорт короткого имени в шапке файла, не полное имя с пространством имён в точке использования. Тип, импорта не требующий (встроенный, глобального пространства языка), — вне правила. Встреченный inline-прецедент — не образец для копии (shared-core «Копирование прецедента»)
- Форма возврата набора записей — по способу адресации у потребителей: адресуют по идентичности (id/slug/хеш) → словарь с этим ключом, ключ внутри значения не дублировать; только перебирают → позиционный список. Одинаковое пост-преобразование набора у двух и более потребителей (перекладка в словарь, повторный поиск по полю) → чинить форму в источнике, перекладку снять. Проверять при написании метода и при появлении второго потребителя.

## Отказ и дефолт

- Невалидный ввод, импорт, коллизия инварианта → fail-fast исключением. Запрещено «спасать» подгонкой данных под инвариант (обнулить, обрезать, отбросить, подменить), в том числе с предупреждением, и обходить негодный экземпляр ради следующего кандидата (другой донор, другая копия) — исключение называет негодный экземпляр. Best-effort с пропуском — только явное продуктовое требование
- Отказ атомарен — всё или ничего: частичное применение, меняющее корректное до ошибки состояние, хуже отказа. Принцип — атомарность (A из ACID), распространённая на эффекты вне хранилища записей — файлы, кеш, связи: файл пишется во временное место и переносится на рабочий адрес после записи в хранилище внутри той же транзакции, и откат сирот не оставляет. Сопутствующие шаги операции — инвалидация производного, синхронизация обратной стороны связей, перенос провенанса — входят в её же транзакцию, вызывающему не оставляются
- Перехваченное исключение, из которого потребителю показывают только текст сообщения (всплывающее уведомление, модалка, поле ошибки в ответе), записывать в журнал вместе со стеком. Автоматический журнал рантайма пишет лишь неперехваченные исключения — пойманное идёт мимо него, и причина остаётся видна только по тексту сообщения

### Дефолт против исключения

Требование не возвращать молча дефолт не запрещает дефолт как таковой: пустой ответ аксессора (null, false, 0, пустая коллекция) несёт один из двух смыслов, различать по тому, что значение значит для вызывающего.

| Смысл пустого ответа | Что это | Исход |
|---|---|---|
| Легитимное отсутствие | спроектированный ответ, у вызывающего есть корректная реакция: записи нет в справочнике, у действия нет своего варианта → общий fallback | дефолт оставить |
| Зависимость не готова | кеш не загружен, инициализация не отработала, метод вызван до своей предпосылки | бросить исключение |
| Данные нарушают инвариант, который держит канал записи | значение пришло мимо его проверки: файлом из репозитория, импортом, строкой старше проверки и т.п. | бросить исключение, называющее запись и её починку |

Одно и то же значение означает и отсутствие, и неготовность → это и есть маскировка (semipredicate problem): развести — исключение на «не готова», дефолт только на «отсутствие».

Признаки маскировки:

- значение приходит из ветки по полю-кешу, заполняемому один раз при инициализации либо входе
- у вызывающего нет отдельной реакции на «не готов» — он трактует дефолт как отсутствие и едет дальше (сущность без визуала, флаг тихо false)
- предпосылка гарантирована порядком инициализации → дефолт-от-неготовности в норме недостижим, значит его появление есть баг, обязанный падать

Признаки легитимного дефолта:

- try-семантика поиска, где «не найдено» — обрабатываемое состояние
- состояние «не готов» невозможно (валидируется у источника на входе) либо у вызывающего есть fallback именно на этот дефолт, а не «поехали дальше»

По признакам непонятно → не угадывать дефолтом: прочитать вызывающие места и порядок инициализации.

## Огораживание ввода

Перечислимое либо справочное значение во вводе любого канала (схема параметров вызова, запрос API, выпадающий список формы, команда протокола и т.п.) — огораживать: точный выбор из достоверного источника (перечень, который отдаёт сам канал, справочник и т.п.) плюс проверка против него до обработки, не произвольный текст. Идентификатор цели действия → параметр пути (path) либо обязательная ссылка на перечень; фильтр либо опция → параметр запроса (query). Исключение — поле, которому нужна свобода (код, данные, произвольная полезная нагрузка и т.п.): документировать явно. Принцип — allowlist-проверка ввода (OWASP).

Запись частична (непереданное сохраняет прежнее значение) → проверка входа считает итоговое состояние (присланное поверх текущего), не присланный фрагмент.

Проверяемое по одному лишь входу (диапазон, форма значения, сочетание параметров) стоит первым блоком операции, до первого обращения к носителю данных; требующее данных — сразу за их получением: частный случай раздела «Место проверки условия» ниже. Принцип — fail-fast.

## Запрещённое действие — не молчать

Действие без легитимного исхода (дубль; повтор операции, для чьих целей есть иные инструменты — обновить, сбросить) → `throw` либо guard на входе (fail-fast), не молчаливый возврат существующего и не no-op. Внутренний потребитель, которому нужен существующий объект, ищет его явно, не через создающую операцию (разделение команды и запроса — CQS, Мейер).
Отсутствие исхода у действия («делать нечего») устанавливается по всем эффектам действия, прочитанным в его коде; предпросмотр, отчёт и иной носитель части эффектов этого признака не дают.

## Боевой потребитель новой возможности

Заводя в продукт новую возможность (инструмент, параметр, поле, контрол, метод и т.п.), назвать её потребителя вне тестирования — пользователя продукта, внешнюю систему, соседний механизм и т.п. — и его задачу. Не называется → не заводить: облегчение собственной проверки и прогона проверок потребителем не является, нужду прогона закрывать существующими каналами либо разовым артефактом. Без чего канал не отдаёт данные никому (срез ответа под лимит вывода) — свойство канала, заводится без потребителя; фильтр под конкретный вопрос — возможность.
Существующая возможность проходит тот же тест: потребитель не называется → снятие; «не мешает» и цена снятия доводом оставить не служат.
Ветка приёма второй формы значения (второй вид входа, второе состояние данных) проходит тот же тест со стороны производителя: назвать свой канал записи, фактически создающий такую форму (форма, программный интерфейс, выгрузка, импорт и т.п.), перебрав каналы целиком. Ни один не создаёт → ветку не заводить, форма отбивается отказом по контракту текущей формы («Анализ и рефакторинг»); принимать ли её — правило продукта (`shared-core` «Правило продукта — решение пользователя»).
Принцип — YAGNI; расхождение — прогон проверок потребителем не считается, и тест проходит заведённая возможность, не только новая. Правило о ветке приёма второй формы идёт против закона Постела («принимай либерально»).

## Механизм-сокращение существующего пути

Механизм, чей единственный вклад — сократить либо переставить шаги уже существующего пути к тому же результату, не заводится. Оправдывает его только исход, недостижимый существующим путём: назвать, что без него теряется либо остаётся недостижимым. Удобство, скорость и меньшее число шагов таким исходом не бывают. Работающий механизм проверяется тем же вопросом, когда правка добавляет ему код (починка его дефекта, распространение на новый носитель и т.п.). При копировании механизма на новый носитель этот вопрос идёт до чек-листа «Копирование прецедента». Принцип — Minimal Interface (Фаулер); расхождение — правило накрывает любой механизм, не только методы класса.
Названный потребитель («Боевой потребитель новой возможности» выше) теста не закрывает: там — кому механизм нужен, тут — что он даёт сверх существующего пути.
Механизм заводится у точки входа (интерфейс человека, программный интерфейс и т.п.) → существующий путь проходит только через эту же точку входа, без внешней программы (правка выгруженной копии и т.п.). Результат механизма, недостижимый через его точку входа и достижимый через другую точку входа, — «Расхождение точек входа одной операции» ниже.

## Точка вариативности без исполнителя второй стороны

Точка вариативности — порт с реализацией по умолчанию, интерфейс и его реализация, флаг либо параметр, ветка под конфигурацию, режим вывода, необязательное удобство подачи и т.п. — существует, пока её вторую сторону исполняет наблюдаемое: вторая реализация в коде, конфигурация развёртывания (состав модулей), тест либо иная автоматическая проверка, проходящая второй стороной (другое значение, конфигурация без модуля), названный потребитель удобства; записанная конвенция и план исполнителем не являются. Исполнителя нет → завести проверку либо снять точку; кто выбирает между ними — `shared-core` «Root-fix у источника». Удобство подачи (фильтр, сводка, отметка, подсказка, подпись и т.п.) даётся всем потребителям пула одним общим механизмом либо не даётся никому; пул — потребители, к которым удобство применимо (разделы, страницы, типы и т.п.). Какой исход у удобства получает рекомендацию — `shared-orchestration` «Манера общения». Решение оставить точку без исполнителя записывается у самой точки вместе с условием её снятия (причина неочевидного решения — «Содержание комментария»); до наступления условия точка правилом не трогается.
Заводя параметр, назвать вызывающего, передающего другое значение; все передают одно значение из одного источника → единица читает источник сама, параметра не заводят (Replace Parameter with Query, Фаулер). Источник вне объявленных зависимостей единицы → параметр остаётся: чтение источника телом завело бы связь, которой не разрешает «Размещение кода по принадлежности» (Replace Query with Parameter, Фаулер).
Принцип — YAGNI, у Фаулера speculative generality; расхождение одно: исполнителем второй стороны признаётся и конфигурация развёртывания, и автоматическая проверка, не только второй вызывающий в коде. Тот же тест в момент заведения — «Боевой потребитель новой возможности» выше; иерархия с единственным подклассом — частный вид точки («Дедупликация»); «Дополнение под одного потребителя» — потребитель один, тут второй стороны нет ни у кого; ветка на состоянии данных, которого не создаёт ни один канал записи, — мёртвая, снос без развилки (`shared-core` «Root-fix у источника»).

## Охват механики по носителям и каналам

Механика заводится у одного носителя, её класс пополняется новым либо о механике одного носителя выносится вердикт (нужна ли, верно ли устроена и т.п.) → назвать класс носителей по свойству, ради которого она заведена (не по имени типа либо каталогу), и провести её по классу целиком; у каждого носителя — по всем каналам к нему, включая каналы через его части (форма, программный интерфейс, импорт, обработчик в клиенте, запуск по расписанию и т.п.). Канал, механики не получивший, отказа не даёт. Носитель либо канал остаётся без механики только по решению пользователя (`shared-core` «Правило продукта — решение пользователя»); запись решения о канале — «Расхождение точек входа одной операции» ниже.

## Расхождение точек входа одной операции

Несколько точек входа (интерфейс человека, программный интерфейс, консольная команда и т.п.) дают доступ к одному предмету — набору записей, процессу и т.п. → на каждой точке входа одинаковы наличие операции над этим предметом и состав перечня его записей: что входит в перечень, чем он разбит, что скрыто. Операция есть на точке входа, если её результат достижим путём из операций этой же точки входа, без внешней программы. Принцип — Minimal Interface (Фаулер), общий с «Механизм-сокращение существующего пути» выше: там путь к тому же результату решает, заводить ли механизм, тут — есть ли операция на точке входа. Расхождение законно только решением пользователя (`shared-core` «Правило продукта — решение пользователя»). Решение записывается комментарием у точки расхождения: дата, что расходится, причина. Решение о целом классе расхождений записывается правилом проекта, точки класса своего комментария не требуют. Расхождение без записи — дефект: наличие операции и состав выравниваются к точке входа, верной по правилу продукта. Подача в модальности своего потребителя (картинка против чисел и т.п.) расхождением не является. Приём — запись архитектурного решения (ADR, Найгард); расхождение с каноном — решение об одной точке записывается комментарием у кода, не отдельным документом.

## Множество потребителей внешнего канала

Проектируя выдачу либо приём на канале, доступном извне (эндпоинт клиента, публичный роут, внешний API), множество потребителей считать по тому, что канал допускает, не по тому, как ходит свой клиент. Границу выдачи задаёт проверка на самом канале, у каждой точки входа своя: отбор у перечисляющей операции границей для выдачи по прямому идентификатору не служит. Принцип — complete mediation (Зальцер и Шрёдер); выдача по прямому идентификатору без своей проверки — уязвимость IDOR (OWASP).

## Ограничение модели — по названному вреду

Вводя в модель ограничение (запрет, уникальность, взаимоисключение), назвать вред от его отсутствия — что сломается, у кого, при каком действии — и подтвердить фактом тем же проходом; не подтверждается → ограничение снять. Отказ ограничения снимается действием → сценарий вреда довести до исхода через это действие: вред после действия не наступил — ограничение его предотвращает; наступил — не предотвращает. Существующее ограничение, взятое доводом за решение, проходит ту же проверку. Отсутствие сценария использования, стройность модели и симметрия вредом не являются.
Ограничение есть гейт доступа к данным → обойти остальные каналы, отдающие те же данные: сосед отдаёт копию без условий → гейта нет; сосед сужает выдачу критерием → копия держит тот же критерий; производное представление, по которому исходного не восстановить, копией не является. Принцип — complete mediation (Зальцер и Шрёдер), общий с разделом «Множество потребителей внешнего канала» выше: там проверку несёт каждая точка входа канала, тут гейт держат все каналы, отдающие те же данные.
Гейт точки входа (роут, эндпоинт, тул) строится на своих данных — принадлежности записи, её критерии видимости, собственном праве роута; вызов проверки доступа к посторонней точке входа гейтом не является. Точка входа той же операции, чья связь с этой объявлена (программный вызов и страница одного действия и т.п.), посторонней не является. Отдаётся производное представление → гейта нет вовсе.

## Место правки на маршруте данных

У значения есть маршрут (вычислитель → сборка пакета → канал доставки), правка законна на каждом звене. До правки пройти маршрут и назвать проходы, которые по этим данным уже идут: правка ложится туда, где нужный признак уже вычислен. Признаки чужой точки: под правку заводится свой цикл; повторно добывается то, что соседний проход уже держит; цена растёт с частотой прохода (каждый кадр, каждая запись). Принцип — Information Expert (GRASP); расхождение — эксперт ищется среди проходов маршрута, не среди классов.

## Место проверки условия

Условие проверяется в самой ранней точке, где его входы уже есть; позже стоит лишь условие, чьи входы появляются только там (результат создания, ответ вызова, значение живого объекта). Условия одного решения разводить по своим точкам, не писать одним блоком у позднейшего. Отбор, порядок, лимит и агрегат, чьи входы известны при сборке набора, входят в саму сборку. Принцип — fail-fast, распространённый с отказа на любое условие решения; признак отбора в фильтре сборки — predicate pushdown; расхождение — порядок, лимит и агрегат идут в сборку наравне с отбором.
Участник общего события либо конвейера (обработчик события страницы, слушатель событий фреймворка, промежуточный слой и т.п.) читает свой вход в точке, заданной явно относительно эффектов соседних участников на этот вход (прокрутки, перерисовки, правки записи либо запроса и т.п.) — до них либо после, как требует его задача: фазой, приоритетом либо порядком вызова. Порядок регистрации такой точкой не является. Соседей и их эффекты на вход перечислить до написания своего участника.

## Число обращений к хранилищу

Операция над набором записей, растущим с данными, берёт их наименьшим числом обращений к хранилищу: связанные записи набора — одним обращением на весь набор; наличие либо счёт набора — из результата его же выборки; запись набора — одной массовой операцией хранилища. Запись по элементу законна, когда отказ одного элемента не должен отменять соседние. Массовая запись минует обработчики записи одного элемента: их эффект вызывается явно тем же проходом либо у записи названа причина обойтись без него. Принцип — Chatty I/O, частный случай — N+1; расхождение: правило накрывает только хранилище, разрешает запись по элементу при независимом отказе и добавляет эффект обработчиков.

## Необратимый шаг во внешней системе

Шаг операции необратим (заливка файла, публикация, отправка в чужой репозиторий, заведение сущности у стороннего сервиса), за ним идут ещё шаги → его исход сохранить в своей записи немедленно, до следующих шагов. Иначе отказ следующего шага оставляет запись без исхода: повтор делает необратимое заново — во внешней системе копятся дубли. Фиксируется ровно состоявшееся, не итоговое состояние операции: по нему повтор доводит оставшиеся шаги, необратимую часть не трогая. Условия отказа проверяются до необратимого шага («Место проверки условия»). Шаг, способный отказать, ставится до необратимого наравне с условиями отказа — и тот, что проверяет, и тот, что действует. После необратимого шага остаются лишь шаги, которые раньше невыполнимы. Откат эффекта возможен → атомарный отказ вместо фиксации («Отказ и дефолт»). Схема — сага с поворотной транзакцией (pivot transaction) на необратимом шаге; расхождение — компенсирующих транзакций нет: обратимый эффект уходит в атомарный отказ.

## Решение — там, где есть контекст

Код выбирает представителя из равноправных входов (первый, минимальный, «любой из»), и выбор меняет исход → решение принимается не на своём месте: перенести туда, где контекст однозначен (Information Expert, GRASP). Замена эвристики выбора дефекта не снимает. Недостающий контекст — воля человека → выбор делает он, значение приходит параметром действия; действие, привязанное побочным к другому, отнимает и возможность не действовать. Перенос выбора к человеку меняет правило продукта → `shared-core` «Правило продукта — решение пользователя».

## Переопределение с вкладом родителя

Переопределяя метод-носитель вклада родителя/примеси (вклад в результат/побочный эффект/мета/инициализацию) — осознанно: либо вызвать родительский вклад (`parent::`/`base.`/`super.`), либо полностью заместить; молчаливый дроп вклада — баг, не выбор. Кросс-доменно: PHP trait/parent, C# `base.`, JS `super.`, mixins/middleware/декораторы, переопределённые методы жизненного цикла фреймворка (инициализация, включение, выключение) без вызова базового. Ситуация — запах Call Super (Фаулер); расхождение — канон снимает обязанность вызова шаблонным методом в базе, правило ведёт место переопределения.

## Оповещение о смене состояния

Состояние ведёт один компонент, читают несколько → при появлении второго читателя перечислить все пути смены (контрол человека, вызов api, фильтр, восстановление сохранённого, начальная установка) и провести каждый через объявленный канал оповещения, поднимаемый в точке, общей всем путям (Observer, GoF). Канал, объявленный словами в комменте, механикой не обеспечен — сверять по коду, поднимающему событие.

## Свежесть производного артефакта

Годность копии производного (ответ по условному запросу, файловый кеш и т.п.) решает отметка свежести — отпечаток входов, снятый до начала сборки и лежащий рядом с копией (`ETag`, файл отметки и т.п.): копия годна, пока отпечаток равен нынешнему. Время файла против даты записи-источника годности не решает: точность часов файла и конец сборки позже её входов оставляют копию свежей после правки в ту же единицу времени либо по ходу сборки. Момент сборки — лишь версия самой копии для адреса и ответа «не изменилось». Принцип — verifying trace («Build Systems à la Carte», Мохов, Митчелл, Пейтон Джонс); тот же дефект у git зовётся racy git. Отметка мерит только свой источник: перед записью значения в производный артефакт назвать источник отметки и все входы значения; вход вне источника (формат сериализации, внешнее состояние) → значение вычислять при выдаче либо втянуть вход в отметку. Изменяемый состав полей либо формат держать на отпечатке — метка версии схемы плюс данные; голая дата метки не несёт. Правя формат, снять существующие копии тем же проходом, включая их запись в отдельно лежащей отметке (реестр, манифест). Формат разбирает чужая сторона → метку версии формата держит она.

Чтение производного значения либо сериализация агрегата сразу после его мутации в том же запросе идёт через мемо и кеши, которые мутация сама не сбрасывает, — снимок может врать. Ответ мутирующей операции не собирается сериализацией мутированного объекта (разделение команды и запроса — CQS, Мейер): свежее состояние отдаёт чтение следующим запросом. Снимок нужен в том же запросе → сбросить мемо у его владельца либо перечитать источник; «только что записал — прочитаю верно» — ложная посылка при любом мемо между записью и чтением.

## Content-addressable идентичность

Идентификатор записи по содержимому — хеш байтов файла в той форме, в которой запись его хранит и отдаёт наружу: хеш воспроизводим из файла любым инструментом, декодированное содержимое зависит от декодера. Форму задаёт потребитель файла: байты, обязанные вернуться наружу теми же (выгрузка в репозиторий и т.п.), хранятся как приняты; файл, который приложение производит либо приводит к своей форме само (перекодировка, нарезка, пересборка кодировщиком и т.п.), хранится без отметок кодировщика — тот пишет в контейнер время записи, и то же содержимое давало бы при каждом сохранении новый хеш, новую запись и каскад её пересоздания. Одно содержимое приходит разными файлами (пересохранённая картинка, другой контейнер звука и т.п.), и продукт считает его одной записью (правило продукта — `shared-core` «Правило продукта — решение пользователя») → запись находится в точке приёма сверкой декодированного содержимого; идентификатор и файл остаются у первой принятой. Принцип — content-addressable storage; расхождение — равенство содержимого сверх равенства байтов даёт сверка при приёме, в идентификатор оно не входит.

## Ожидание чужого времени в сборке ответа

Вызов, ждущий сторону, чьё время нам не подконтрольно, — поход по сети к чужому серверу, запуск чужого процесса, обращение к стороннему сервису, — в сборку ответа, которого ждёт его получатель, не ставить, когда он кратен числу записей выдачи. Три признака нужны вместе:

- Чьё время ждём. Ось — время, не граница, за которую уходит вызов: обращение к соседнему модулю и запрос фронта к своему же бэку читаются «внешними», правилом не покрыты — тот же процесс либо та же машина, время предсказуемо; число запросов к своей базе, кратное числу записей выдачи, — проблема N+1 запросов, не этот предмет («Число обращений к хранилищу» выше); свой расчёт по содержимому — «Свой расчёт в сборке ответа» ниже
- Кратность числу записей выдачи — вызов на строку списка. Одиночный такой вызов на странице одной записи не запрещён
- Место — внутри формирования ответа. Ответ ушёл получателю → тот же вызов законен, и в нём лечение: запрещена сборка ответа, не показ значения вообще

Ограничитель (не больше N вызовов на запрос, порог свежести у записи) решением не является: ответ несёт N ожиданий подряд, а выдача остаётся неактуальной — обновлены N записей из показанных. Записей больше, чем успевает опросить один запрос → просроченные находятся всегда, и оба дефекта держатся разом.

Свежесть ведёт канал мимо сборки ответа: до-опрос из браузера после отрисовки по показанным записям плюс обход по расписанию; сборка ответа читает только сохранённую отметку (схема stale-while-revalidate).

## Свой расчёт в сборке ответа

Расчёт по содержимому файла либо графа связанных записей, повторяемый на каждой сборке ответа и кратный числу записей выдачи, ведётся в точке смены исходных данных, результат хранится в записи (materialized view). Сборка ответа читает сохранённое. Кеш в пределах запроса решением не является. Агрегат связанных записей, который хранилище считает тем же запросом выдачи (подзапрос, группировка и т.п.), своим расчётом не является: хранимым значением он становится, когда замер времени выдачи называет этот запрос её главной статьёй. Расхождение с materialized view — агрегат запроса хранится только по замеру. Ось — своё время; чужое держит «Ожидание чужого времени в сборке ответа» выше.

## Канал проверки состояния среды

Состояние среды, читаемое рантаймом языка либо ядром напрямую (жив ли процесс, есть ли файл, занят ли порт), читается ими, не запуском внешней утилиты с разбором её вывода. Утилиты в образе может не быть вовсе, и её отсутствие приходит пустым выводом — тем же, каким приходит отрицательный ответ: решение строится на ложном «нет». Сигнала об отказе не возникает нигде — код возврата теряется в разборе, пустой вывод разбирается штатно, — и следствия расходятся веером, каждое со штатным видом.
Внешняя программа, делающая работу, невыразимую своими средствами, под правило не подпадает; своих средств для состояния нет → присутствие программы проверять отдельно, её отказ разводить с отрицательным ответом и отдавать отказом операции.

## Анализ и рефакторинг

- Вердикт статического анализа («условие всегда истинно», «проверка избыточна», «ветка недостижима», «метода не существует») — гипотеза его модели, не факт: снимать проверку либо сужать объявление — только назвав, на чём вердикт держится, и исключив живой случай (окно до инициализации, запись по вычисляемому индексу, переключатель, меняемый вне прогона анализа). Проверка живая, неверна модель → код оставить, сообщение гасить в конфиге анализатора либо игнорировать; подгонка кода под модель запрещена
- Кандидат на мёртвый код (метод, обработчик, ветка после рефактора) → обойти все потребители и пути вызова; подтвердилось лишним → удалить самому без запроса разрешения, если содержимое восстановимо из истории либо индекса (`git ls-files --error-unmatch <путь>`, `git show HEAD:<путь>`, `git show :<путь>`). Неотслеживаемый файл, носитель под игнором git и код вне репозитория стираются невозвратно — их снос под гейтом-через-подтверждение (skill `implement-workflow-gates`). Тем же проходом править комментарии-ссылки на удалённое. Приём — Remove Dead Code (Фаулер)
- Видимость члена выбирает его фактический потребитель при написании: только изнутри класса → закрытый, только наследники → защищённый; открытый без вызывающих снаружи → сузить либо инлайнить («Дедупликация»); видимость задана контрактом надкласса либо интерфейса → решать в контракте. Принцип — минимальная доступность членов (Блох, Effective Java)
- Свой код сменил форму — данных, контракта между своими сторонами либо пути к исходу — → переход одним проходом, без parallel change: все копии прежней формы приводятся к текущей тем же проходом (шаг под гейтом идёт предложением пользователю, недосягаемая копия называется пользователю до правки), код и тексты знают только текущую форму. Отказ на негодном входе — по контракту текущей формы, не по узнаванию прежней. Чужую форму знает лишь точка приёма, переводящая её в свою; форма, которую свой канал создаёт сейчас, прежней не является.
- Правка, обязанная сохранить поведение (сведение копий, вынос, перенос), чей вклад доходит до байтов выпускаемого документа (выгрузка, экспорт, ответ), принимается по методу Golden Master (характеризующий тест); расхождение с каноном — входы подбирать так, чтобы каждый сведённый экземпляр исполнился.

## Единый источник истины

Кодовая проекция `shared-core` «Одно знание — один носитель» (DRY). Повторяющийся литерал/значение/конфиг/логика — не копировать: один источник (класс констант, enum, конфиг модуля-владельца, общий сервис/база/трейт). Ссылаться по имени (`Enum::Case->value`), не строкой. Копия устаревает молча — источник уехал, копия соврала. Механика выноса — «Дедупликация» ниже; перечни enum/числа/имена в skill и доке — skill `shared-skill-rules` / `shared-doc`.

Перечисление заводится под множество с редко меняющимся составом, чьи значения адресует код ссылкой. Множество, пополняемое файлами либо записями данных, адресуется строкой; разрешимость строки проверяется в точке обращения.

Значение, которое меняет автор установки, а не код, — текст бренда, промт генерации, предел установки и т.п., — объявляется переменной окружения модуля-владельца; константа держит значение, меняющееся только вместе с читающим его кодом. Принцип — «Config» из The Twelve-Factor App.

Сторонний пакет, утилита либо сервер принимает значение только своей формой — файлом настроек, форматом и т.п.: эта форма вторым носителем значения не становится. Значение остаётся в одном источнике: собственный код читает его оттуда, а форму собирает из него при запуске потребителя. Та же форма служит потребителю ещё и кешем производного (короткоживущий токен, скомпилированное состояние) → форма переживает запуск, пока её значение совпадает с источником; разошлось — форма пересобирается, производное потребитель добирает сам.

Один наблюдаемый исход строят несколько независимых исполнителей (разные контуры, языки, процессы) — едино правило исхода, не код: копия реализации тут неизбежна, потому расхождение исходов есть дефект, а не свойство контура. Правя одного исполнителя, назвать остальных и привести тем же проходом; направление выравнивания задаёт тот, чей исход верен по правилу продукта, своего правила ни один исполнитель не заводит. Приёмку выравнивания закрывает сверка каналов наблюдения между собой — `shared-artifact-check` «Верификация артефактом».

Денормализованная проекция (кэш ради фильтра, листинга, скорости) легитимна, но верна лишь пере-вычисляемой из источника при каждой его записи (синхронизация, сохранение агрегата и т.п.); носитель выбирать по изменчивости источника: стабильная мета вмораживание переживает, изменчивый признак пересчитывается при каждой записи источника. Долговечность носителя состояния мерится сроком жизни объекта-хозяина: назвать событие, при котором носитель теряет состояние; хозяин его не переживает → потеря состояния норма, более долговечного носителя не заводить.

Значение, общее нескольким потребителям и меняющееся независимо от них, хранится у своего владельца — единицы, которой оно принадлежит, — и читается потребителями оттуда. Копия, оставленная у потребителя, годна по отметке владельца («Свежесть производного артефакта» выше).

Довод «вторая копия знания» вопроса о месте знания не решает: сперва называется владелец — тот, чьё знание, — и только потом снимается копия у остальных. Нынешнее место хранения владельца не называет.

Свойство едет потребителю каналом своего носителя, не справочником обо всех элементах класса внутри чужой сущности; довод «канал носителя такого не возит» — задача расширить канал. Довод об экономии строится по всем точкам, где значение материализуется (запись справочника, копия в каждом экземпляре рантайма, отправка соседнему процессу), перечисленным до вердикта.

Подготовленный срез данных (файловый кеш, экспорт, снимок), собранный модификаторами, читают из артефакта, не из первоисточника: чтение сырого состояния повторяет у себя каждый модификатор и расходится со сборкой; запись идёт в первоисточник; нужного поля в артефакте нет → дополнить сборку.

Существующая ручная копия (в прецеденте, во фреймворке) — не довод сохранить дублирование при возможном общем источнике: вынести и переписать все копии разом, включая образец.

Заведение общего носителя (база, трейт, общий сервис, функция) — точка обхода всего проекта: носители выносимого механизма искать по тому, что код физически делает (значение-константа, литерал, вызов), не по имени, каталогу либо модулю; носитель, написанный тем же заходом, подключается к базе, а не пишется рядом. Копия, к базе не подключённая, застывает на поведении до выноса.

Под новое состояние либо нужду заводится элемент (поле, флаг, контрол, показ числа либо метки и т.п.) → сперва назвать существующий элемент, который несёт тот же факт либо от нового состояния стал неверен. Такой элемент расширяется либо пересчитывается. Второй элемент рядом заводится, лишь когда назван вход, при котором он обязан разойтись с существующим; иначе существующий дублируется либо остаётся неверным. Частные случаи:

- состояние рантайма: заводя поле-флаг, проверить, не выражено ли состояние наблюдаемым свойством объекта (активность, видимость, режим и т.п.) либо значением-источником (настройка, поле сущности, ответ сервера и т.п.)
- хранимое поле записи: заводя колонку, json-поле либо свойство внутри выгружаемого файла, назвать уже хранимые данные, из которых значение выводится (дочерние записи, соседние поля, файл вне базы и т.п.), затем вход, при котором поле обязано с ними разойтись; входа нет → поле производное: не хранить, вычислять при чтении. Хранить его без такого входа законно лишь денормализованной проекцией (выше в этом разделе; повод хранить ради цены расчёта — «Свой расчёт в сборке ответа»): вводом она не заполняется — поля ввода ни в форме, ни в писчем наборе программного интерфейса у неё нет. У существующего поля тот же тест ставится, когда один факт читается с разных носителей: код — с поля, страница — с дочерних записей, фильтр базы — с поля
- контрол интерфейса: одно действие пользователя несёт один контрол; заводя контрол, искать существующий того же действия по всему рендеру страницы (панель, вкладка, колонка, базовый шаблон и т.п.); различие семантики эффектов — не вход, при котором контролы обязаны разойтись: эффекты складываются на одном контроле. Действие над элементами набора, который страница уже выводит перечнем (таблица, список, дерево и т.п.), встаёт контролом в строки этого перечня — и при заведении контрола, и при переделке существующего
- пометка у декларации (ключ объявления операции, флаг конфигурации, аннотация и т.п.): заводя её, назвать уже объявленную связь предмета декларации с носителем, держащим тот же факт (ссылка на раздел, родитель в иерархии, внешний ключ записи и т.п.); связь есть → значение выводится из неё, своя пометка не заводится; связь стоит лишь у части предметов → довести её до всех

Обязанность носителей разойтись — в тестах этого раздела и в «Ось понятия и вывод из неё» — задаёт их потребитель: на названном входе ему нужен ответ именно этого носителя, не второго; расхождение, на котором потребитель получает ложный ответ, обязанности не доказывает.

Имя ключа в структуре-возврате называет источник одним именем для всех потребителей; переименование ключей у потребителя (перекладка один-в-один при сборке ответа) заводит второй словарь — лечить переименованием в источнике. Выбор контейнера — «Типы» выше.

## Приведение состава к эталону

Операция, приводящая состав записей к эталону (версия источника, родительская версия, присланный файл и т.п.), сохраняет записи, которые эталон несёт: идентификаторы и связи у них остаются, содержимое приводится к эталону. Снимаются только записи, которых эталон не несёт. Снос состава с повторной сборкой из эталона приведением не является.
Запись, которой эталон не несёт, а строку держат ссылки других записей, снимается формой, которую выбирает потребитель ссылки: мягким удалением либо отсутствием.

## Размещение кода по принадлежности

Код ложится в модуль по принадлежности — причине своего появления и вызывающей стороне. Объявленная зависимость даёт право использовать чужой модуль, не держать у себя код чужой принадлежности.
Дописывая в общий механизм нескольких вариантов (типов контента, форматов файла, платёжных провайдеров и т.п.) знание одного варианта — его формат, правило, ветку по его признаку и т.п., — сперва назвать точку, где механизм уже расходится по вариантам (реестр стратегий, интерфейс с реализацией у каждого варианта, переопределяемый метод и т.п.): знание ложится в реализацию варианта, общему механизму остаётся вызов этой точки. Точки нет → форма знания варианта — «Дедупликация» ниже. Правило действует и при дописке в существующий класс, не только при выборе модуля под новый. Принцип — открытость/закрытость (OCP) через Strategy либо Template Method (GoF); расхождение — правило о месте знания, не запрет правки общего кода.
Принадлежность данных (поля, связи, значения) называет замер: чей код содержательно манипулирует значением — создаёт, меняет, валидирует само значение. Читающий, показывающий, ведущий ссылкой и применяющий значение к чужому предмету (проверка по перечню, исполнение по настройке) владельцем не становится, как и форма, которой он значение получает; служебное касание (синхронизация обратной стороны связи, делегирующий вызов) исключается. Перестройка структуры принадлежности не меняет. Второй довод того же веса — чем держится инвариант связи: инвариант заполненности («ровно одно из двух», «одно требует другого») табличное условие базы выражает только на колонках одной строки, отдельная таблица-связка его не даёт.
Код, общий нескольким потребителям, → вниз, в модуль, от которого каждый потребитель зависит напрямую. Прямое использование чужого модуля объявляется зависимостью самого потребителя; косвенная достижимость через посредника объявлением не является. Объявленная зависимость — вход этого правила: новая сдвигает модуль-приёмник общего кода, размещение перепроверяется. Цикл зависимостей снимается выносом общего вниз; «получится цикл» доводом против верного размещения не служит. Основа — пакетные принципы Мартина: общей закрытости (CCP), ацикличных зависимостей (ADP), устойчивых зависимостей (SDP).
Текст читающего запроса к хранилищу живёт у корневой сущности, которую запрос читает, — в её репозитории (Repository, Фаулер), не у потребителя результата; объём запроса, глубина соединений и число потребителей места не меняют. Запрос, чья корневая сущность вычисляется во время исполнения, остаётся у потребителя: статического корня у него нет. Штатное чтение без своего текста запроса — по идентификатору, по значениям полей, по критерию — зовётся прямо у потребителя, репозитория под него не заводят.

## Дедупликация

Порядок решения: сперва слой — чем логика является и куда принадлежит («Размещение кода по принадлежности» выше), — затем внутри разрешённого слоя форма (порог метода, порог класса, инлайн, обёртка). Приёмником инлайна служит потребитель, чей слой такую логику принимает; слой, чей состав ограничен записанным правилом проекта, приёмником не бывает.

- Перед созданием класса, перечисления либо метода — проверить существующие на совместимость (аргументы, домен): совместимо → расширить существующий, в том числе его сигнатуру; несовместимо → своя единица
- Методы с почти одинаковым телом → один метод, различие — аргументом (Parameterize Function, Фаулер). Различие, сведённое к одному значению либо наличию/отсутствию одного элемента результата (ключ в возвращаемой структуре) и заданное типом либо перечислением, → ветка внутри метода, не выносить в переопределение, отдельный метод либо класс: одно значение отдельной единицы не требует. Различаются тела веток, не одно значение → переопределение законно (Replace Conditional with Polymorphism; делать осознанно — «Переопределение с вкладом родителя» выше). Малое различие, всплывшее в уже схлопнутом методе, → добавить ветку, не разъединять обратно — преждевременная абстракция
- Общая единица отбора для нескольких потребителей (обход записей, фильтр набора и т.п.) → до выноса сверить отбор каждого; у потребителя с другим отбором он остаётся свой. Иначе общий отбор молча меняет его исход
- Тело единицы распалось на блоки, не делящие между собой ни данных, ни исхода, → делить по этим блокам. Объём тела и число его строк основанием деления не служат. Принцип — высокая связность (cohesion)
- Дедуп не откладывается, вопреки правилу трёх (Робертс, у Фаулера): второй почти-идентичный метод — точка немедленного схлопывания; ярлык «тривиальная обёртка / потом» копию не оправдывает — тривиальность задаёт форму дедупа (инлайн), не право отложить
- Метод с единственным вызовом — инлайнить (Inline Function, Фаулер), даже если «красиво выделен»: расхождение с каноном — критерий не ясность тела против имени, а число вызовов и объём. Отдельный метод оправдан только при >15 строк со своей ветвистой логикой или если вызывается из ≥2 мест или рекурсивный. Цепочки крупных одноразовых методов (A→B→C) — тоже инлайнить
- Гард/предусловие без возвращаемого значения (валидирует и бросает, вызывающему ничего не отдаёт) — инлайнить в защищаемую операцию даже при >15 ветвистых строк: допуск «>15 ветвистых строк → метод» только для значение-возвращающих под-билдеров (`build*`/`compute*` → данные, что вызывающий вставляет в результат; имя документирует фрагмент вывода). Гард — интринсивное предусловие одного вызывающего, не переиспользуемая единица: имя прячет гейт за индирекцией, держать видимым в начале операции; отдельным методом оправдан лишь при ≥2 вызывающих. Различитель — не «проверка ли это», а возвращает ли потребляемое значение: предикат `isX`, по которому вызывающий ветвится, — значение-метод (правило не про него); `assertX`, который бросает, — гард
- Порог отдельного класса в своём файле выше порога метода: класс, чей публичный интерфейс зовут из одного файла-потребителя, схлопывается в него методом (Inline Class, Фаулер); расхождение с каноном — критерий не малая нагрузка класса, а один потребитель. Класс оставляют по названному основанию: ≥2 потребителя; точка расширения по конвенции слоя, записанной правилом проекта, при исполнителе второй стороны («Точка вариативности без исполнителя второй стороны»); звено цепочки наследования, объявленной конвенцией слоя в записанном правиле проекта (граница — буллет о единственном подклассе ниже); граница между процессами либо раздельно развёртываемыми модулями — раздельность развёртывания подтверждает конфигурация развёртывания каждой роли, не план и не комментарий. Вынос ради единообразия решает пользователь (`shared-orchestration`)
- «Этим владеет только наследник-владелец зоны либо сегмента» класса не оправдывает: у довода нет дна — класс на каждый сегмент пути вверх. Выносится корень, реально общий двум и более местам, не каждый промежуточный сегмент
- Прокси/обёртку не плодить — звать целевой напрямую: запах Middle Man, лечение Remove Middle Man (Фаулер); расхождение с каноном — судится каждая обёртка по своему телу, не доля делегирующих методов класса. Чистый форвард (в другой метод либо в источник значения — переменную окружения, константу, конфиг), в том числе с приведением типа, → прокси; своя нетривиальная логика (проверки, бросок, null-fallback, запрос к хранилищу, содержательное преобразование) → не прокси. Формы: метод-прокси и геттер-делегат `getXY()` → звать `getX().getY()`; геттер над источником значения → читать источник по месту; класс-фасад с единственным форвардом → внедрять целевую зависимость; тонкий подкласс с флипом видимости → брать значение через родительский метод
- Прокси/обёртку не оправдывают: ни «≥2 точек вызова», ни «симметрия с соседним сервисом» (соседний оправдан своей логикой, пустая обёртка симметрию не наследует), ни модификатор доступа. Модификатор — граница против внешнего потребителя (опубликованный API, чужой непра́вимый код); нужен доступ изнутри своего модуля — звать целевой напрямую либо расширить видимость самого целевого, обёртку не заводить. Граница между процессами либо раздельно развёртываемыми модулями — настоящая, под это не подпадает. Ось тут — существование обёртки; выбор видимости члена держит «Анализ и рефакторинг»
- Операция с несколькими точками входа (два интерфейса к одной операции и т.п.) и нетривиальной разделяемой логикой — проверками, несколькими шагами, побочными эффектами, провенансом, дрейфующими при копии, — → одна единица в слое логики её предметной области, точки входа зовут её (Service Layer, Фаулер). Выносится вся последовательность: частичный вынос разводит точки входа. Расхождение с каноном: тривиальная операция (запись плюс один вызов) единицей не оформляется и при нескольких точках входа — копия двух строк дрейфом не грозит, инлайн у каждой. Одинаковый текст ошибки у вызывающих выноса не оправдывает: текст не функционал, его расхождение ничего не ломает
- «Не прокси» (своя логика по телу) и «единственный вызов / единственный потребитель» — ортогональные оси, прогонять оба теста. Юнит с оркестрацией, проверками и броском проходит proxy-тест и всё равно подлежит инлайну, если вызывается из одного места. Остановка анализа на «не прокси» — типовой срыв
- Тест на прокси и инлайн применять к форме после безопасного behavior-preserving изменения, не к текущей. Юнит, становящийся прокси или одноразовым инлайн-кандидатом после правки, не ломающей и не раскрывающей лишнего внешнему потребителю, — уже таков. Типовые трансформы: расширить видимость — безопасность по оси поведения и инкапсуляции, вторая ось — компилируемость переопределяющих наследников, пройти по ним как при правке контракта; перенести тривиальную композицию к вызывающему; вынести тело в единый источник — метод стал чистым форвардом → инлайнить в точки вызова тем же проходом, делегат не оставлять. Срыв: формулу вынес в общий сервис, старый метод оставил форвардом, точки вызова не переключил
- Перенос кода (схлопывание класса в потребителя, вынос в общий носитель, переезд между слоями и модулями, разделение файла) — написание каждой единицы заново: на новом месте у каждого метода, класса, параметра и ветки заново называется основание существовать (число вызывающих там, порог объёма и ветвистости, слой); основания нет — единица схлопывается тем же проходом
- Абстрактный/родительский класс с единственным подклассом — красный флаг преждевременной абстракции. Закрытое тело, извлечённое в родителя и зовущееся из одного подкласса, схлопывать в этот подкласс (инлайн тела и удаление базы — Collapse Hierarchy, Фаулер), пока второй подкласс не появился реально. Комментарий-обещание второго потребителя («общее тело для X/Y» при отсутствующем Y) второй подкласс не заменяет — частный случай запрещённого «возможного будущего потребителя», применённый к иерархии. Граница: звено цепочки наследования, объявленной конвенцией слоя в записанном правиле проекта, точкой вариативности не является и от правила закрыто: второго подкласса оно не предполагает by design, его тело есть свой этап слоя, не абстракция под будущего второго наследника. Общее тело, извлечённое в родителя под будущих наследников, конвенцией не закрывается: оно остаётся, пока вторую сторону — второй подкласс — исполняет тест, иная автоматическая проверка либо конфигурация развёртывания («Точка вариативности без исполнителя второй стороны»). Конвенция — записанное правило носителя, не наблюдаемая практика: «у соседей так же», «наследник пока один» и удобство её не образуют; конвенции нет → правило в силе
- Класс списывается с существующего целиком — те же точки входа (роуты, команды, обработчики), тот же разбор входа и форма ответа — с заменой тела одного-двух шагов (источник данных, правило записи) → шаблонный метод (Template Method, GoF): точки входа целиком — шаблон в базе, заменяемый шаг — абстрактная точка расширения. Расхождение с каноном — порог и признак: различие в одном значении точки расширения не даёт — ветка (буллет о почти одинаковых телах выше); признак по коду — два класса объявляют каждый своим телом точку входа с одинаковым именем либо одинаковым хвостом адреса маршрута. Второй подкласс тут существует в коде — граница с преждевременной абстракцией буллета выше

### Ветки одной развилки — одной формой

Ветки развилки равноправны, когда каждая доводит операцию до её штатного исхода: ни одна не есть отказ, ранний возврат либо частный случай. Равноправные ветки оформляются одной формой — каждая своей именованной единицей либо все инлайн ветками одного условного оператора. Метод с развилкой собственного тела ветки после неё не несёт: ему остаются преамбула и выбор ветки.
Порог отдельной единицы мерится по каждой ветке: прошли обе — выносятся обе; не прошла ни одна — инлайн обе; прошла одна → вынос соседней ради единообразия решает пользователь (`shared-orchestration`). Вторую ветку, заводимую к уже написанному телу, не писать отдельной единицей при первой в теле метода. Принцип — один уровень абстракции в методе (Composed Method, Бек); расхождение — при разных порогах у веток единообразие выбирает пользователь.

### Дополнение под одного потребителя

Единица нужна многим и остаётся; предмет правила — её дополнение (параметр, ветка, поле, режим, ключ возврата), заведённое ради одного потребителя. Знать о дополнении обязаны все: передавать значение, держать умолчание, разбирать ветку.
Перед добавлением назвать исход отказа от дополнения — чем потребитель обходится без него. Обходится общим значением либо своими средствами → не заводить: отказ меняет частность (формулировку надписи, оттенок поведения), а не механику, нужное одному потребителю решать у него самого. Остаётся лишь своя копия единицы (разметки, тела, значения) → дополнение законно.
Цену меряет число мест, обязанных о дополнении знать, не его размер; копия единицы дороже этой цены. Единственный потребитель дополнения ушёл → снять дополнение тем же проходом. Принцип — разделение интерфейсов (ISP, Мартин); расхождение — лечение не делением интерфейса, а решением у самого потребителя.

### Ось понятия и вывод из неё

Несколько признаков, всегда выводимых друг из друга и заполняемых в одном месте, — одно понятие, разложенное на флаги. Свести к одной оси с закрытым перечнем значений (частный случай make illegal states unrepresentable, Мински); заполняет её точка, где известны исходные факты. Детектор разложения — тест на обязанность носителей разойтись («Единый источник истины» выше), прогнанный по набору попарно: входа для пары не называется → признаки пары лежат на одной оси.

Вывод из оси принадлежит общему носителю — тому, что рисует, — не вызывающим. Стиль, доступные действия, подписи, тексты подтверждений, попадание под фильтры и счётчики (список открытый) он выводит сам, приняв одно значение оси. Вызывающему остаётся то, что осью не выражается.

Включатель поведения — признак, объявленный под это поведение; свойство данных, чья область шире, включателем не служит. Проба до написания условия: назвать вход, при котором свойство есть, а поведение не нужно; называется → завести свой признак, имя носителя свести к его фактической области.

Значения, друг из друга не выводимые, но всегда заполняемые вместе из одного источника и передаваемые порознь — отдельными параметрами либо полями, — запах Data Clumps, лечение Introduce Parameter Object (Фаулер). Попарный тест выше такой набор пропускает: по значению признаки расходятся всегда, вход для пары называется, и набор читается независимым. Расхождение с каноном — признак и место сборки объекта. Признак — назвать вызывающего, который заполняет одно значение без другого, а не проба удалением одного значения; не называется → значения принадлежат одному объекту. Объект собирается там, где значения уже лежат вместе: разборщик-обёртка у вызывающих распаковку переносит, а не снимает.

Точка срабатывания обоих классов — добавление параметра либо поля к существующей единице: попарный тест прогонять по новой паре, добавляемое против каждого соседа из того же источника.

## Root-fix у источника

Дефект родился в источнике (сосед/слой/процесс отдал не тот тип/формат/пакет, упал метод) — лечить в точке возникновения, не маскировать у потребителя; у потребителя — только диагностический лог. Значение без объявленного типа в источнике (текст без схемы, переменная окружения, ячейка таблицы и т.п.) дефектом источника не является → тип приводит ждущий его потребитель. Тип у источника под такого потребителя — дополнение: судит «Дополнение под одного потребителя». Принцип — закон Постела («принимай либерально»), суженный до значения без типа. Формы обхода-маскировки:

- защита ради одного типа (`if`/`instanceof`/`match`/`method_exists`/`try-catch`/fallback/null-check/конвертер) → перенести защиту в тип (сделать безопасным / реализовать интерфейс везде / явно запретить тип `throw`; у Фаулера Introduce Special Case и Replace Conditional with Polymorphism) либо починить источник
- Скан/пере-вычисление вместо инварианта, который источник обязан держать
- ПАРАМЕТР-ФЛАГ (запах Flag Argument, Фаулер), разводящий потребителей общего критерия («пропускать ли X»): сперва проверить сам критерий — склеивает два независимых свойства → расщепить в источнике на два предиката с точными именами; расхождение с каноном — режимный параметр законен, когда потребители решают разные задачи над одним свойством
- худшее — проектировать вокруг текущего неверного состояния источника: чинить источник, не строить поверх

Ограничение текущей реализации, всплывшее как «стопор», — кандидат на root-fix, не потолок: варианты выстраивать самому лестницей от простого устройства к сложному — брать простейшее устройство, решающее задачу (KISS). Формы простейшего: разовая операция над данными (мигрировать, перегенерировать, push) либо готовый инструмент вместо accommodation-кода под рассинхрон; расширение существующего механизма вместо параллельной структуры (элемент под новое состояние либо нужду — «Единый источник истины» выше); данные для другого слоя → сперва существующий канал доставки в этот слой целиком, не эмиссия в чужом модуле. Перед обходом локализовать, чьё ограничение: само-наложенное вышестоящим кодом (root-fix там), само-наложенное формой хранения (заплатка внутри контейнера — маркер-значение, сигнал о дефекте вместо предотвращения — сигнал сменить форму: искать соседа с тем же классом данных и другой формой) либо framework/внешнее. Scope держать на фактической цели.
Предмет находки лежит на канале приёма чужого артефакта (файл от художника, пакет стороннего редактора, импорт) → достижимость меряется тем, что допускают формат и код приёма; «таких данных у нас нет» недостижимостью не является.
Прогон проверки вскрыл расхождение двух носителей одного контракта (элемент есть у одного, у второго не объявлен) → направление выравнивания решает потребитель элемента — читатель значения; читателей нет → снос элемента с обеих сторон. Исполняемость производителя живости не доказывает.
Вводя инвариант (зарезервированное значение, флаг-состояние, sentinel, по которому различается поведение), защитить его guard'ом на всех точках записи поля, включая чужие слои (изолированная среда исполнения, клиент либо фронтенд, внешняя интеграция и т.п.); довод «сейчас так никто не пишет» пропуск не оправдывает. Место guard'а — где инвариант может быть нарушен, не где обнаружен: метод, отдающий данные наружу (сериализация, выгрузка), точкой записи не является. Инвариант на паре значений — точки перечислять по обоим. Заводя новую точку записи поля с действующим инвариантом, правило приведения формы держать в точке, общей всем каналам записи. Принцип — инвариант класса (Design by Contract, Мейер); расхождение — точки записи перебираются и за пределами класса, в чужих слоях.
Повод, под который код уже написан, исчез либо сменилась посылка его основания, когда соседнее решение той же задачи закрыло ту же нужду другим механизмом, → судьбу написанного решает переоценка по существу, не откат и не оставление по умолчанию; кто решает по её итогу — `shared-core` «Root-fix у источника».

## Не глушить сигнал ошибки

Удаление либо подавление сигнала ошибки (throw, log, показ пользователю) ради исчезновения симптома — сокрытие дефекта (антипаттерн error hiding): сперва заземлить механизм (почему ошибка возникает), затем чинить причину. Заземление вскрыло, что сам сигнал выбран неверно (throw на ожидаемом состоянии, где рантайм трактует его фаталом) → смена на корректный контроль-флоу законна.

## Полнота охвата и проверки

Перед суждением либо правкой кода обойти все ветви (error paths, `catch`, fallback, каскады, условные — дефект чаще в обработчике) и всех потребителей источника, у каждого свой контракт; граница потребителей — явный контракт, не предположение об идентичности. Потребителей ищут по каждой форме имени, которой канал вызова адресует единицу: своим именем и именем, выведенным из него соглашением фреймворка (аксессор по имени свойства без префикса, обработчик по имени события и т.п.). Расширение отдаваемого множества (снятие фильтра) обход не отменяет: потребитель-искатель (guard, резолвер) расширение переживает, потребитель-фильтр получает мусор либо ложный контрол — для каждого спросить отдельно.

## Утверждение о коде — после чтения этого кода

Утверждение о поведении конкретного кода (какой класс/механизм, как вычисляется значение, что отдаётся наружу) — только после чтения этого кода.
Границы «этого кода»:

- авторский текст о поведении кода (коммент, докблок, `description`, подсказка поля, сообщение об ошибке и т.п.) — не этот код: заземляет прослеженная самим цепочка (чтение вычислителя, замер в живой системе, пробный вызов). Наблюдаемое разошлось с описанным → первым действием разложить цепочку, лишь затем трогать значения. Одно правило описывают два текста у двух носителей → факт заземляет текст у той стороны, о которой утверждение; расхождение текстов — сама находка. Когда текст протухает — «Содержание комментария»
- vendor-звено на маршруте данных (submit формы, сериализатор, event-цепочка) — тот же «этот код»: читать в vendor до точки прохождения либо отбития значения
- при наследовании — член фактического класса исполнения, не предполагаемого родителя: подкласс затеняет свойство и метод
- у производного значения (кеш-поле, снимок, мемо, проекция) — вычислитель до конца цепочки, включая гейты, гасящие часть полей
- носитель срабатывает несколькими каналами (участник каркаса и слушатель событий, обработчик и планировщик и т.п.) — вывод о том, какой его эффект у операции теряется, стоит на чтении всех его каналов
- наблюдение живой системы заземляет наблюдённое значение, не правило его порождения (кто шлёт, по какому условию): правило читать в коде-вычислителе до трансляции наблюдения и до опоры на него
- обе стороны канала обмена: что уходит от отправителя, читается в коде отправителя, между сторонами лежат сборка пакета, отбор, чистка, кеш; обмен наблюдаем (пакет в журнале, дамп) → диагностировать снимком обмена, не реконструкцией из кода; вторая подряд гипотеза об одном дефекте — снимать обмен
- обе стороны сравнения («у соседа иначе», «как у X»): образец читается наравне с предметом, роль образца заземлением не является
- достижимость ветки на приходящих данных заземляет код, порождающий передаваемое состояние, — гейты каждого канала, способного состояние создать, — не механизм рассылки

Давность своего чтения, носитель, открытый под другой вопрос, и пересказ документа либо слов пользователя — `shared-core` «Заземление перед суждением».

## Вердикт и обоснование критерия

Архитектурный/рефактор-вердикт («X лучше/хуже», «не переносить», «нарушает слои») — после grep/чтения реальных call sites и принятых в проекте паттернов; общий принцип без них не основание, принцип, опровергаемый кодом проекта, отбрасывать. Форма ответа, под которой вердикт выдаётся, — `shared-core` «Вердикт и обоснование критерия».
Числовая величина, названная фактом (в ТЗ, ответе, обосновании), заземляется замером, а переход от измеренного к искомому (разность, доля, отношение) доводится вычислением до конца. Константа в коде — гипотеза о величине, до наблюдаемого эффекта стоит ещё звено; «примерно сошлось» — сигнал считать точнее. Настраиваемое поле читать у носителя настройки (конфиг, запись базы, переменная окружения и т.п.), не по объявлению в коде. Величина, зависящая от состояния системы, замеряется в рабочем состоянии. Величина с сырого носителя мерится тем же разбором формата, каким читает потребитель. Величина на входе, который выставит потребитель вывода (настройка пользователя, выбор из диапазона), берётся краем объявленного диапазона с самым тяжёлым исходом, не умолчанием, и выбор края называется рядом с числом. Замер с экземпляра переносится только на экземпляры с тем же кодом механизма, ограничивающего величину, — проверить, действовало ли ограничение на замеренном.
Место, порождающее замеренную величину (запросы, время, память), заземляется замером с атрибуцией по вызывающему, не чтением кода (правила Пайка 1–2); нет атрибуции у прибора → доработать прибор.

## Фактический вопрос ≠ нормативный

Нормативный вопрос о дизайне («как лучше/правильно организовать», «как надо») отвечается про идеал: текущая реализация — вход для фактов, не потолок для дизайна. Ответ на фактический и нормативный вопрос, доводы, подменяющие ought на is, и сильная версия чужого предложения — `shared-core` «Фактический вопрос ≠ нормативный».

- Прочитанный код встал границей пространства решений → ограничение снимать лестницей «Root-fix у источника»
- Существующий механизм защищается его свойством как требованием задачи → до возражения перебором вызывающих установить, ради чего механизм заведён и кто его потребители. Механизм, живущий ради обхода другой задачи, эталоном не бывает; своё прежнее решение планку поднимает

Инвариант, переживший стилман (дешевизна на горячем пути, безопасность), → guardrail у опасной точки, не повод отвергнуть лучшую организацию.
Каждое цитируемое отличие («у типа X нет фичи Y») классифицировать тестом «сохранилось бы это в дизайне с нуля?»: да → by-design, законный довод против; нет → пробел, довод за унификацию. Наличие у одного носителя паттерна не доказывает — конвенцию читать по всем соседям-аналогам; отсутствие у него того, что несут все соседи, — пробел. Установленная конвенция — тот же is: прецедент прогнать критерием, которым меряешь предложение, не проходит — называть долгом, не образцом, и правилом не записывать.
Перед категоричным «не делать / уже оптимально» — опровергающая линия (`shared-core` «Независимая опровергающая линия»).

## Копирование прецедента

Нормативный момент возникает не только по вопросу «как лучше», но и проактивно — когда сам проектируешь, копируя структуру прецедента (роут, форма, поток, раскладка, состав отдаваемого наружу): копирование — нормативный чекпоинт, не механическое тиражирование (cargo cult programming). Проверять перед репликацией:

- оптимален ли прецедент — не оптимален → выровнять к лучшему варианту оба (прецедент и новое), не тиражировать худший
- переносится ли обоснование формы: назвать ограничение, породившее форму у прецедента (внешний потребитель, свойство носителя), и проверить, действует ли оно на новом месте; не действует → сузить форму (private, инлайн, отдельные поля). Собственный код, чьё единственное назначение — заставить скопированную форму работать на новом месте (разборщик, адаптер, обёртка), — сигнал менять форму, не достраивать вокруг неё
- не сам ли прецедент обход у потребителя (accommodation-код над пробелом в трейте, базе, родителе) → root-fix в источник, сняв прецедент, новую копию и прочие ручные копии разом
- копируется и состав отдаваемого наружу (поля вывода, ключи ответа, схема) — каждый элемент проходит тот же чекпоинт

Точка срабатывания — момент, когда форма списывается с образца, куда бы копия ни ехала: в код, в схему хранения, в ТЗ, в вариант вопроса пользователю. Предмет шире кода: состав полей носителя, набор колонок, устройство данных.

## Образец и восстановление из git

Готовые образцы — в родительском модуле (объявленная зависимость) и в соседних модулях того же класса.
Переписывая код либо UI с удалением старых файлов — снесённую функциональность восстанавливать самому из git-истории (`git show HEAD:<путь>`) целиком за один проход и до переписывания целевого файла.
Образец не назван, а дефект — неверное взаимодействие механик, которое в другой точке тех же данных работает → рабочий контрпример искать самому первым действием и сравнить носители битой и рабочей точки до предложений вариантов; обход (запретить действие, передать человеку) до сравнения — не вариант.
Поведение одного входа операции (программный вызов, страница интерфейса и т.п.) расходится с обещанным либо со вторым входом той же операции → первым действием читать второй вход: его реализация — образец, варианты починки без сравнения не предлагаются.

## Многофайловая правка

Код ложится по новому адресу (новый подкаталог, модуль, каталог с нуля) → покрытие сводов и спек масками `paths` рвётся молча: до первой правки перечислить своды и спеки, чьи правила нужны этому коду, начиная с тех, чьи `paths` матчили прежнее место, и довести их `paths` до нового адреса.
Операция либо конструкция, живущая у нескольких носителей, перед правкой и вердиктом сверяется со всеми своими реализациями: расхождение закрывается выравниванием к лучшей либо различием, названным по устройству носителя. Разный наблюдаемый исход таким различием не бывает («Единый источник истины» выше). Носителей без реализации находит класс носителей («Охват механики по носителям и каналам» выше). При исправлении ошибок проверять все аналогичные файлы модуля. Сломан механизм → множество обхода задают его носители (типы, сущности, страницы), не сходство файлов; по каждому — свой вердикт достижимости, исход назвать перечнем носителей.

## Содержание комментария

Правило, записанное в своде правил, комментами по коду не пересказывается: у кода — не больше одного короткого указателя на правило, в точке принятия решения. Корпус правил лежит вне репозитория кода → указателя на свод в коде нет.

Однотипный код в N местах, требующий пояснения, → сперва проверить, не снимается ли сам дубль дедупом («Дедупликация»); дедуп невозможен либо by-design (кросс-модуль, кросс-язык, симметрия ORM-сущностей) → знание в одном каноне: общий узел кода (трейт, база, интерфейс, enum, докблок), а без узла — ведущий носитель. Зеркалу коммент не нужен, когда код сам ведёт к канону; короткий указатель — только у неочевидного зеркала-ловушки (guard, риск рекурсии, неявный инвариант), указатели разные. Финальным проходом искать оставшиеся идентичные строки-комменты.

Содержание комментария (любой язык) — только ограничение либо инвариант, которого код не показывает: причина неочевидного решения, чужая система координат, скрытый контракт потребителя. Принцип — комментарий отвечает «почему», не «что». Не писать: пересказ следующей строки; историю правки и переход было→стало («X убран», «теперь Y вместо Z», «раньше было») — тот же запрет у любого авторского текста-описания (`shared-core` «Пишу текст описания или контракта»); обоснование правки ревьюеру — ему место в описании pull request. Причина-инвариант под запрет не подпадает. Плотность комментирования соседнего кода индульгенцией не является. Судья очевидности — будущий читатель без контекста: механику он выведет из кода; понимание, размазанное на много прыжков, — сигнал рефактора, не повод для коммента. Протухает то, что дублирует извлекаемое из кода; внекодовое стабильное (внешний контракт, чужая система координат) не протухает.
