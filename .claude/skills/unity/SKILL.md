## Доступность Unity MCP

Тулы `ai-game-developer` отвечают только при запущенном на машине пользователя Unity Editor с MCP-плагином (Window/AI Game Developer → Start).

- Проба — прямой вызов из сессии тула состояния редактора сервера `ai-game-developer` (`editor-application-get-state`): он же сразу отдаёт нужный контекст — Play Mode и состояние компиляции. Тулы сервера deferred, схему догрузить `ToolSearch`.
- CLI `npx unity-mcp-cli run-tool <tool-name> --input '<json>' --url <url>` (`<url>` — значение `mcpServers.ai-game-developer.url` из `.mcp.json` ЦЕЛИКОМ, вместе с путём после порта; урезанный до `host:port` адрес отвечает отказом всегда) — запасной канал, только когда сервера `ai-game-developer` в сессии нет вовсе. Его отказ недоступности плагина НЕ доказывает: отказ о маршруте самого CLI, `HTTP 404` приходит и при живом Editor, отвечающем на прямой вызов тула.
- Сырое JSON-RPC-рукопожатие по порту плагина (`initialize`, `notifications/initialized`, `tools/call` через curl либо скрипт) каналом агента не является. Ответ порта на `initialize` приходит и при недоступных в сессии тулах — доступности тулов он не заземляет. Разбор SSE-ответа стоит ходов. Запрет — о канале работы агента, не о коде хуков, ходящих по тому же порту.
- Вывод «Unity MCP недоступен» и отказ от Unity-задач — только после проверки пути до плагина (пункт ниже); у сервера `ai-game-developer`, подключённого к сессии, проверке пути предшествует отказ ПРЯМОГО вызова тула.
- Сервер `ai-game-developer` не подключился к сессии либо отказ соединением пришёл на прямой вызов тула или на CLI → о редакторе это не говорит: сперва проверить путь до плагина — слушает ли порт из `.mcp.json` процесс на Windows (`netstat.exe -ano` из WSL) и совпадает ли сетевой режим WSL (`wslinfo --networking-mode`) с требованием `docs/Окружение Windows и WSL.md`. Режим расходится с требованием либо слушатель есть, а соединения нет → пользователю идёт правка пути. Слушателя нет → проба процесса редактора («Запуск и закрытие редактора»): не запущен — запустить самому, запущен — просьба поднять сервер плагина. Правка пути и запуск бывают нужны разом.

## Запуск и закрытие редактора

Редактор клиента запускать и закрывать самому. Открытым его держат только под работу, которой без него нет: проверку в Play Mode, прогон тестов клиента, сборку и осмотр сцены либо элемента интерфейса и т.п. Закрывается программа целиком: остановка Play Mode (канон клиента, «Вход в игру») выхода из неё не заменяет.

- Проверка компиляции правки C# идёт без редактора — компилятором `csc` из .NET SDK. Редактор скомпилирует правку сам при следующем запуске. Ссылки и `DefineConstants` правленой сборки брать из её `<имя сборки>.csproj`, сгенерированного Unity в корне клиентского проекта. Список исходников в нём сверять с `.cs`-файлами сборки на диске: файл, которого в списке нет, `csc` не видит — компиляция сходится без него.
- Импорт ассетов (`.meta` новому файлу заводит только обновление ассетов в редакторе) и поведение в игре компиляция `csc` не показывает — они предмет проверки в Play Mode. Проверка в Play Mode идёт без подтверждения (`workflow-gates` «Проверка правки») пачкой по всему накопленному к концу работы, не после каждой правки. Редактор поднимается под неё разово.
- Жив ли редактор, показывает проба процесса `Unity.exe`, в чьей командной строке стоит путь клиентского проекта. Процессы с `-batchMode` (воркеры импорта и т.п.) редактором не считаются. Порт плагина признаком не служит: его слушает отдельный процесс сервера плагина.
- Запуск — только при отрицательной пробе процесса, фоновой командой: редактор версии из `ProjectSettings/ProjectVersion.txt` клиентского проекта с `-projectPath` этого проекта. Готовность — ответ тула состояния редактора, дожидаться её поллингом.
- Закрыть редактор, как только он не нужен ближайшему шагу: пачка работы в нём кончилась, работа уходит в ожидание человека (окно вопроса, стоп-сигнал и т.п.), ответ завершается. Правка под немедленный повтор той же проверки — ещё работа в редакторе. Редактор, в котором шла своя работа, закрывается и тогда, когда его запустил пользователь.
- Условие выхода — чистое состояние: игра не идёт и не запускается, нет компиляции и импорта (идут — дождаться конца), не открыт режим правки префаба, ни одна открытая сцена не помечена изменённой. Нечистое от своей работы — привести к чистому (игру и сцену — порядком канона клиента). Нечистое не от своей работы — редактор не закрывать, причину назвать в итоге ответа.
- Выход — `script-execute` с прямым вызовом `EditorApplication.Exit(0)` в теле скрипта. Условия выхода проверяет тот же скрипт перед вызовом. Через `EditorApplication.delayCall` у редактора без фокуса выход не исполняется. `Exit` не спрашивает о сохранении: свои правки ассетов сохранить до него. Ответ вызова приходит обрывом соединения, закрытие подтверждает проба процесса редактора.
- Моменты завершения ответа и вопроса человеку подпирает хук `.claude/hooks/unity-playmode-stop-reminder.sh`: редактор, в котором работал вызывающий, он закрывает сам при чистом состоянии, иначе называет причину; при живом фоновом исполнителе вызывающего не закрывает. Правило действует и при смолчавшем хуке; текст доклада хука — осознанный дубль, правится парно.

## Путь к файлу из редактора

Код, исполняемый внутри редактора (`script-execute`, редакторный скрипт), — процесс Windows: каталог WSL он адресует UNC-путём `\\wsl.localhost\<дистрибутив>\<абсолютный путь WSL>`. Имя дистрибутива отдаёт переменная `WSL_DISTRO_NAME` из WSL. Каталог инструмента текущего проекта такой код адресует этой же формой — само правило места файла держит skill `artifact-check` «Место файла, заведённого по ходу работы».

Форма годится, пока путь разбирает сама платформа. Пакет, собирающий путь своим кодом, UNC схлопывает — файл уходит не туда, и отказа не приходит: такому пакету каталог WSL называют буквой диска, назначенной этой файловой системе. Действующий случай — пакет записи у оснастки съёмки роликов (skill `video-pipeline`).
