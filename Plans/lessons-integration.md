# План: интеграция lessons → release (этапы по группам приоритета)

## Контекст

Источник: `D:\lessons\` — каталоги RPG_01..RPG_38 по [Unity RPG Tutorial](https://www.youtube.com/playlist?list=PLX-uZVK_0K_6JEecbu3Y-nVnANJznCzix); Lesson #0 — intro без кода. Состав видео каждого урока — `D:\lessons\README.MD`.

Однако release — это MMO-клиент с серверной стороной (`Z:\var\www\html\game`), не singleplayer-RPG из туториала. Поэтому уроки служат **референсом UI/UX и потоков**, но не копируются дословно — данные приходят с сервера, а singleplayer-логика (save-load, локальные характеристики) заменена на сетевые пакеты.

## Порядок

Этапы разложены по четырём группам приоритета. Разработка идёт группами 2 → 4, внутри группы — сверху вниз; старт — первый этап группы 2. Группа 1 очереди не образует: это копилка правок значений, они подкручиваются по мере надобности и в любой момент. Номер урока при этапе — пометка происхождения, очерёдности не задаёт. Этап без номера — тема, которой в уроках нет вовсе (уроки одиночные). «Первый незакрытый этап» = первый этап без ✅ в группах 2 → 4.

| Группа | Что попадает |
|---|---|
| 1 — Баланс и настройка | правка значений без нового кода: таймауты команд, периоды восстановления, шансы дропа, цены, радиусы |
| 2 — Обязательное новое | без чего MMO RPG не существует |
| 3 — Дешёвые закрытия | фактически сделано либо стоит часы: проверить и вычеркнуть |
| 4 — Потом | нужное, но откладываемое; часть — после запуска игры |

Группа 1 отделена решением пользователя: смешанная с разработкой механики правка значений завышала оценку этапа. Настройка значения, всплывшая по ходу другого этапа, уходит в группу 1.

**Гейт перед каждым этапом:** кратко изложить пользователю, что делает этап и что предлагается перенести (взять / урезать / выбросить — в уроках бывает ненужное для MMO), работу начинать только по его подтверждению. Вердикт «не делаем» — пометкой by-design в разделе «Не делаем», этап не удалять.

**Исходники урока:** код уроков инкрементален — каждый следующий диффается с предыдущим и несёт исправления ошибок предыдущих. Открыв исходник урока, брать и фиксы последующих уроков по той же теме.

**Серверные части этапов:** игровые данные (компоненты, события, префабы) живут в БД и правятся только через MCP-тулы домена (`element-*`/`entity-*`/`game-*`); каталога `Build/Game/storage/php/...` на диске НЕТ (проверено) — упоминания таких путей в этапах ниже унаследованы от прежней версии плана как доменные ориентиры (какой компонент/событие/префаб нужен), конкретику исполнитель выясняет на старте этапа через `*-schema`/`*-list`.

## Принципы

1. **Адаптация, не копирование**: каждый Unity-RPG-урок переносится в текущую архитектуру (Spriter+Universal animator, EntityModel, MMO-пакеты, серверный source-of-truth). Singleplayer-механики (SaveManager, локальный XP) — выбрасываем.
2. **«UI меньше — режем сервер»**: если в плане UI меньше slot-ов/полей/etc, чем шлёт сервер — сужаем сервер, а не раздуваем UI.
3. **Серверная разработка идёт параллельно** — части этапов уже имеют ready/in-progress серверные планы (см. в этапах).
4. **Прототип-платформа, не конкретная игра**: game-specific геймдизайн уроков (редкости/quality и подобное) не заводим; новые поля/компоненты — только при реальном потребителе, абстрактно и без перегруза функционалом. Существующие универсальные поля (`Prefab.name`, `Prefab.description` из админки) переиспользуем вместо введения новых.

Файлы: [TilemapXray.shader](../Assets/Shaders/TilemapXray.shader) (шейдер `Mmogick/TilemapXray`), [TilemapXray.mat](../Assets/Resources/Materials/TilemapXray.mat), [TilemapXray.cs](../Assets/Plugins/Mmogick/Client/Model/TilemapXray.cs), [MapController.cs](../Assets/Plugins/Mmogick/Client/Controller/MapController.cs) (навешивание компонента и разметка слоёв карты после загрузки). ## Группа 3 — Дешёвые закрытия

### Этап #17 — Контейнеры: возврат существ, приватная добыча, сундуки (#17.0–17.3) [LARGE]

Разросся против урока решением пользователя (2026-08): вместо точечного «окна сундука» — единая модель контейнера для трупа и сундука плюс возврат существ в мир. Урок даёт только сундук (#17.1–17.2) и ревизию фиксов (#17.0); слоты сундука (#17.3) у нас уже покрыты сеткой окна добычи из #14.

#### Почему шире урока

Труп с пустой добычей до этапа гасил КЛИЕНТ: рендер всех частей тела принудительно отключался, кликабельные зоны выключались, и всё это пере-сканировалось каждые полсекунды (визуал Spriter собирается асинхронно). Выключить сам объект нельзя — следующая дельта не нашла бы его и создала дубль. Это был обход отсутствующего серверного удаления: решение «видно ли тело» принимал не владелец состояния.

Второе: состав добычи был публичен (компонент `loot`, isSend) — содержимое КАЖДОГО контейнера ехало каждому, кто его видит. Для временных трупов терпимо, для карты с сундуками — мусорный трафик и подглядывание чужого лута издалека.

#### Модель

1. **Возврат существ — в основе (фреймворк rpg2d).** Очередь отложенного создания в `World`, разбираемая каждый кадр в `refresh` (рядом с очередью удаления). Событие-таймер на самой сущности для этого не годится: к моменту возврата сущности уже нет, а события вдобавок исполняются только когда рядом есть живой игрок. Тик игры (`Game.tick`) под очередь не годится — это вызов пользовательского кода каждый кадр.
2. **Смерть → удаление, не оживление на месте.** Не-игрок по истечении срока лежания (группа `status/despawn`, 60 секунд) снимается с карты, и выходной код сущности ставит заказ на возвращение на точку появления; пауза до возвращения — настройка игры (по умолчанию 30 секунд). Игрок остаётся на своей ветке: `status/resurrect` поднимает его на месте, тело с карты не убирается.
3. **Точка появления — в `buffer`, её кладёт код инициализации фреймворка** тем, кого создаёт при старте карты: к моменту смерти существо уже ушло с неё. Носитель общий — своей копии точки появления есть не у каждого: мобу без зоны её кладёт код входа игры в параметры события блуждания, у зонных (обход по точкам) копии нет.
4. **Добыча приватна.** `loot` перестаёт быть публичным; состав едет адресно тому, кто открыл контейнер, — адресную доставку ведёт событие открытия `ui/loot/open`. Во фреймворке уцелели примитивы прежней модели — `isLootableBy` и `inventorySendTo`. Право на добычу остаётся публичным: его несёт команда группы `status/lootfree`. Клиент рисует отсчёт над телом по остатку её срока. Список допущенных мал, публичность его не отягощает.
5. **Труп и сундук — одно понятие «контейнер»**, обыскиваются одним событием. Разница: труп по таймауту уходит, сундук остаётся стоять.
6. **Сундук открыт/закрыт — действие сущности.** Открытие ставит `action=open`; закрытие ведёт проверка столкновений на клетке контейнера: пока на ней стоит игрок, действие остаётся прежним; игрока нет — действие возвращается в `idle`, и проверка снимает сама себя. Действие `open` заводится в справочнике действий игры.

#### Клиент

Скрытие пустого тела снимается целиком ([CorpseLootMarker.cs](../Assets/Scripts/Model/CorpseLootMarker.cs) — `HideBody`/`ShowBody`/пере-сканирование); окно открывается по ответу события, а не локально по публичной дельте. Закрытие окна при исчезновении сущности клиент уже умеет ([LootWindowController.cs](../Assets/Scripts/Controller/LootWindowController.cs), `RefreshWindow`).

#### Контент сундука

Картинки — из уроков (`RPG_38/RPG_38_00/RPG/Assets/Sprites/Chest`): `chest_closed.png` + `chest_open.png`, отдельные файлы, а не кусок атласа (в TMW сундук лежит внутри общего листа NPC-спрайтов `graphics/sprites/model/unique.png`, кадры 8 и 9, и открытого состояния там нет вовсе). Два состояния набором картинок не выразить — он разводит картинки по ракурсу; значит анимация с двумя клипами (закрыт/открыт), как у портала (одна поза клипом).

Точки размещения — по картам TMW, где сундуки стоят NPC-скриптами (`tmw/tmwa-server-data-master/world/map/npc/*/chest.txt`: карты 002-5, 004-5, 013-3, 052-2, 099-8 с координатами).

**Зависимости:** #14 (окно добычи, события переноса).
**Верификация:** Play Mode — моб убит, тело лежит, обыскивается, по таймауту исчезает и возвращается на точку появления; сундук открывается кликом, содержимое приходит только открывшему, крышка закрывается по сходу с клетки.

#### Ход работы (2026-08-06)

✅ **Основа (rpg2d):** очередь отложенного создания в `World` — поле `$_delayed`, метод `addLater(prefab, data, delay)`, разбор — `releaseDelayed()` из кадра, и только когда на карте есть живые существа в округе (тот же список по `lifeRadius`, что кадр собирает для событий): без них мир не меняется вовсе, возврат ждёт своего часа в очереди. Признак «обрабатываться вдали от игроков» задаёт существу `lifeRadius`, отдельного механизма под это не заводим.
✅ **Смерть → удаление + возврат:** не-игрок по смерти уходит с карты и через паузу возвращается на точку появления, мёртвый игрок воскресает на месте. Проверено логом песочницы: тело удалено, существо создано заново и снова ходит. Раскладка исполнителей потом переделана — действующая описана пунктом «Подготовка существа к возврату — в выходном коде сущности» (раздел «Закрыто вне нумерации этапов»).
✅ **Приватная добыча:** компонент `loot` больше не рассылается видящим (`isSend=false`, доступен и виду `object`), его триггер шлёт состав адресно всем, кто стоит на клетке контейнера. Событие `ui/loot/open` восстановлено из пометки удаления и переписано под `loot`; описания `ui/inventory/take`/`put` обновлены.
✅ **Отмена подхода:** при пометке группы `ui/loot` удалённой из кода `move/walk/to` выпала строка, снимавшая подход к контейнеру, когда игрок уводит персонажа сам (в git-версии файла она есть). Возвращена, описание события обновлено.

### Этап #14 — Loot (#14.0–14.6) [MEDIUM] ✅

Вердикты пользователя (2026-07): окно добычи — UI с ВЫБОРОМ, что забирать; размер окна ≤ размера инвентаря (лут-выдача не может превышать вместимость инвентаря by-design); страницы урока (#14.4, по 4 строки на страницу) не переносим.

**Модель добычи (сервер)**

- добыча — приватный компонент `loot` самой сущности: видящим не рассылается, состав едет адресно по событию открытия `ui/loot/open`;
- состав разыгрывается в момент смерти по компоненту `loot_table`; инвентарь и экипировка существа при смерти не трогаются;
- право на добычу несёт команда группы `status/lootfree` на трупе: забрать может тот, кто в её списке допущенных; команды нет — добыча свободна любому;
- перенос предметов — события группы `ui/inventory` (`take`, `put`, `index` с параметром `key`); выдачу исполняет контейнер через служебную группу `item/give`;
- ёмкость добычи равна ёмкости инвентаря (число слотов в значении по умолчанию компонента `inventory`);
- гашение добычи — по виду сущности: у не-игрока невынесенное пропадает вместе с телом, уходящим с карты по сроку лежания; у игрока тело с карты не убирается, а добычу, право на неё и накопитель урона гасит воскрешение;
- круг допущенных расширяется ступенями по вкладу урона, пока допускать не станет некого; общий срок закрепления (30 секунд от смерти) очередь делит на ступени поровну и от обеих веток не зависит.

**Окно добычи (клиент)**

- момент показа решает клиент: игрок стоит на клетке трупа. Клик по трупу издалека — обычное движение к его клетке, окно открывается по прибытии;
- сетка слотов по паттерну инвентаря, перерисовка только по серверным дельтам компонента; опустевшая добыча закрывает окно;
- кнопка «Забрать всё» — одна команда `take` со списком всех занятых позиций: инвентарные команды сервер исполняет по одной за тик, пачка отдельных take затёрла бы сама себя;
- право на добычу зеркалится неактивными кнопками — UX-фильтр поверх серверной проверки;
- файлы: [LootWindowController.cs](../Assets/Scripts/Controller/LootWindowController.cs), [CorpseLootMarker.cs](../Assets/Scripts/Model/CorpseLootMarker.cs), `LootTakeResponse`/`LootPutResponse`, метка слота контейнера `LootSlotMarker` с ветками переноса в `Item.Use`.

**Отличия от урока — by-design:** перетаскивание контейнер↔инвентарь и «Забрать всё» в уроках отсутствуют (в #23 лишь рефактор Item→Drop для сбора с нескольких трупов) — оба введены решением пользователя.

**Проверено** (Play Mode 2026-08-06): окно открывается по прибытии на клетку трупа, взять / положить / переставить, стак, забор последнего предмета — окно закрылось само, добыча пуста, ошибок в консоли нет.

Последний прогон: сошёлся 21 сценарий — приватность состава, открытие с подходом, розыгрыш добычи при смерти, отсчёт права на добычу, забор и укладывание, срок лежания тела с возвратом существа, пополнение приведением к составу префаба. Не проверены каналом сценарии, требующие двух игроков в бою (существо гибнет за секунду, а второй игрок вступает через служебный канал с задержкой около 10 секунд), воскрешение игрока и несколько краевых предусловий. ### Этап #18 — Торговец: покупка и продажа (#18.0–18.5) [MEDIUM] ✅

Вердикты пользователя (2026-08-13): покупка и продажа делаются одним этапом; ассортимент торговца — ограниченный запас с пополнением по сроку, не бесконечный; цена строится по образцу TMW — базовая цена у предмета, множители у торговца.

#### Модель

1. **Торговец — контейнер с ценником**, не параллельная ветка: то же окно и те же команды переноса, что у сундука. Покупка — забор из контейнера (`ui/inventory/take`), продажа — укладывание в него (`ui/inventory/put`); отдельных команд «купить» и «продать» нет. Отличие от сундука одно: перенос платный.
2. **Ассортимент и запас монет лежат в компоненте добычи торговца** (`loot`), заданном его префабом. Пополняет их команда пополнения контейнера (`object/container/respawn`) — та же, что у сундука. Ею же исполняется записанное в описании префаба `coin`: запас монет торговца ограничен и восстанавливается тем же сроком, что его товар.
3. **Деньги — предмет `coin`**, отдельного счёта у игрока нет: цена списывается из его стака монет, выручка от продажи зачисляется туда же. Источник денег в мире уже есть — монеты выпадают из существ таблицей дропа.
4. **Базовая цена — компонент предмета, множители — компонент торговца.** Базовую цену несут те же виды, что и компонент количества, — `item` и экипируемые. Множителей у торговца два: наценка при продаже игроку и множитель при скупке у него. Наличие компонента множителей и означает, что сущность торгует. Образец TMW: базовых цен у предмета две — покупки и продажи (`tmw/tmwa-server-data-master/world/map/db/item_db_*.txt`), а в списке товаров торговца стоит множитель к базовой (`world/map/npc/*/shops.txt`); у нас база одна, обе стороны сделки задают множители торговца.
5. **Покупку исполняет контейнер.** В своём тике он считает цену, затем читает стак монет покупателя. Монет хватает — покупателю одним изменением состояния уходят и зачисление товара (`__add`), и новые значения его монетных слотов: абсолютные числа с пометкой переноса (`__transfer`). Монеты контейнер зачисляет себе. Точка истины одна, возвратов нет.
6. **Продажу исполняет игрок** — владелец своего инвентаря: списывает товар у себя и заявляет контейнеру выдать N монет. Команде выдачи (`item/give/index`) для этого нужен параметр количества: сейчас позиция выдаётся только целиком.
7. **Множители от статов предмета** ложатся поверх базовой цены на этапе #36, вместе с появлением самих статов: без потребителя не заводятся (принцип 4).

#### Отличия от урока — by-design

- Продажи в уроке нет вовсе — она решение пользователя.
- Страницы по 10 строк не переносим: в окне добычи от страниц уже отказались, высота панели считается по числу ячеек.
- Раскраска названия по редкости не переносится — редкостей у нас нет (принцип 4).

**Зависимости:** #14 (окно контейнера и команды переноса), #17 (контейнер, приватный состав, пополнение по сроку).
**Верификация:** Play Mode — подойти к торговцу, открыть, купить предмет (монеты убыли, товар в инвентаре), продать предмет (монеты прибыли), опустошить ассортимент и дождаться пополнения.

Дефекты платформы и контента, не этапы уроков.

- ✅ **Baseline-префаб не доезжал до клиента и блокировал вход** — починено 2026-08-14. Вход в игру выбрасывало на экран входа с ошибкой «У заклинания thunderbolt2 не задана группа команды (компонент event)»: на сервере у префаба всё на месте, а в клиентском каталоге префабов его нет вовсе. Механизм оказался не тот, что был записан прежде. Восстановление помеченного элемента больше не удаляет строку в базе: возврат содержимого к версии из git снимает пометку заодно, строка остаётся, её дата двигается, и восстановленный префаб приходит клиенту в дельте каталога. Прежде строка удалялась, дата возвращалась к файловой, и в дельту префаб не попадал никогда. Тем же снят второй дефект: помеченный префаб с привязкой картинки либо анимации нельзя было вернуть вовсе — удаление строки отбивал guard самого префаба. Проверено прогоном: префаб с анимацией помечен, восстановление прошло, привязка цела, префаб пришёл в дельте. Клиентский добор недостающих записей каталога снят решением пользователя: обход у потребителя, вдобавок глушащий сигнал. Вместо него клиент сбрасывает каталог в ветке ошибки книги заклинаний — саму ошибку по-прежнему показывает, но игрок не попадает в петлю «вход → та же ошибка → вход». Чем именно была выбита из кеша исходная запись `thunderbolt2`, установить не удалось: кеш затёрт до разбора.
- ✅ **Карта 55 падала** — починено 2026-08-14. Причина: у сущностей появились поля без применённой миграции, и любая перезагрузка данных карты валила процесс ошибкой «неизвестная колонка». Миграции применены, карты поднимаются.
- ✅ **Существо не вернулось на точку появления** — отдельного дефекта возврата нет. Карта 54 упала раньше, чем истекла пауза возврата: её журнал ошибок нёс ту же «неизвестную колонку», что и пункт выше. Сам возврат подтверждён прогоном спеки добычи в тот же день.
